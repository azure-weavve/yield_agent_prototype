## 0. 결론 요약

문서가 "단일 claim 전제로 얽혀 있다" 고 지목한 세 파일 중 **`registry.py` 는 거의
무관하고, `hypotheses.yaml` 은 계약 문서로서만 얽혀 있다.** 실제 결합의 중심은
문서가 언급하지 않은 **`graph/evidence.py` + `graph/nodes.py::_finalize_gate`** 다.

그리고 **"다축 집계" 는 이미 끝나 있다.** 남은 알맹이는 문을 넓히는 것이 아니라
**문에 들어올 자격을 넓히는 것**이다. 지금 계약은 이렇게 요약된다.

> 리포트의 근거가 될 수 있는 것은 **`hypotheses.yaml` 에 등록된 가설이 발급했고,
> 고정 판별선을 넘은 후보**뿐이다. 그 둘 중 하나라도 어긋나면 출력이 **0줄**이다.

문서 §5 가 말한 "챔버 B가 의심되나 온도인지 파티클인지 구분 불가" 를 담을 자리가
없는 이유가 정확히 이것이다.

## 1. 이미 끝난 것 (문서가 낡았다)

문서 §3 "서술의 얕음" 과 §6-1 의 "다축 집계 리팩터" 는 상당 부분 이미 구현돼 있다.
그대로 실행 계획으로 읽으면 없는 일을 한다.

## 2. 실제 결합 지점 (영향 범위)

### A. Claim 은 등록 가설만 발급한다 — 잔차가 들어올 문이 없다

```
hypotheses.yaml → registry.load_hypotheses() → engine.evaluate()
                                                 └ {"hypothesis_id": ..., "candidates": [...]}
                                                        ↓
                       evidence._is_hypothesis_result()  ← 판별자
                                                        ↓
                                    Claim → ClaimGroup → final_claims → 리포트
```

- `graph/evidence.py:409` `_is_hypothesis_result()` — dict 이고 `hypothesis_id` 와
  `candidates` 를 **둘 다** 가져야 Claim 이 된다.
- 그 형태를 만드는 곳은 `domain/engine.py:evaluate()` **하나뿐**이고,
  `hypothesis_id` 는 `spec['id']` 즉 **`hypotheses.yaml` 에 적힌 이름**이다.
- 결과: **2단 센서(`compare_sensor_distribution`)는 후보를 내도 Claim 이 되지
  못한다.** claim_id 자체가 없으므로 `finalize` 로 지목할 수도 없고, 순위·접기·
  `final_claims`·`[근거]` 어디에도 못 들어간다. 게이트는 "2단 센서로 근거를 더
  좁혀라"(`_no_candidate_action`)라고 안내하면서, 그 결과를 승인 대상으로는
  받아 주지 않는다.

**이것이 "등록된 가설 이름을 강제하는 finalize 계약" 의 실체다.** 미등록 잔차를
1급 출력로 올리려면 여기가 첫 관문이고, 손댈 곳은 `evidence.py` 의 판별자와
`Claim` 의 필수 필드다. `registry.py` 는 건드릴 필요가 없다.

### B. 이진 판별선이 "출력 유무" 를 정한다 — 약한 신호 = 무신호

- `_record_evidence` ← `ranked_groups()` ← `Bundle.passing()` — `passes=True` 인
  후보만 통과한다.
- `passes` 는 `domain/engine.py:_passes()` 가 `score >= 0.5` · `target_pass >= 2` ·
  `status == ok` 로 정한다. 연속값이 이 지점에서 **부울로 붕괴**한다.

**실측(조사 중 재현):** 등록 4축을 전부 돌리고, 그중 한 축이 `score 0.4 · p 0.2`
후보를 냈는데 판별선(0.5)을 못 넘은 상태로 게이트를 부르면 —

| 상황 | 판정 | `final_claims` |
|---|---|---|
| 4축 ok + 미통과 후보만 | (loop 1) 반려 → (loop 7) `inconclusive` | `[]` |
| ok + no_signal 섞임 | `no_signal` ("대조한 축에서는 원인을 좁힐 수 없다") | `[]` |

즉 **"약한 신호가 있다" 와 "아무것도 없다" 가 같은 출력**이다. 수치 자체는
`findings` JSON 으로 리포트 LLM 프롬프트에 흘러가지만, 코드가 붙이는 `[근거]` 줄과
`claims` 블록에는 0건이고 sys 프롬프트는 동시에 "신호 없음으로 서술하라 ·
확정 결론을 쓰지 마라" 를 건다. 잔차는 구조적으로 소각된다.

부수 효과: 미통과 후보만 있으면 `_no_candidate_action` 의 물러설 안내(`step_back`)도
안 붙는다((2)(3)(3b) 어느 것도 안 열리므로). LLM 은 종료할 길이 없어 `MAX_LOOPS`
까지 왕복하다 `inconclusive` 로 끝난다 — 예산 낭비 경로이기도 하다.

> **[2026-09-12 갱신]** 이 절 전체는 2026-08-31 당시 관측이다. 위 표의 "4축 ok +
> 미통과 후보만 -> loop 7 `inconclusive`" 는 그 뒤 두 차례 닫혔다: 판별선 아래
> 후보는 이제 `weak_signal` 로 잔차 출력되고(2026-09-06), 전축 ok · 통과 0 · 잔차도
> 0(score 가 잔차 아랫선에도 못 미침)인 상태는 `no_separation` 이 loop 7 전에 받는다
> (M4, 2026-09-09). "약한 신호가 있다" 와 "아무것도 없다" 가 같은 출력이라는 결론은
> 더 이상 참이 아니다.

### C. 순위 축이 순열 p 하나 — 잔차에는 p 가 없다

- `evidence._rank_key()` = `(p_permutation, -score)`, p 가 없으면 **1.0 으로 최하위**.
- 센서·잔차 후보는 p 를 내지 않는다(설계상 안 낸다 — `tools/sensor_compare.py`
  모듈 docstring이 "p-value 를 쓰지 않는다" 를 못박았다).
- 그래서 A 를 열어 잔차를 Claim 으로 승격시키면 **전부 자동으로 꼴찌**가 되고,
  게이트 (1)번은 "1등 묶음" 을 요구하므로 잔차는 영원히 승인되지 않는다.

문서 §7 첫 항목("축 간 효과 크기의 공통 척도")과 **같은 자리다.** A·B 를 하면
이 문제가 즉시 따라온다 — 미룰 수 있는 별건이 아니다.

### D. 종료 사유 어휘에 "구분 불가" 가 없다 — 판정 하나 추가 = 코드 4곳

`finalize_status` 는 현재 11종(`graph/state.py:25`)이고, 값 하나마다 대응하는 자리가
정해져 있다.

| 자리 | 파일 | 분기 수 |
|---|---|---|
| 게이트 판정 | `graph/nodes.py::_finalize_gate` | 5 (+조기 출구 6) |
| mock 결론문 | `llm/client.py:255~295` | 10 |
| 운영 sys 프롬프트 | `llm/client.py:398~443` | 10 |
| 라우팅 | `graph/build.py:24` | 값 유무만 봄 (변경 불필요) |

`no_signal` 의 개문 조건은 `not passing()` **and** `not claim_id` **and**
`"no_signal" in statuses` 다. 세 번째 조건 때문에 **"후보는 났지만 약하다" 는
no_signal 로도 들어올 수 없다** — 문서 §7 세 번째 항목("no_signal 의 재정의")이
가리키는 지점이 정확히 이 조건절이다.

### E. 상태 스키마는 서술이 단수다

- `final_hypothesis: str` · `final_confidence: float` — 근거는 이미 복수인데
  **서술과 확신도는 하나**다. "A인지 B인지 구분 불가" 는 근거 목록이 아니라
  서술 쪽에 담겨야 하는 정보다.
- `Claim` 은 frozen dataclass, 1급 필드 17개 + `extra` dict. 잔차 표시나 "다음에
  무엇을 보면 갈리는가" 필드를 `extra` 에 넣으면 게이트는 읽을 수 있지만
  `format_group_line`·리포트 프롬프트가 안 본다 → 1급 승격이 필요하다
  (`_FIRST_CLASS_FIELDS` 도 같이 고쳐야 한다, `evidence.py:50`).

## 4. 그래서 무엇을 어떤 순서로 바꾸는가 (권고)

순서 의존이 A → C → B → D/E 로 한 방향이다.

1. **C 먼저 (공통 척도).** p 없는 후보를 어떻게 줄 세울지 정하지 않으면 A·B 의
   결과물이 전부 꼴찌로 밀려 아무 데도 안 나온다. 가장 까다롭고 가장 앞이다.
2. **A (Claim 발급 자격 확대).** `_is_hypothesis_result` 판별자와 `Claim` 필수
   필드를 손대 등록 가설 밖의 증거도 claim_id 를 받게 한다.
3. **B (판별선의 이진 붕괴 완화).** `passes` 를 출력 유무의 스위치로 쓰는 것을
   멈추고, 미통과 후보도 "잔차" 로 실어 보낸다. `REPORT_MAX_EVIDENCE` 상한이
   이미 있어 폭주는 막힌다.
4. **D/E (어휘와 서술).** "구분 불가" 판정 신설 또는 `no_signal` 분해. 판정 하나당
   `_finalize_gate` + mock + 운영 프롬프트 3곳을 **반드시 같이** 넣는다.

**착수 시 훼손 실험 필수.** 지난 5회 리뷰에서 매번 실재 결함이 나왔고 그 절반이
"고치다 만든 회귀" 였다. 특히 **버킷/분기를 새로 만들면 '그 후보가 예전 버킷에
있었기에 켜지던 조건' 을 전부 찾을 것** — `passing()` 에 매달린 곳이
`_record_evidence`·`_gate_rejection`·`_no_candidate_action` 세 군데다.

## 5. 이번 조사로 정정된 것

- 문서 §6-1 의 "`domain/evidence.py`" 는 오타다. 실제 경로는 **`graph/evidence.py`**.
- "`registry.py` 가 단일 claim 전제로 얽혀 있다" 는 **사실이 아니다.** registry 는
  yaml → StructuredTool 변환만 하고 claim 을 모른다. 계약 변경의 영향이 없다.
- 문서 §6 step 0 의 config 버그는 **이미 해결**돼 있다(`tools/commonality.py:97-99`).
