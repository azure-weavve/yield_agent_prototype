# status_node 분석 · 문제점 · 목적 재정의

> 2026-07-18 논의 정리. 앞부분은 현재 동작·문제점의 **분석 기록**, 뒷부분은
> 목적 재정의에 따른 **재설계 방향**이다. 아직 확정되지 않은 열린 질문은
> 마지막 절에 따로 모았다 — 이 문서는 작업 착수 전의 합의 초안이며,
> 열린 질문이 닫히기 전에는 코드 작업을 시작하지 않는다.
>
> 구현: `docs/superpowers/plans/2026-07-19-status-input-redesign.md` 로 확정 (2026-07-19)

## 1. 현재 status_node 동작

### 입력
진입점 `main.py` 가 `build_graph().invoke({"question": "..."})` 로 호출한다.
이 시점 상태는 사실상 `{"question": str}` 하나뿐이다.

중요한 점: **status_node 는 `question` 을 판단에 쓰지 않는다.** seed 메시지에
문자열로 끼워 넣기만 하고, 분석 대상은 SQLite 에서 직접 찾는다.

### 동작 (3단계 + 3갈래 출구)
1. `yt.find_low_yield_lots()` — 평균 수율 임계(90) 미만 lot 을 낮은 순으로 전부 반환.
   각 lot 에 `worst_wafer`(수율 최저 1장) 서브쿼리를 첨부. `summary` 문자열 생성.
   - `if not lots` → **출구 A**: 빈 그룹으로 리포팅 조기 종료.
2. `yt.find_defect_group(lots[0]["lot_id"])` — 최악 lot 에서 `defect_type` 완전 일치로
   `target_group`(저수율 & 대표 불량 유형) / `control_group`(같은 lot 의 `none`) 을
   **코드가 결정론적으로** 판정.
   - `if not target_group` → **출구 B**: target 없이 control 만 담아 리포팅.
3. seed 메시지 생성 (SystemPrompt + 현황/그룹/질문) → **출구 C**: 분석 루프로 진입.

### 출력
`{messages, target_group, control_group, status_summary, findings}`.
`findings` 에는 `loop:0` 으로 `find_low_yield_lots`, `find_defect_group` 이 감사 기록된다.

## 2. 문제점 (심각도 순)

### A. 침묵 실패 — 틀렸는데 티가 안 나는 것

**1. `question` 이 대상 선정에 전혀 반영되지 않음**
- `question` 은 seed 메시지에 문자열로만 들어가고, 대상은 무조건
  `find_low_yield_lots()[0]`.
- 왜 문제인가: 자연어 입력을 받는 구조인데 입력을 무시한다. 다른 대상을 물어도
  **거부·경고 없이** 엉뚱한 대상을 분석하고 리포트는 그럴듯하게 나온다. 거부보다
  나쁜 "조용히 다른 답". 데모 질문에만 우연히 맞아떨어져 안 드러난다.

**2. 대조 그룹 선정이 target 과 비대칭**
- target: `yield < 90 AND defect_type='center_spot'` / control: `defect_type='none'`
  (**수율 조건 없음**).
- 왜 문제인가: 수율 89.9인 `none` wafer 가 정상 대조군에 들어간다. 대조군이 오염되면
  `compare_process_logs` 의 `suspect_equipment`(불량군 전원 통과 & 대조군 0명)가
  조용히 희석되어, 진짜 원인 장비가 suspect 에서 탈락할 수 있다. 더미 데이터는
  대조군 수율이 93~97이라 이 구멍이 안 드러난다.

**3. 출구 B(`target_group==[]`)가 "이상 없음"과 뭉개짐**
- 수율은 낮은데 저수율 wafer 가 전부 `none` 이면 여기로 빠진다.
- 왜 문제인가: 이건 "수율 이상은 실재하나 불량 맵 패턴으로는 안 잡힌다"는 중요한
  신호인데, `finalize_status` 없이 report 로 가고 fallback 문구가 (a)이상 없음
  (b)루프 한계 (c)그룹 못 묶음을 전부 "원인 미확정" 하나로 처리한다.
  (`docs/deferred-internal-integration.md` 8번에 기록됨)

### B. 설계 범위의 한계 — 의도인지 미처리인지 불분명한 것

**4. `lots[0]` — 최악 lot 1개만 분석**
- `find_low_yield_lots` 는 전부 반환하는데 분석은 1개만. 나머지는 배경 텍스트로만 언급.
- 왜 문제인가: (1) 여러 lot 동시 저수율은 공통 원인의 강한 신호인데 버려진다.
  (2) "평균 수율 최저"가 "분석 가치 최고"가 아니다 — 1장이 극단적으로 낮아 평균이
  깎인 lot 이, 전 wafer 가 균일하게 낮은(계통 원인 의심) lot 을 제친다.

**5. lot 경계 안에서만 대조군을 찾음**
- 왜 문제인가: lot 내 대조는 교란변수 통제에 유리하나, **lot 전체를 오염시킨 원인은
  구조적으로 못 잡는다.** 원인 장비가 lot 전체를 거쳤다면 대조군도 거쳤고
  suspect 에서 탈락 — 원인이 클수록 못 잡는 역설.
  (로드맵의 "재현성: 다른 lot·시간대 반복" 이 이 지점을 겨냥)

**6. 그룹 판정에 EDS(임베딩 유사도)를 안 씀**
- 그룹 기준은 `defect_type` 문자열 완전 일치. `search_similar` 는 루프 tool 로만 존재.
- 왜 문제인가: 결정론 원칙(임베딩 클러스터링 금지)은 이해되나, 프로젝트의 간판
  자산인 EDS 유사맵이 그룹 판정에 기여하지 않는다. 그리고 `defect_type` 라벨 품질에
  분석 전체가 종속된다 — 유사맵이 존재하는 이유가 "라벨 없이 패턴으로 묶기"일 텐데
  정작 그걸 안 쓴다.

### C. 결합 · 잔재 — 지금 안 아프지만 나중에 아플 것

**7. seed 메시지 문자열이 mock 의 파싱 계약**
- `ScriptedMockLLMClient._groups()` 가 `"불량 그룹 (...): ..."` /
  `"대조 그룹 (정상): ..."` 라인을 정규식으로 파싱.
- 왜 문제인가: `nodes.py` 와 `client.py` 가 문자열 포맷으로 결합. 프롬프트 문구를
  다듬는 순간 mock 이 조용히 깨진다. `control_group=[]` 이면 정규식 매칭 실패로
  ValueError (deferred 8번 마지막 — 현재 시드 데이터에선 도달 불가라 미룸).

**8. `worst_wafer` 는 죽은 코드**
- 단일-wafer 시절 `target_wafer = lots[0]["worst_wafer"]["wafer_id"]` 잔재.
  지금은 `_summarize_lots` 출력 문자열에만 남음.
- 왜 문제인가: 읽는 사람이 "worst_wafer 가 분석 대상인가?" 오해. `find_low_yield_lots`
  docstring 도 이미 사라진 "시나리오 2(그 wafer 로 유사 검색)" 를 여전히 언급.

**9. `find_low_yield_lots(threshold=config.YIELD_THRESHOLD)` — 기본 인자 import 시점 바인딩**
- 왜 문제인가: 런타임에 threshold 를 바꿔도 기본값에 반영 안 됨. 지금은 상수라
  안 아프나, threshold 를 입력에서 받거나 lot 별로 다르게 하려는 순간 터진다.
  (deferred 8번에 기록됨)

### 문제들의 공통 원인
**1·2·3번이 실질 문제이며, 공통점은 "더미 데이터가 너무 착해서 안 드러난다"** 는 것.
대조군 수율 93~97, defect 라벨 완벽, 저수율 lot 하나 — 시나리오가 구멍을 정확히
비껴간다. 지금은 문제가 있어도 pytest 가 전부 green 이라 손댈 근거가 없다.

## 3. 목적 재정의

### 원래 의도 (사용자 확인)
> 사용자가 따로 질문을 입력하지 않고 **분석 대상을 입력**(`root_lot + wafer`,
> 나중에는 시스템이 자동으로 분석 대상을 판단하는 추가 시스템 예정)하면,
> 그에 대한 **원인을 파악**하는 것.

### 이게 바꾸는 것
- **`question` 은 질문이 아니라 분석 대상 지정이다.** 지금 코드는 결함이라기보다
  인터페이스 자체가 목적과 어긋나 있다.
- 지금 status 가 하는 "저수율 lot 을 찾아 최악을 고르는" 일은 목적상 status 의 일이
  아니다. 그건 나중에 붙일 **자동 대상 판단 시스템**의 일이다. 그 자동 선정 로직이
  status 에 미리 들어앉아 있어서, 사용자가 대상을 줘도 무시하게 만든다.

### 대상 선정의 두 모드
- **수동 모드** (지금 만들 것): 사용자가 `root_lot + wafer` 를 준다 → 그걸 분석.
- **자동 모드** (나중): 시스템이 대상을 판단 → `find_low_yield_lots` 류가 여기서 산다.

→ status 는 **"대상은 이미 정해져서 들어온다"** 를 전제로 재구성되어야 하고,
대상을 고르는 일은 status 앞단으로 빠져야 한다.

### 입력 형태: 한 장 · 그룹 둘 다 지원
사용자가 주는 wafer 는 **한 장(불량 wafer 1개)** 또는 **불량 그룹 전체** 둘 다 가능.
다운스트림(`compare_process_logs`)은 항상 wafer 리스트 두 개(target/control)를
받으므로, 두 입력 형태를 한 형태로 맞추는 **정규화 계층**이 필요하다 (지금 없음).

### 대상 확정 2단계
- **1단계 — 대상 그룹 확정 (입력 형태에 따라 갈림)**
  - 그룹 입력 → 그대로 target_group. 묶기 끝.
  - 한 장 입력 → **형제 wafer 묶기** 필요. 여기가 핵심 갈림 (열린 질문 참조).
- **2단계 — 대조군 확정 (공통)**
  - target_group 이 정해지면 대응하는 정상 대조군을 코드가 고름. 입력 형태 무관 동일.
  - 문제 2·5번(대조군 오염/비대칭, lot 경계)이 여기서 그대로 남고 더 중요해진다.

### 문제 우선순위 변화
- **1번(질문 무시)**: "결함"이 아니라 **재설계 대상**. 입력 형식을
  `root_lot + wafer` 로 바꾸는 일.
- **4번(lot 1개만 분석)**: **소멸**. 대상을 사용자가 주니 lot 선택 불필요.
- **2·3번(대조군 오염/비대칭)**: **그대로 남고 더 중요.** 대상이 주어져도 대조군은
  여전히 코드가 골라야 함.
- **6번(EDS 미사용)**: 한 장 입력의 형제 묶기에서 EDS 가 제 역할을 할 후보로 재등장.

## 4. 작업 순서 (합의된 방향)

두 작업은 성격이 다르다:
- **구멍 드러내기** = 실행 문제. 할 일이 명확하고 오늘 바로 가능.
  `generate_dummy.py` 에 구멍을 드러내는 케이스를 심어 2·3·4번을 테스트에서
  빨갛게 만든 뒤 고친다.
- **질문 무시 / 입력 재설계** = 설계 결정 문제. 원칙 충돌(아래 열린 질문)을 먼저
  풀어야 코드를 쓸 수 있다.

두 작업은 겹친다: 저수율 lot 을 두 개 심으면 "특정 대상 지정 → 다른 대상 분석"이
테스트에서 바로 드러난다. 즉 **구멍 드러내기가 입력 재설계의 필요성까지 증명**한다.

권장 순서:
1. `generate_dummy.py` 에 구멍 케이스 추가 (대조군에 저수율 `none` 1장, 저수율 lot 2개,
   defect 라벨 없는 저수율 wafer 1장) → 2·3·4번이 실패 테스트로 가시화.
2. 아래 열린 질문 확정 → 입력 인터페이스 재설계(`question` → `root_lot + wafer`) 착수.

## 5. 열린 질문 (2026-07-18 저녁 논의 결과 — Q1·Q3 확정, Q2 보류)

- **Q1 확정: 2번 — EDS 유사맵으로 묶기.** 유사도 컷오프를 상수로 고정해
  결정론 원칙을 유지한다. 문제 6(간판 자산 EDS 미사용)도 함께 해소된다.
- **Q2 확정 (2026-07-18 추가 논의): 단계적 확장.** 수율 조건은 이미 반영(문제 2 수정).
  lot 경계는 필요할 때만 한 칸씩 — 상세 규칙은 7절.
- **Q3 확정: 앞단 분리 + 자리만 남김.** status 는 "대상은 정해져서 들어온다" 전제로
  재구성하고, find_low_yield_lots 류는 별도 대상-선정 모듈로 분리. 지금은 수동
  입력만 구현하되 자동 모드가 같은 인터페이스로 나중에 붙을 자리를 남긴다.

**Q1. 한 장 입력 시 형제 wafer 묶기 방식** — 아직 미확정.
사용자가 한 장을 지정했다는 건 "이 wafer 가 문제다"라는 판단이 이미 섰다는 뜻이므로,
형제 묶기의 목적은 "누가 문제인지 찾기"가 아니라 "이 문제의 **범위가 어디까지인지**
확인하기"에 가깝다. 후보:
1. `defect_type` 라벨로 묶기 — 결정론, 지금 방식 확장. 라벨 품질에 종속.
2. EDS 유사맵으로 묶기 — 유사맵의 본업("이 패턴과 닮은 애들 데려와"). 결정론 원칙과
   절충 필요(유사도 컷오프를 상수로 고정하면 결정론 유지 가능).
3. 형제 안 묶고 그 한 장만 vs 대조군 분석 — 묶기 자체를 스킵.

**Q2. 대조군 선정 규칙 재정의** — 문제 2·5번과 직결. 수율 조건을 넣을지, lot 경계를
넘을지. Q1 확정 후 함께 정리.

**Q3. 자동 대상 판단 시스템과의 경계** — `find_low_yield_lots` 류를 status 에서
떼어내 자동 모드 쪽으로 옮길 시점·형태. 지금은 수동 모드에 집중하되, 코드 구조상
자동 모드가 나중에 깔끔히 붙을 자리를 남겨둘지 결정.

## 6. 형제 묶기 세부 결정 (2026-07-18 추가 논의 — 확정)

1. **탐색 범위: 다른 lot 포함(전체 인덱스).** 형제가 다른 lot 에서 잡히는 것
   자체가 "같은 패턴이 다른 lot·시기에 재현된다"는 신호 (로드맵 재현성 항목,
   문제 5 완화). `search_similar` 는 원래 전체 인덱스 탐색이라 구현 부담 없음.
   - 파생 이슈 (다음 논의에서 확정): target 이 여러 lot 에 걸칠 때 대조군 규칙.
     제안 = **형제 각자의 lot 에서 대조군을 뽑아 합집합** — lot 내 대조 원칙을
     wafer 단위로 유지, Q2 를 미리 결정하지 않는다.
2. **컷오프는 튜닝 가능하게.** `config.SIBLING_MIN_SIMILARITY` 기본값 상수
   + `.env` 오버라이드 (LLM 설정과 같은 방식). 실행 중 흔들리지 않으면
   결정론 원칙과 충돌 없음. 유사 사례 검색용 `EDS_MIN_SIMILARITY`(0.5)와는
   용도가 달라 별도 상수 (형제 묶기는 "같은 사건" 판정이라 더 높게 시작).
3. **defect 라벨은 판정 기준에서 제외, 참고 정보로 강등.** 묶기는 불량 맵
   패턴(원본 신호) 기준. 유사맵과 라벨이 충돌하면 유사맵이 이기고,
   라벨 불일치는 리포트에 참고로만 남긴다.
4. **형제가 안 잡히면 "추후 분석 필요".** 엔지니어도 분석 불가능한 케이스 —
   `finalize_status` 에 `isolated`(고립 패턴, 자동 분석 범위 밖) 추가,
   출구 A/B 구분과 같은 메커니즘으로 리포트까지 전달.

## 7. Q2 확정: 대조군 규칙 — 단계적 확장 (2026-07-18 추가 논의)

전제: Q1 의 전-lot 형제 탐색이 문제 5 를 절반 해소한다 — 형제가 여러 lot 에서
잡히면 대조군도 (아래 1단계만으로) 자연히 여러 lot 이 되어, lot 전원이 공유한
원인 장비도 다른 lot 대조군의 control_count=0 으로 잡을 수 있다. Q2 의 본체는
형제가 전부 같은 lot 인 잔여 케이스다.

- **1단계 (기본): 형제 각자의 lot 내 합집합.** 각 형제의 lot 에서
  defect 'none' + 수율 임계 이상 wafer 를 뽑아 합친다. lot 내 대조 원칙을
  wafer 단위로 유지 — 교란변수 통제가 가장 좋다.
- **2단계 (1단계 부족 시): 같은 root_lot 의 다른 분할 lot 으로 확장.**
  같은 웨이퍼 출발이라 교란이 가장 적은 확장. 단 평가랏은 의도적 조건 변경이라
  오염원 — **양산랏끼리만**. lot_type 컬럼(ETL 이후)이 전제이므로 규칙만 확정,
  활성화는 사내 연동 후.
- **3단계 (그래도 부족): 확장하지 않고 정직 보고.** "대조군 부족 — lot 내 대조
  한계, 추후 분석 필요" 를 별도 finalize_status 로 리포트까지 전달.
  전-DB 무관 매칭(시기·제품 교란 통제 규칙)은 실데이터 보고 필요해지면 그때 설계.
- **리포트에 대조군 출처(어느 lot, 몇 단계 확장) 를 항상 명시**한다.
- "부족" 의 기준(최소 대조군 크기 상수)은 구현 시 결정, 튜닝 가능하게 둔다.
