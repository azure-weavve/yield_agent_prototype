## 1. score 계산식 — 확인된 사실

후보 키 하나(`(level, step_seq, key)`, 예: `(chamber, CC002000, ETCH9_B)`)마다
2×2 분할표를 만든다.

| | 그 키를 거침 | 안 거침 |
|---|---|---|
| 타깃 | a | b |
| 대조군 | c | d |

```
coverage_target  = a / (a + b)
coverage_control = c / (c + d)
score            = coverage_target - coverage_control     # 범위 -1 ~ 1
```

**층화 후 합산(pooling).** 타깃이 여러 root_lot 에 걸치면(EDS 확장 모드 B)
root_lot 하나 = stratum 하나로 쪼개 각각 a/b/c/d 를 세고, **카운트를 더한 뒤
마지막에 한 번 나눈다.** 층별 score 를 평균하지 않는다.

> 예: A층 8/8 vs 0/8, B층 1/1 vs 1/2
> - 카운트 합산 → 9/9 − 1/10 = **0.9** (현재 방식)
> - score 평균 → (1.0 + 0.5)/2 = 0.75
>
> 표본 크기에 비례해 가중되는 셈. 웨이퍼 1장짜리 층이 8장짜리와 동등한 발언권을
> 갖지 않는다.

**분모에서 빠지는 것들**

- 이력이 없는 wafer → `missing_history` 로 분리
- legend 컬럼이 하나라도 NULL 이면 그 레벨 후보를 안 만듦 (가짜 키 금지)
- 타깃·대조군 중복 wafer 는 타깃으로만 계산
- `nt_tot == 0` 또는 `nc_tot == 0` 후보는 버림

**필터·정렬**

- `score <= MIN_SCORE` 는 반환하지 않음
- 정렬 `(-score, -coverage_target, -target_pass, step_seq, key)` → `top_k` 절단

**판정은 여기서 안 한다.** `passes` 는 `domain/engine.py` 의 `_passes()`:

```
passes = (status == "ok")
         AND score >= COMMONALITY_PASS_MIN_SCORE
         AND target_pass >= COMMONALITY_PASS_MIN_TARGET
```

`target_pass` 하한이 따로 있는 이유 — score 1.0 은 2/2 에서도 40/40 에서도 나온다.
score 만으로는 표본 크기를 구분할 수 없다.

## 2. root_lot 층화가 실제로 통제하는 범위

### 2-1. 설계 문서 B-3 의 문구가 과장이다

문서에 "root_lot 층화로 route·시간 교락이 구조적으로 제거됨" 이라고 적혀 있는데,
**"제거" 가 아니라 "일부만 좁혀짐"** 이다. 세 가지를 구분해야 한다.

| | 뜻 | commonality 에서의 지위 |
|---|---|---|
| route **정의**(flow) | 이 제품이 원래 어떤 step 을 거치게 되어 있나 | 교락 — 통제 대상 |
| route **실현**(path) | 각 step 을 실제로 어느 eqp/ch/ppid 가 처리했나 | **측정 대상(신호)** |
| 재처리로 삽입된 step | 불량이라서 추가로 거친 step | 역인과 — 통제 안 됨 |

root_lot 층화가 잡는 것은 **첫 번째뿐이다.** 같은 root_lot 이면 제품·기술노드·flow
정의가 같으므로 "타깃은 ETCH9, 대조군은 ETCH8" 이 제품 차이 때문일 가능성은
배제된다. 그 이상은 아니다.

**split 은 교락이 아니라 신호다.** 같은 root_lot 안에서 split 되어 lot_id 가 갈리고
eqp 경로가 달라지는 것 — 이게 바로 commonality 가 찾으려는 대상이다. 제거하면
도구가 할 일이 없어진다.

### 2-2. 시간도 느슨하다

root_lot 하나가 fab 에 머무는 기간은 짧지 않다. split 된 자식 lot 이 며칠~몇 주
간격으로 처리될 수 있고 그 사이에 PM·셋업 변경·PPID 개정이 들어간다. **"타깃은 PM 전,
대조군은 PM 후" 가 root_lot 안에서도 성립한다.**

`meta` 에 두 그룹의 처리 시각 범위를 싣는 것은 **통제가 아니라 진단 재료로 넘긴
것**이다. 설계 문서 자체도 이 부분은 "시간 교락 진단 재료" 라고 쓰고 있어 B-3 문구와
서로 안 맞는다.

### 2-3. 진짜 위험한 자리

- **split 기준이 결과와 상관될 때.** 계측 결과를 보고 나눴거나 일정·우선순위(hot lot)로
  나눴다면, "타깃만 거친 챔버" 는 그 챔버가 원인이라서가 아니라 **그 챔버로 보내진
  이유가 이미 불량과 얽혀 있어서** 나온다. 층화는 이걸 전혀 건드리지 못한다.
- **재처리 역인과.** 불량이라서 재작업을 탄 wafer 는 추가 step·설비 이력이 생긴다.
  결과가 원인 쪽 카운트를 만든다. 실데이터에 재처리 이력 240만 건이 확인된 상태라
  가설이 아니라 실재하는 조건이다.

### 2-4. 분모 conflation — **미확인, 확인 필요**

`_count_stratum` 이 세는 `seen` 이 **이력 행이 하나라도 있는 wafer** 로 보인다.
그렇다면 후보 `(CC002000, ETCH9_B)` 의 `target_total` 에 CC002000 을 아예 안 지난
wafer 도 들어간다. 즉 `b`(안 거침)가 두 가지를 합친다.

- 그 step 을 거쳤지만 **다른 챔버**를 썼다
- 그 step 을 **아예 안 지났다**

경로가 같은 wafer 끼리면 후자가 0 이라 문제없지만, split 으로 step 집합이 갈리면
섞여 들어온다. 그러면 score 가 챔버 분리도가 아니라 **step 통과 여부**를 반영한다.

> **확인 방법**: `tools/commonality.py` 의 `_count_stratum` 에서 `seen` 을 어떻게
> 집계하는지 본다. `WHERE step_seq = ?` 로 좁혀 세는지, 전체 이력에서 wafer 집합만
> 뽑는지.

## 3. 이름과 구현의 불일치 — commonality vs contrast

### 3-1. 좁은 의미의 commonality 는 타깃만 본다

엔지니어가 하는 commonality 는 불량 wafer 들의 EQP_CH path 를 늘어놓고 교집합·
집중도를 보는 것이다. 출력은 "불량 10장 중 8장이 ETCH9_B 를 지났다" 한 줄이고,
그게 의미 있는지(전 wafer 가 다 지나는 자리인지)는 사람이 도메인 지식으로 판단한다.

현재 구현은 타깃 통과율에서 대조군 통과율을 빼므로 **이미 2군 비교(contrast)** 다.
`find_commonality` 라는 이름과 `coverage_target - coverage_control` 이라는 식이
서로 다른 방법을 가리킨다.

### 3-2. 대조군이 강제된 구조적 이유

**현재 score 계산에는 yield 도 계측값도 안 들어간다.** 후보 키마다 묻는 건 "이 wafer 가
여길 지났나" 뿐이고, 결과 변수는 이미 **타깃/대조군이라는 그룹 소속에 접혀 있다.**
불량이라는 사실이 y 축에 값으로 남아 있지 않고 "타깃 집합의 원소다" 라는 라벨로
소비된다.

결과를 측정하지 않고 그룹 정의에 숨기면 비교 대상 없이는 아무것도 말할 수 없다.
그래서 대조군이 필수가 된다.

### 3-3. 대조군 기반 설계의 대가

- **`score <= MIN_SCORE` 후보는 아예 안 나온다.** target-only 관점에서 엔지니어가
  제일 먼저 보는 "타깃 전원이 지난 자리" 는 대조군도 전원 지났으면 score 0 이라
  조용히 사라진다. 사람이 보고 기각할 행들을 도구가 미리 지운다.
- **`no_signal` 은 이 설계가 만든 맹점이다.** 원인이 root_lot 전체에 걸리면 score 가
  전부 0 이 된다. target-only 였다면 통과율 100% 짜리 키가 목록 맨 위에 떴을 것이다.
  원래 있던 한계가 아니라 대조군을 lot 내부로 잡아서 생긴 것.

## 4. 엔지니어의 metro 분석과의 괴리

엔지니어는 x=시간, y=계측값, legend=확인 항목(PPID 등)으로 그려 **특정 수준이
나머지와 다른지**를 본다. 이 방식은 대조군이 필요 없다 — 계측값이 y 축에 살아
있으므로 PPID_A vs B vs C 를 서로 비교하면 되고, 어느 쪽이 "타깃" 인지 미리 정할
필요가 없다.

| | 엔지니어의 metro 분석 | 현재 구현 |
|---|---|---|
| 결과 변수 | 계측값 (연속) | 없음 — 그룹 소속으로 대체 |
| 그룹핑 | legend 수준끼리 (A vs B vs C) | 타깃 vs 대조군 |
| 비교 내용 | 값 분포 차이 | 통과 여부 비율 차이 |
| 시간축 | x 축 — drift·step change 가 보임 | 없음 (`meta` 에 범위만) |
| legend 의 뜻 | 색으로 나눌 항목 | 키를 만들 컬럼 |

**`legend` 라는 단어만 빌려왔고 하는 일은 다르다.** 엔지니어는 legend 수준끼리
비교하는데, 구현은 legend 로 키를 만들어 타깃/대조군을 비교한다.

Stage 2 의 `compare_sensor_distribution` 이 y 축을 되살리지만(Cohen's d), 거기서도
그룹핑은 여전히 타깃/대조군이지 PPID 수준끼리가 아니다. **"PPID_X 만 다른 PPID 들과
다르다" 는 형태는 지금 어느 도구로도 안 나온다.**

## 5. 통계적 불확실성이 정량화되지 않는다

2군 비교로 넘어갔으면 표본 변동을 다뤄야 하는데 현재 방어는
`target_pass >= COMMONALITY_PASS_MIN_TARGET` 하나뿐이다. 2 vs 2 의 score 1.0 과
20 vs 40 의 score 1.0 이 같은 값으로 나란히 정렬된다.

p-value 를 뺀 것 자체는 근거가 있다 — 후보 키가 수백 개라 α=0.05 면 우연히 수십 개가
유의해진다. 다만 **p-value 를 안 쓰는 것과 불확실성을 아예 정량화하지 않는 것은 다른
문제**인데 지금은 후자다.

검토된 흔적이 문서에 없는 선택지: Fisher exact + FDR, 차이의 신뢰구간,
permutation null.

## 6. 수정 범위 산정

### 병목은 도구 파일이 아니라 게이트 계약이다

`graph/nodes.py` 의 `_finalize_gate` 승인 조건:

```
claim.passes  AND  claim.score >= bundle.top_score(claim.tool)  AND  conf >= 임계
```

**`claim_id` / `passes` / `score` 를 못 내는 도구는 근거가 될 수 없다.** 새 방법이 이
셋을 그대로 내면 파일 두어 개로 끝나고, 못 내면 게이트·Claim·리포트까지 딸려 온다.

### A. target-only 경로 나열 — 2파일 + 테스트

새 도구 모듈 + `tools/agent_tools.py` 등록. 타깃 wafer 의 `step_history` 를 읽어
`(step_seq, eqp_id, ch_id)` 별 통과 수를 세서 정렬해 돌려주는 것뿐.

**함정**: target-only 는 구조적으로 `score` 가 없다(비교 대상이 없으니 순위 축이
안 나온다). 그래서 게이트가 쓸 claim 을 못 만든다. 선택이 갈린다.

- **탐색용으로만 둔다** → 정말 2파일.
  ⚠️ **이름에 `hyp_` 접두를 붙이면 안 된다.** 게이트가 `TOOLS_BY_NAME` 에서 `hyp_`
  접두를 긁어 "등록 가설 전부 돌았나" 를 판정하는데, 통과 후보를 못 내는 도구가 그
  집합에 들어가면 `unrun` 이 안 비어 `no_signal` 판정 경로가 막힌다.
- **결론 근거로 쓴다** → 게이트 계약 변경. B 와 비슷한 규모.

### B. metro legend 수준 비교 — 전반 수정 (6~8파일)

후보(candidate)의 **정의**를 바꾸는 일이라 번진다. 세 계약이 동시에 깨진다.

| 계약 | 현재 | metro 방식 | 파일 |
|---|---|---|---|
| 함수 시그니처 | `evaluate(spec, group_ids, control_ids)` — 2군 전제 | 군이 legend 수준 개수만큼 | `domain/engine.py`, `domain/registry.py` |
| Claim 모양 | 2×2 카운트 | 분포 통계(수준별 n·평균·산포·효과크기) | `domain/evidence.py` |
| `top_score` 의미 | 같은 도구 내 최고 분리 점수 | "가장 튀는 수준" — 척도가 다름 | `graph/nodes.py` |

여기에 `domain/hypotheses.yaml`(legend 스키마의 뜻이 바뀜)과 리포트 출력이 따라온다.
`nodes.py` 와 `evidence.py` 는 시스템 중심이라 회귀 범위가 넓다.

**B 의 선행 조건**: metro 계측값이 지금 DB 에 없다. `load_internal.py` 가 적재하는 건
`yield` 와 `step_history` 둘뿐이고, 도메인 정리 B-2 는 "FDC 를 주 기질, metro 는 있을
때만 보강" 으로 정리했다. 계측값 소스 확보가 도구 설계보다 앞선다
(→ `load_internal.py` 수정 범위 포함, 승인 필요).

## 8. 판단 보류 항목

이 문서는 **문제를 정리했을 뿐 방향을 정하지 않았다.** 아래는 결정이 필요한 자리다.

1. target-only 를 되살릴 것인가 — 되살린다면 탐색용인가 근거용인가
2. 결과 변수를 계측값으로 되살릴 것인가 — 되살린다면 타깃/대조군 축을 유지한 채
   얹을 것인가, legend 수준 비교로 바꿀 것인가
