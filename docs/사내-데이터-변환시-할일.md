  공정명은 원천의 `area` 컬럼. `step_history.area` 는 **NULL 허용**이라 안 실어도

- [ ] EDS `/search` 응답의 wafer 식별자도 `{root_lot}_{no}` 체계인지 확인
  (다르면 `HttpEDSSearcher` 매핑에서 조립).
- [ ] 적재 후 정합성 검사: `load_internal.validate()` 리포트에 fatal 없음 확인

      `find_low_yield_lots`
  직접 호출로 상식 검증.
- [ ] **`ppid 결측률` 과 `[grain]` 줄을 눈으로 확인** (fatal 이 아니라 warn 이므로 위
  항목만 보면 놓친다). 결측률 `1.0` 이면 ppid 가 안 실린 것이고,
  `[grain] ... 0/N군` 이면 **lot/recipe 마스터 단위 조인 의심**이다 — 둘 다
  `hyp_ppid_commonality` 가 **에러 없이 틀린 답**을 내는 상태다.
  `N`(판정 대상) 은 **설비·챔버가 wafer 마다 갈리는 lot×스텝 군**만 센다. `N` 이 0 이면
  판정 불가 — 스텝마다 단일 장비만 쓰는 공정이면 이 검사는 원리상 침묵한다.
  경고가 떠도 확정은 아니다(한 lot 을 여러 챔버에 같은 레시피로 돌리는 것도 정상):
  ppid 몇 건을 원천과 직접 대조해 grain 을 확인할 것.
- [ ] **`varying` 이 `checkable` 대비 극히 작으면(예: `3/2000`) 의심할 것** — 경고는
  `varying` 이 정확히 0 일 때만 뜨므로, **일부 스텝만** 마스터 조인된 부분 오염은
  경고 없이 지나간다. 정상 스텝들이 반례를 공급해 전역 조건을 만족시켜 버리기 때문이다.
  비율이 유일한 단서다. (코드에 임계값은 두지 않았다 — 보정할 실분포가 아직 없어서
  임의 수치가 판정에 들어가는 것을 피했다.)

## 4. mock → openai 전환의 함의

- `ScriptedMockLLMClient` 는 더미 시나리오(finalize(0.6) → hyp_eqp_ch_commonality →
  compare_sensor_distribution → finalize(0.9))를 **하드코딩한 스크립트**.
  실데이터에선 동작하지 않으므로 **반드시 `LLM_MODE=openai` 필요**.
  (Stage 4 에서 라벨 기반 `aggregate_defects` 가 삭제되어 각본이 재작성됐다.)
- 실제 LLM 은 mock 처럼 얌전하지 않다 — 엉뚱한 tool 이름·비숫자 confidence 를 낼 수 있음.
  이때 비로소 §0 의 tool 오류 복구·confidence 방어(이미 구현됨)가 실효를 발휘한다.
  한 메시지에 tool_call 을 여러 개 내는 것도 실제 LLM 에서만 생기는데, 그 경로는
  미룸 5번(2026-07-29 완료)이 막았다.
- 그 밖의 실패 경로 테스트 확충(미룸 7번)이 이 단계에서 함께.
