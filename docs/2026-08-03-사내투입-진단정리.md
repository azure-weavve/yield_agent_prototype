## 1. 처리 완료 — 모듈 이름 그림자 + 스크립트 실행 경로

### 증상

```
python -X utf8 data/load_internal.py
→ ModuleNotFoundError: No module named 'console'
```

### 원인 (두 겹)

1. **스크립트 경로 실행 시 저장소 루트가 `sys.path` 에서 빠진다.**
   `python data/load_internal.py` 는 `sys.path[0]` 에 `data/` 를 넣고 CWD 는 넣지 않는다.
   `main.py` · `data/generate_dummy.py` 는 `sys.path.insert` 를 직접 하고 있었으나
   `data/load_internal.py` 만 빠져 있었다.

2. **site-packages 에 `config` 라는 최상위 이름의 무관한 패키지가 깔려 있었다.**
   그래서 `import config` 가 실패하지 않고 **엉뚱한 패키지를 집었고**, 다음 줄
   `from console import say` 에서야 죽었다. 에러 메시지가 `config` 가 아니라
   `console` 을 가리킨 이유가 이것이다.
   → 조용히 틀리는 실패였다. `pip install console` 까지 되어 있었다면 두 import 가
   모두 "성공" 하고 `config.DB_PATH` 단계에서 엉뚱한 값으로 갔을 것이다.

### 조치 (완료)

- `config.py` → **`ya_config.py`**, `console.py` → **`ya_console.py`** 로 개명.
  연관 import 전부 수정 완료. 최상위 이름이 흔하지 않게 되어 그림자 위험 제거.
- `data/load_internal.py` 상단에 경로 방어 추가 (`ya_config` import **보다 위**):

  ```python
  from __future__ import annotations

  import argparse, os, re, sqlite3, sys
  from pathlib import Path

  # 스크립트 경로 실행 시 sys.path[0] 은 data/ 다 — 저장소 루트가 빠진다.
  sys.path.insert(0, str(Path(__file__).resolve().parent.parent))

  import ya_config as config          # noqa: E402
  from ya_console import say as _say  # noqa: E402
  ```

- 세 실행 형태 모두 정상 동작 확인.

문서 수정이 아직이다. 코드는 고쳤지만 점검표 명령이 옛 상태다.

### 2-2. wafer×스텝 중복 240만건 — **확인 완료, 정상**

적재 시 뜬 경고:

```

```

최다 중복 사례를 열어 보니 `eqp_id` · `ppid` · `timestamp` 가 모두 갈린다.
조인 중복(카티전)이면 오른쪽 테이블 행이 곱해질 뿐이라 **설비가 바뀔 이유가 없다.**
따라서 실제 재처리 이력이다.

**판정: 경고 닫음.** 점검표 기록 양식의 `warn:` 칸에 남길 문구 ↓

```
wafer×스텝 중복 이력 2,422,713건 (전체 28M 중 8.6%)
→ 확인 완료: eqp_id·ppid·timestamp 가 갈리는 실제 재처리 이력. 조인 중복 아님.
→ 미결: 전컬럼 완전 동일 행 약 16만건 (0.6%). 별도 확인 예정.
```

### 2-3. 전컬럼 완전 동일 행 16만건 — **미해결 (조사 보류)**

재작업으로 설명되지 않는다. 같은 설비·같은 PPID·같은 timestamp 로 두 번 실린 행.
원천 추출 쿼리가 행을 복제할 가능성이 있다.

**현재 결과에 미치는 영향은 없다** — `commonality` 는 wafer 를 집합(set)으로 세므로

## 3. 발견된 설계 결함

### 3-1. `[grain]` (ppid 조인 단위) 검사가 구조적으로 침묵한다 — **재설계 필요**

**현재 로직**: "설비·챔버는 갈리는데 `ppid` 는 안 갈리는" 군을 lot 단위 조인의
증거로 보고, `varying == 0` 일 때만 경고를 띄운다.

**문제**: 그 패턴은 **정상 공정에서 압도적 다수**다.

> 매엽식 설비는 wafer 가 한 장씩 들어간다. 챔버가 5개면 같은 lot 의 wafer 가
> 1번은 A, 2번은 B, 3번은 C 챔버로 분산 투입되고, **PPID 는 당연히 같다.**

따라서 이 검사는 정상과 비정상을 구분하지 못한다.

- 조인이 제대로 됐어도 → `varying` 비율 낮음
- 조인이 lot 단위로 틀렸어도 → `varying` 비율 낮음

게다가 실데이터 규모에서는 재작업·스텝별 레시피 차이 때문에 `varying` 이 우연히
0을 벗어나 **경고 자체가 안 뜬다.** 이번에도 6,000건이 그렇게 경고를 껐다.

**추가로 위험한 점**: 이 지표가 사람에게 잘못된 의심을 유도한다.
실제로 이번 세션에서 `6,000 / 1,300,000` (0.46%) 이라는 비율을 보고 "99.5%가
그렇다면 조인 문제" 라는 **틀린 판단**이 나왔다. 도메인상 그게 다수인 게 정상이다.

**도메인 사실 (재설계의 근거)**:

> `ppid` 는 **root_lot 단위로는 갈리고 lot 단위로는 안 갈린다.**
> 동일 root_lot 에서 PPID 를 테스트하기 위해 나누는 경우가 있기 때문이다.

→ 그러므로 **층화 기준을 무엇으로 잡느냐가 판정을 좌우한다.**
현재 `validate()` 가 `root_lot_id` 로 묶는지 `lot_id` 로 묶는지 먼저 확인해야 한다.
`lot_id` 로 묶어야 "갈리면 이상" 이 성립한다.

**선택지**: 판정 로직 교체 / 검사 삭제 / 유지 후 문구만 완화.
현재는 노이즈에 가까우므로 최소한 지금 형태로 두면 안 된다.

**주의**: `hyp_ppid_commonality` 가 이 컬럼 위에서 돈다. 조인 단위가 틀리면
**에러 없이 틀린 집계**가 나온다. 결측률 0.0 이라 초록불인데 답이 틀리는 상태다.
이 검사가 정리되기 전까지 2단 PPID 가설 결과는 신뢰하지 않는다.

### 3-2. `area` 는 적재만 되고 아무도 읽지 않는다

`area` 컬럼 자체는 적재 경로 전부에 정상적으로 존재한다 (DDL · `_normalize()` ·
INSERT · `validate()` 의 `area_null_rate` · 왕복 회귀 테스트).

그런데 **읽는 코드가 없다.**

- `tools/commonality.py` 의 `_history()` 가 SELECT 하는 건
  `wafer_id, step_seq, timestamp` + legend 컬럼뿐. `area` 는 어느 legend 에도 없다.
- `claim_id` 는 `eqp_ch_commonality:chamber:CC002000:ETCH9_B` 형태이고,
  `evidence.format_evidence_line()` 도 `area` 를 싣지 않는다.

→ 점검표의 "`area` 가 없으면 리포트를 사람이 못 읽는다" 는 서술이 **방향이 뒤집혀
있다.** 정확히는 "**`area` 를 실어도 지금은 리포트에 안 나온다**" 다.
결측률 0.0 을 확인하고 리포트를 열면 여전히 `CC002000` 만 보인다.

**선택지**:
1. `_history()` SELECT 에 `area` 추가 → 후보 dict → `format_evidence_line` 까지 전달
2. 지금은 두고 점검표 문구만 "적재는 되지만 리포트 표기는 미구현" 으로 정정

### 3-3. 재작업이 commonality 카운트에 미치는 영향 — **기록만**

한 wafer 가 같은 스텝을 두 설비에서 거치면 `_count_stratum()` 이 **양쪽 다
"거쳤다" 로 카운트**한다.

- 재작업 wafer 는 후보 키를 여러 개 갖게 되어 후보 수가 늘어난다 (top-k 경쟁 심화)
- 재작업 자체가 원인일 때는 오히려 유리하고, 아닐 때는 노이즈 후보가 된다

8.6% 규모라 무시할 수준은 아니다. 다만 실제 문제인지는 `engine.evaluate` 결과에
재작업 흔적이 섞여 나오는지를 봐야 판단할 수 있다.

## 5. 조사용 스크립트 — 완전 동일 행 16만건

착수할 때 쓸 것. 저장소 루트에 임시 파일로 두고 끝나면 삭제.

```python
# check_exact_dup.py
import sqlite3
import time

import ya_config as config

conn = sqlite3.connect(config.DB_PATH)
conn.row_factory = sqlite3.Row
q = lambda s, *a: conn.execute(s, a).fetchall()
one = lambda s, *a: conn.execute(s, a).fetchone()[0]

COLS = "wafer_id, step_seq, area, eqp_id, ch_id, ppid, timestamp"
t0 = time.time()


def tick(msg):
    print(f"[{time.time() - t0:6.1f}s] {msg}", flush=True)


# ── 1. 중복 그룹만 임시 테이블로 (이후 질의는 전부 여기에) ──────────────
tick("중복 그룹 추출 중... (전수 스캔, 수 분 소요)")
conn.execute(f"""
    CREATE TEMP TABLE dup AS
    SELECT {COLS}, COUNT(*) AS n
    FROM step_history
    GROUP BY {COLS}
    HAVING COUNT(*) > 1
""")
conn.execute("CREATE INDEX tmp_dup_ws ON dup(wafer_id, step_seq)")

n_group = one("SELECT COUNT(*) FROM dup")
n_excess = one("SELECT SUM(n - 1) FROM dup") or 0
n_total = one("SELECT COUNT(*) FROM step_history")
tick(f"완전 동일 그룹 {n_group:,}개 · 초과 행 {n_excess:,}건 "
     f"(전체 {n_total:,}행의 {n_excess / n_total:.2%})")

if n_group == 0:
    raise SystemExit("완전 동일 행 없음")

# ── 2. 배수 분포 — 2회에 몰리는지, 꼬리가 긴지 ─────────────────────────
print("\n-- 반복 배수 분포 --")
for r in q("SELECT n, COUNT(*) c FROM dup GROUP BY n ORDER BY n LIMIT 20"):
    print(f"  {r['n']:3d}회 반복: {r['c']:>10,}그룹")
print(f"  최대 반복: {one('SELECT MAX(n) FROM dup')}회")

# ── 3. 어디에 몰려 있나 — 특정 스텝/설비/공정에 집중되면 원인이 좁아진다 ─
for col in ("step_seq", "area", "eqp_id"):
    print(f"\n-- {col} 상위 10 (초과 행 기준) --")
    for r in q(f"""SELECT {col} k, SUM(n - 1) x, COUNT(*) g
                   FROM dup GROUP BY 1 ORDER BY x DESC LIMIT 10"""):
        print(f"  {str(r['k']):<20} 초과 {r['x']:>9,}건 / {r['g']:>8,}그룹")
    n_dup_vals = one(f"SELECT COUNT(DISTINCT {col}) FROM dup")
    n_all_vals = one(f"SELECT COUNT(DISTINCT {col}) FROM step_history")
    print(f"  ({col} 고유값: {n_dup_vals:,} / 전체 {n_all_vals:,})")

# ── 4. root_lot 집중도 — 특정 lot 만이면 추출 범위 문제 ────────────────
print("\n-- root_lot 상위 10 --")
for r in q("""SELECT y.root_lot_id k, SUM(d.n - 1) x, COUNT(DISTINCT d.wafer_id) w
              FROM dup d JOIN yield y ON y.wafer_id = d.wafer_id
              GROUP BY 1 ORDER BY x DESC LIMIT 10"""):
    print(f"  {r['k']:<15} 초과 {r['x']:>9,}건 / wafer {r['w']:>5,}장")

affected = one("""SELECT COUNT(DISTINCT y.root_lot_id) FROM dup d
                  JOIN yield y ON y.wafer_id = d.wafer_id""")
total_lots = one("SELECT COUNT(DISTINCT root_lot_id) FROM yield")
print(f"  (영향 root_lot: {affected:,} / 전체 {total_lots:,})")

# ── 5. timestamp 성질 — 해상도가 뭉개지면 '동일'이 쉽게 성립한다 ────────
print("\n-- timestamp --")
print(f"  NULL 그룹: {one('SELECT COUNT(*) FROM dup WHERE timestamp IS NULL'):,}"
      f" / {n_group:,}")
print("  값 예시:", [r["timestamp"] for r in
                   q("SELECT DISTINCT timestamp FROM dup "
                     "WHERE timestamp IS NOT NULL LIMIT 5")])

# ── 6. 재작업 이력과 같은 자리에서 나는가 ──────────────────────────────
# "겹친다" = 행이 겹치는 게 아니라, 같은 (wafer_id, step_seq) 자리에서
#            완전동일 복제와 재처리 이력이 함께 나타나는가.
print("\n-- 재작업 이력과 겹치는가 --")
conn.execute("""
    CREATE TEMP TABLE reproc AS
    SELECT wafer_id, step_seq
    FROM step_history
    GROUP BY wafer_id, step_seq
    HAVING COUNT(DISTINCT eqp_id || '|' || COALESCE(ppid, '')) > 1
""")
conn.execute("CREATE INDEX tmp_reproc_ws ON reproc(wafer_id, step_seq)")

pairs = one("SELECT COUNT(*) FROM (SELECT 1 FROM dup GROUP BY wafer_id, step_seq)")
overlap = one("""SELECT COUNT(*) FROM
    (SELECT DISTINCT wafer_id, step_seq FROM dup) d
    JOIN reproc r ON r.wafer_id = d.wafer_id AND r.step_seq = d.step_seq""")
print(f"  완전동일을 가진 (wafer,step) 쌍: {pairs:,}")
print(f"  그중 재처리(설비·PPID 갈림)도 있는 쌍: {overlap:,}")

# ── 7. 실제 행 샘플 ───────────────────────────────────────────────────
print("\n-- 최다 반복 사례의 원본 행 --")
top = q("SELECT * FROM dup ORDER BY n DESC LIMIT 1")[0]
print("  그룹:", {k: top[k] for k in top.keys()})
print("  같은 wafer·step 의 전체 이력:")
for r in q("""SELECT * FROM step_history WHERE wafer_id = ? AND step_seq = ?
              ORDER BY timestamp""", top["wafer_id"], top["step_seq"])[:12]:
    print("   ", dict(r))

tick("완료")
```

### 판독 기준

| 관찰 | 해석 |
|---|---|
| 특정 `step_seq` · `eqp_id` 몇 개에 집중 | 그 설비/스텝 이력이 원천에서 이중 기록되는 구조. 범위가 좁아 원천 담당자에게 문의하기 쉽다 |
| 전 스텝에 고르게 퍼지고 배수 대부분 2회 | 추출 쿼리가 행을 두 번 집는 모양. `_extract()` 문제 |
| 6번에서 대부분 겹침 | 재작업 이력을 끌어오는 조인이 행을 한 번 더 집는 것. 원인 하나 |
| 6번에서 거의 안 겹침 | 재작업과 무관한 별개 현상 |
| `timestamp` 가 날짜까지만 / 분 단위로 뭉개짐 | 중복이 아니라 **해상도 문제**. 실제로는 다른 시점의 처리 |

## 6. 환경 메모

- 로컬 검증 환경은 **Windows + Windows PowerShell 5.1**.
  `&&` 는 PowerShell 7 부터 지원 → 5.1 에서는 `;` 또는 `Push-Location` / `Pop-Location`.
- 파이썬은 **3.11 이하**로 추정. f-string 표현식 안에 따옴표 중첩(삼중 따옴표,
  중첩 f-string)이 `SyntaxError` 를 낸다. 쿼리는 f-string 밖으로 뺄 것.
- cp949 콘솔이라 실행 시 `-X utf8` 을 계속 붙인다.
- 그림자 확인용 (둘 다 `ModuleNotFoundError` 가 나와야 **정상**):

  ```powershell
  Push-Location data
  python -X utf8 -c "import ya_config; print(ya_config.__file__)"
  Pop-Location
  ```
