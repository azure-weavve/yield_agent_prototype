## 0. 왜 필요한가

수율 분석 에이전트가 지금까지 **더미 데이터로만** 검증됐다. 테스트가 전부 통과해도 실제
공정에서 원인을 찾는지는 확인된 적이 없다. **원인이 이미 밝혀진 과거 이슈 3~5건**을 받아서,
에이전트가 엔지니어가 도달한 답에 도달하는지 본다.

이 첫 검증은 사내 LLM·EDS·센서 연동 없이 **수율과 공정 이력 두 가지만으로** 한다.

받고 싶은 것은 두 종류다.

1. **데이터** (2절) - 수율, 공정 이력
2. **사례와 원인 확정 기록** (3절) - 초기 불량 현상·대상·판단 기준, 최종 원인과 확정 근거,
   당시 이용 가능했던 정보와 나중에 알게 된 정보의 구분

**평가의 핵심은 타당한 근거로 최종 결과에 도달하는가이다.** 엔지니어와 같은 순서로 조사할
필요는 없다. 정답 이름뿐 아니라 어떤 비교·재현·조치 후 결과로 원인을 확정했는지 받아,
후보 적중과 경쟁 설명을 구별한 근거를 함께 평가한다. 상세 조사 순서·배제 후보·조사 기간은
실패 원인 진단과 효율 비교를 위한 **선택 자료**이며, 없어도 검증을 시작한다.

현재 역할 분담: 수율·공정 이력은 사용자가 직접 추출하고, 엔지니어에게는 사례와 원인
확정 기록을 우선 요청한다. 2절은 직접 추출할 때의 확인 명세로도 사용한다.

## 1. 어떤 사례를 고르나

### 꼭 맞아야 하는 조건

- **원인이 확정된** 사례 (엔지니어가 근거를 들어 결론낸 것)
- 불량 wafer 가 **특정**돼 있다 (처음에 이상하다고 지목한 wafer 목록을 알 수 있다)

### 사례의 용도를 구분한다

- **A. 현재 기능 검증:** 같은 root_lot 안에서 타깃과 비타깃을 비교할 수 있는 사례.
  현재 대조군은 타깃이 속한 root_lot들의 **비타깃 wafer 전원**이며 정상 여부로 거르지 않는다.
  기본 설정에서는 이 대조군의 총수가 3장 미만이면 그래프가 "대조군 부족"으로 종료한다.
  3장 이상이어도 스텝별 결측이나 root_lot별 비교 가능성에 따라 계산이 제한될 수 있다.
  비타깃의 양호 확인 여부와 불량 혼입 여부는 별도로 기록한다.
- **B. 현재 한계 확인:** lot 전체에 영향을 준 원인이나 현재 분석 축 밖의 원인 사례.
  같은 root_lot 안에 양호 또는 비타깃 wafer가 없어도 포함한다. 현재 도구로 원인을
  찾는 것을 필수 성공 조건으로 삼지 않고, 비교가 막히는 이유와 필요한 후속 조사를 확인한다.

### 3~5건을 섞는 방법

| 권장 구성 | 이유 |
|-----------|------|
| 원인이 **설비·챔버**인 사례 1건 이상 | 에이전트의 주 분석 축이다 |
| 원인이 **PPID(레시피)** 이거나 **비정규 스텝 통과 여부**인 사례 1건 | 2차 분석 축을 본다 |
| 불량 wafer 가 **여러 root_lot 에 걸친** 사례 1건 이상 | 최근 고친 층화 점수 계산(여러 lot 을 묶을 때 생기는 착시 보정)을 실데이터에서 확인한다 |
| 원인이 **위 축 밖**(원자재, 마스크 등)인 사례 1건 | 에이전트가 **없는 원인을 지어내지 않는지** 본다. 못 찾는 것이 정답인 사례다 |
| **lot 전체에 영향을 준 원인** 사례 최소 1건 (B) | lot 내부 비교의 한계를 확인한다. 당시 다른 lot과 무엇을 비교했는지 함께 받는다 |
| 챔버와 레시피처럼 **두 원인이 한동안 구분되지 않았던** 사례가 있으면 우선 | 경쟁 설명을 구별하는 능력을 확인한다. 상세 조사 순서는 없어도 된다 |

한 사례가 여러 구성 조건을 충족해도 된다. A와 B를 함께 확보하고, 여러 root_lot에 걸친
타깃이 있다는 사실과 **lot 사이 비교가 필요한 사례**라는 판단은 구분한다.
선별한 3~5건은 기능 공백과 우선순위를 찾기 위한 사례이며, 사내 원인 발생 비율의 추정 표본은 아니다.

## 2. [데이터 담당자용] 추출 명세

### 2-1. 범위 - 가장 중요한 두 가지

> ⚠️ **불량 여부와 무관하게 root_lot 전체를 뽑아 주십시오.**
> 타깃이 걸친 **root_lot마다 wafer 전부**를 뽑아 주십시오. 현재 대조군은 그중 비타깃입니다.
> lot 전체 불량인 B 사례도 전체를 제공하고, 내부 비교군이 없다는 사실을 그대로 기록합니다.

> ⚠️ **특정 스텝만 뽑지 말고 공정 이력 전체를 뽑아 주십시오.**
> 원인 스텝만 골라 주면 정답을 알려 주는 셈이 됩니다. 또 "그 스텝을 거쳤는가" 자체를 보는
> 분석 축이 있어서, 비정규 스텝(`step_seq` 끝에 `EC`)까지 **전부** 있어야 합니다.

- 기간: 해당 lot 의 **수율 측정 시점까지**
- **재작업**으로 같은 스텝을 여러 번 지났으면 **모든 통과를 그대로**, 시각과 함께 주십시오.
  마지막 통과만 남기지 마십시오 (저희 쪽에서 중복을 확인합니다).

### 2-2. 수율 - wafer 1장당 1행

| 필드 | 필수 | 내용 | 주의 |
|------|:---:|------|------|
| `root_lot_id` | ● | root lot ID (5자) | |
| wafer 순번 | ● | 두 자리 순번 (`01` ~ `25`) | 원천 컬럼명이 `wafer_id` 여도 됩니다. `1`/`01` 섞여도 됩니다 |
| `lot_id` | ● | 분할 lot 포함 lot ID | |
| `lot_type` | ● | **사내 두 자리 코드 원본** (`PP`, `ES` 등) | **변환하지 말고 그대로** 주십시오 |
| `yield` | ● | 수율 수치 | 단위를 알려 주십시오 (%인지 0~1인지) |
| `date` | ● | 수율 측정 일자 | |
| `defect_type` | | EDS 불량 유형 라벨 | 없으면 **빈칸**. `none` 같은 값을 채우지 마십시오 |

### 2-3. 공정 이력 - wafer × 스텝 통과 1회당 1행 (wafer 당 수백~천 행)

| 필드 | 필수 | 내용 | 주의 |
|------|:---:|------|------|
| `root_lot_id` | ● | | |
| wafer 순번 | ● | 수율 쪽과 같은 체계 | |
| `step_seq` | ● | 제품군 2자리 + 순서 6자리 (`CC001000`) | **원본 그대로**. `EC` 접미를 떼지 마십시오 |
| `eqp_id` | ● | 설비 ID | |
| `ch_id` | ◐ | 챔버 ID | 챔버 개념이 없는 설비는 빈칸 |
| `ppid` | ◐ | **그 wafer 가 그 스텝을 돌 때 실제로 쓴** PPID | ⚠️ 아래 2-5 참조 |
| `timestamp` | ◐ | 스텝 통과 시각 | 재작업 구분에 필요합니다. 사건 의미와 관측 단위는 2-6에 기록 |
| `area` | | 그 스텝의 공정명 | 없어도 분석은 되지만, 있으면 결과를 사람이 읽을 수 있습니다 |

● 필수 · ◐ 강력 권장 · 빈칸 선택. ch_id·ppid 결측은 해당 축의 비교를 제한합니다.
timestamp 결측은 이력의 시간 해석을 제한하며, 현재 설비 공통성 계산 자체를 제외하지는 않습니다.

### 2-4. 형식

- CSV(UTF-8) 또는 parquet. **사례마다** 수율 파일 1개 + 공정 이력 파일 1개
- 파일명에 사례 번호 (`case01_yield.csv`, `case01_steps.csv`)
- 컬럼명은 원천 이름 그대로 두셔도 됩니다. 대응표만 한 줄 적어 주십시오

### 2-5. 에러 없이 틀리는 것들 (꼭 확인 부탁드립니다)

| 실수 | 결과 |
|------|------|
| **`ppid` 를 lot 마스터나 레시피 마스터에서 조인해 옴** | PPID 분석이 에러 없이 **틀린 결과**를 냅니다. 적재된 데이터만 봐서는 저희가 구분할 수 없습니다. **추출 쿼리에서 ppid 가 wafer×스텝 단위로 오는지 한 번만 확인해 주십시오** |
| `lot_type` 을 한글 두 글자(`양산`/`평가`)로 바꿔서 줌 | **에러 없이 전부 평가 lot 으로 분류**됩니다(판정이 코드 첫 글자 `P` 로 갈립니다). 영문(`prod`)으로 바꾸면 적재가 멈춥니다. **원본 코드 그대로** 주십시오 |
| `step_seq` 끝의 `EC` 를 뗌 | 비정규 스텝이 정규 스텝과 섞여 그 축의 신호가 사라집니다 |
| `step_seq` 와 `area` 가 뒤바뀜 | 적재 검사에서 경고로 잡히지만, 뽑을 때 컬럼 이름을 한 번 봐 주십시오 |
| 수율을 0~1 비율로 줌 | 적재 검사는 0~100 범위만 봐서 **경고 없이 통과**하고, 임계(90)에 걸려 **전부 저수율로** 읽힙니다. 단위만 알려 주시면 저희가 맞춥니다 |
| root_lot의 일부 wafer만 뽑음 | 비타깃 누락으로 비교가 왜곡되거나 대조군이 부족해집니다. 실제 lot 전체 불량과 추출 누락을 구분하십시오 (2-1) |

### 2-6. 시간·순서·추가 자료의 제공 가능 여부

아래는 **원천의 의미와 제공 가능성을 확인하는 항목**입니다. 미확인/제공 불가도 그대로
답해 주십시오. 추가 자료 확보 때문에 기본 수율·공정 이력 전달을 늦출 필요는 없습니다.
현재 적재 계약에 자동으로 추가되는 필드가 아니므로, 제공 시 별도 파일과 대응표로 보관합니다.

| 확인 항목 | 적어 주실 내용 |
|-----------|----------------|
| timestamp의 사건 | track-in / 실제 process 시작 / process 종료 / track-out / 기타 / 미확인. 스텝마다 다르면 구분 |
| timestamp의 관측 단위 | wafer별 실측 / lot·batch 공통 시각을 wafer에 복제 / 기타 / 미확인 |
| 시각 정밀도 | 초·분 등 정밀도, 시간대, 서로 다른 시스템의 시각을 비교할 수 있는지 |
| 추가 시작·종료 시각 | 이전 공정 완료, 현재 process 시작·종료, 설비 직전 작업 종료 시각의 제공 가능 여부와 원천 |
| wafer 순번·슬롯 | wafer 식별 순번과 실제 슬롯 번호의 관계, 공정별 슬롯 변경·재배열 이력 제공 가능 여부 |
| 실제 처리 순서 | wafer별 처리 순서와 실제 챔버·head·chuck 배정의 제공 가능 여부. wafer 번호와 같다고 추정하지 않음 |
| 불량 정도 | 당시 사용한 영역·bin별 불량률, 계측 대용특성 등의 값·단위·관측 시점·wafer 연결 키 제공 가능 여부 |
| 다른 lot 자료 | 당시 비교 lot의 수율·전체 공정 이력 및 제품·route·기간 정보의 제공 가능 여부. 비교 lot 목록과 선정 이유는 3절 조사 기록에 별도 기재 |

단일 timestamp의 차이는 정체시간이 아닐 수 있습니다. wafer 번호도 실제 처리 순서로
간주하지 않습니다. 다른 lot 자료를 받아도 현재 대조군에 자동 편입하지 않으며,
후속 비교의 설계·평가 자료로 따로 보관합니다. 최초 입력과의 분리는 4절을 따릅니다.

## 3. [당시 조사한 엔지니어용] 사례 기록 양식

사례마다 한 장씩 적어 주십시오. **필수는 초기 현상·최종 원인·확정 근거·정보 시점 구분**입니다.
상세 조사 경로는 기억나는 경우에만 적으며, 비어 있어도 사례 접수·검증을 진행합니다.

```
[사례 번호]       case01
[제품 / 시기]
[사례 용도]       A 현재 기능 검증 / B 현재 한계 확인

■ [필수] 처음 알게 된 것 (초기 입력·평가 맥락)
  - 처음 이상하다고 지목한 wafer:          (목록)
  - 그때 알고 있던 것:                     (예: "특정 lot 수율 급락", "EDS 맵 패턴 유사")
  - 당시 불량 판단 지표와 단위:            (전체 수율 / 특정 bin 비율 / 영역 불량률 / 기타)
  - 관측 단위와 대상 영역·bin:             (chip / shot / wafer / lot 등)
  - 양불 또는 약불·중불·강불 구분 기준:     (수치 기준 또는 당시 판단 근거, 없으면 미정)
  - 비타깃의 양호 확인 여부와 근거:        (확인 / 불량 혼입 / 미확인)
  - Test issue 확인 상태와 당시 근거:      (확인 / 미확인)

■ [필수] 최종 원인과 확정 근거 (평가용 — 최초 입력과 분리)
  - 원인 축:   설비 / 챔버 / PPID / 비정규 스텝 통과 / 기타(        )
  - 구체적으로: step_seq=          eqp_id=          ch_id=          ppid=
  - 확정 근거:                            (어떤 비교·재현·조치 후 결과로 확인했는가)
```

11개 항목을 모두 채울 필요는 없습니다.

## 4. 넘기면 안 되는 것 - 정답 누출 막기

에이전트가 **당시 알 수 있었던 정보만으로** 답을 찾는지 봐야 합니다.

- **최초 분석 입력으로 쓰는 것**: 3절의 "처음 이상하다고 지목한 wafer"와 2-1~2-3의
  해당 root_lot 수율·공정 이력 중 당시 이용 가능했던 자료. 그 밖의 초기 현상 정의는 평가 맥락으로 보관한다
- **입력에 넣지 않는 것**: "원인이 밝혀진 뒤에야 알게 된 정보", 나중에 추가로 찾은 불량 wafer,
  원인 스텝 표시
- 수율 테이블에 원인 스텝 컬럼이 있어도 괜찮습니다 - 적재할 때 저희가 비웁니다

3절 양식은 **입력(처음 알게 된 것)** 과 **평가 자료(최종 원인·확정 근거, 선택 조사 경로)** 를 칸으로 나눠 두었습니다.
저희는 정답 칸을 결과를 보기 전까지 열지 않습니다.
2-6의 추가 자료와 3절의 조사 항목·결정적 비교·비교 lot 선정 이유도 최초 입력에 자동으로
넣지 않습니다. 원천 관측 시점과 조사 중 확보 시점을 구분해 보관하고, 후속 실험에 사용하면
추가한 자료와 선정 경위를 별도로 기록합니다.

## 5. [분석 담당 · 내부] 받은 뒤 절차

밖으로 보낼 필요 없는 절입니다.

### 5-1. 결과를 보기 전에 먼저 기록한다 (사후 끼워맞춤 방지)

사례마다 **분석을 돌리기 전에** 아래를 적어 둔다.

- 타깃 wafer 목록과 그 근거 (3절 "처음 지목한 wafer" 그대로)
- 대조군 (같은 root_lot 비타깃 전원 - 자동으로 잡히지만 장수를 기록)
- 사례 용도 A/B, root_lot별 타깃·비타깃 수와 양호 확인 여부, 입력 자료의 당시 이용 가능 범위
- 설정값 (`ya_config` 의 임계, 순열 회차)

정답을 본 뒤 타깃·설정을 바꿔 다시 돌린 실험은 **최초 검증과 따로** 기록한다.

### 5-2. 적재 - 더미를 덮어쓰지 않는다

- ⚠️ `data/load_internal.py` 의 기본 출력 경로가 **`data/yield.db`(더미)** 다.
  반드시 `--db data/case01.db` 처럼 **별도 경로**를 준다.
- ⚠️ `_extract()` 는 아직 **빈 자리**(`NotImplementedError`)다. 받은 CSV 를 읽어 입력 계약
  형태로 넘기는 코드를 붙여야 한다(`load_internal.py` 머리 주석의 입력 계약).
- 적재 뒤 `validate()` 리포트:
  - **fatal 0건** (yield 0행, wafer_id 형식, root_lot 불일치, 고아 wafer 50% 초과, 이력 없음 50% 초과)
  - 경고도 눈으로 본다: **`ppid` 결측률**(1.0 이면 ppid 가 안 실린 것), **wafer×스텝 중복 이력**
    (재작업인지 확인), `step_seq` 형식 경고
  - 식별자 조인: 수율과 공정 이력의 wafer 가 서로 다 맞는지
  - ⚠️ **수율 단위**: 0~1 비율로 왔으면 적재 전에 0~100 으로 바꾼다 - `validate()` 의 범위 검사(0~100)가
    비율을 못 잡는다
  - `lot_type` 경고 "양산 lot 0건" 이 뜨면 원천 코드가 변환돼 온 것이다(한글 두 글자면 전부 평가로 분류됨)

### 5-3. 분석 실행 (P1-4)

- LLM 없이 커먼널리티 도구(`find_commonality` 등)를 직접 호출한다.
- ⚠️ 분석 도구는 **`ya_config.DB_PATH` 하나만** 읽고, 그 값은 **하드코딩**(`data/yield.db`)이다.
  별도 DB 를 읽게 하는 방법은 P1-4 착수 때 정한다(실행 스크립트에서 경로를 바꿔 주거나
  파일을 교체). 파일 교체라면 **더미를 먼저 백업**한다(`사내-투입-점검표.md` 0-1).
- 사례마다 기록할 것: 후보·순위·분모·제외 사유, 그리고
  **(a) 알려진 원인이 후보·1등 묶음에 드는가**, **(b) 경쟁 설명을 구별할 근거가 있는가**,
  **(c) 데이터가 부족하면 확정을 보류하고 필요한 확인을 식별할 수 있는가**.
- A 사례는 (a)와 함께 비교 가능한 표본·축을 평가한다. B 사례는 원인 적중을 필수로 요구하지
  않고, 대조군 부족·비교 불가·차이 미검출 등 실제 제한과 원인 확정에 필요한 근거를 대조한다.
  B 사례를 정해진 종료 코드 하나(`no_signal` 등)로 끝날 것이라고 가정하지 않는다.
- 최초 결과 기록 후 최종 원인·확정 근거를 열어, 막힌 지점·관련 조사 항목·필요 데이터를
  사례별로 정리한다. 상세 조사 경로가 있으면 보조로 대조하되 경로 일치는 성공 조건이 아니다.
  후속 질문 자동 생성은 현재 구현된 것으로 간주하지 않고 필요한 확인은 사람이 정리한다.
  이 결과로 lot 간 비교, 시간·순서 분석, 후속 질문 기능의 우선순위를 정한다.

### 5-4. 함께 답할 열린 질문 (pooling 작업에서 넘어옴)

- `a == 0 and c_ == 0` 층 스킵 모양(후보가 한 층에만 나타남)이 실데이터에서 얼마나 자주 나오는가
- pooling 성능 초과분(+39.7% / +34.1%)을 수용할지 - stratum 수·후보 수 분포를 보고 판단
