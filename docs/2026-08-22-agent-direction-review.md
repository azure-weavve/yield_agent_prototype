작성일: 2026-08-22
목적: Claude Code 세션에서 상세 설계/구현을 이어가기 위한 논의 정리

> 발전 방향이다. 원문은 당시 기록으로 보존한다.

## 1. 문제 제기 — 위화감의 정체

팀의 실제 업무는 **신규 제품에서 아직 이름이 없는 이상을 표면화**하고, 경향성과 공통점을 근거로 분석기술팀·제품기술팀에 정밀 분석을 의뢰하는 일이다.

그런데 현재 `yield_agent`는 구조적으로 **진단기(diagnosis)**다.

- `hypotheses.yaml`에 등록된 가설 목록이 곧 도달 가능한 결론의 전체 집합
- `finalize`가 단일 `claim_id`를 요구 → "이미 이름 붙은 원인 중 하나를 고르라"는 계약
- 이름이 없으면 `no_signal`로 폐기

즉 **닫힌 세계 분류기로 열린 세계 탐색을 하려는** 미스매치. 사용자 표현으로는 "미래의 것을 찾아야 하는데 과거의 것으로 한정시키는" 느낌.

### 도구 계층은 대체로 멀쩡하다

EQP_CH 공통성, PPID 공통성, step_passage, 메트로 분포 비교, EDS 군집화는 전부 **도메인 지식이 박혀 있지 않은 일반적 차이 탐지기**다. 문제는 그 위층(결론 계약)이다. 도구가 "이 챔버에 몰려 있다"는 신호를 찾아도 기존 가설 이름으로 번역하도록 강요당한다.

→ **폐기가 아니라 종단 계약의 반전**이 필요.

## 2. 출력 계약의 전환

### 원인 결론형 (현재)

> "PHOTO_02 챔버 B의 온도 이상이 원인이다"

- 가능한 원인 목록이 닫혀 있어야 성립
- 출력 1개, 배타적
- 신규 제품에서 원인이 목록에 없으면 **반드시 실패** (억지 선택 or `no_signal`)

### 정밀분석 후보형 (목표)

> "불량 14장 중 12장이 챔버 B 통과(대조군 40장 중 3장). 효과크기 X. 등록된 어떤 패턴으로도 설명되지 않음 → 챔버 B의 Y 항목 측정 의뢰 권장"

- 순위가 매겨진 N개, 각 항목에 **다음 행동**이 부착
- 가설 집합의 완결성 불필요

### 네 가지 실질적 차이

| 항목 | 원인 결론형 | 정밀분석 후보형 |
|---|---|---|
| 완결성 요구 | 가설 집합이 전부여야 성립 | 불필요 |
| 오류 비용 | 신뢰 붕괴 | 확인 1회 낭비 |
| 평가 지표 | 정확도 | recall@k, 의뢰 낭비율 |
| 미지의 처리 | 실패(`no_signal`) | **가장 가치 있는 출력** |

신규 제품 도메인에서는 recall이 압도적으로 중요.

### 주의점 두 가지

- 후보 목록이 **판단 회피가 되면 안 된다.** 판단을 안 하는 게 아니라 종류를 바꾸는 것: "무엇이 원인인가" → "무엇이 얼마나 이상한가". 순위 부담은 그대로 진다.
- 기존 가설은 버리지 않는다. **배경 제거기**로 재배치 — 알려진 재발 패턴을 "이미 아는 것"으로 걷어내고 **남은 잔차를 부각**시키는 역할.

### 파생 결정

FDC 기준선을 그룹 대조 vs 시간 대조 중 무엇으로 할지 미결이었으나, **신규 제품이면 과거 정상 구간 자체가 없다.**
→ **그룹 대조가 기본, 시간 대조는 성숙 제품용 옵션.**

## 3. "분석이 얕다"의 세 가지 층위

핵심 정리. 각각 원인도 해결책도 다르다.

### 깊이(depth)의 얕음
한 축을 끝까지 파지 못함. 챔버 수준에서 신호가 보이면 장비/시간대/PPID 조합으로 grain을 바꿔가며 재확인해야 하는데 한두 번 호출하고 넘어감.
→ **해결: 반복 탐색 능력 = 서브에이전트**

### 폭(breadth)의 얕음
볼 수 있는 축 자체가 적음. FDC 센서 계층 미구현, DBKM 미구현, 장비 내부 dwell time 접근 불가.
→ **해결: 도구 추가**

### 서술(narration)의 얕음
실제로는 찾았는데 단일 `claim_id`로 눌려서 보고서에 한 줄로 나옴.
→ **해결: 증거 계약 + `finalize` 다축 집계. 서브에이전트와 무관.**

> **중요**: 서브에이전트로는 서술의 얕음이 해결되지 않는다. 서브에이전트가 아무리 풍부한 정보를 뱉어도 `finalize`가 단일 `claim_id`만 받으면 그 정보는 메인 컨텍스트 안에서 죽는다. **창고에 물건을 더 쌓는 것과 창고 문을 넓히는 것은 다른 작업.** 오히려 문 앞에서 버려지는 양만 늘고, 그 압축을 LLM이 자기 재량으로 하게 되어 도구 출처 추적성이 끊긴다.

## 4. 서브에이전트 설계 — 두 가지 방식

### 방식 A: 결론 반환형

각 서브에이전트가 자기 축에서 판정까지 내려 메인에 전달.

```
경로 서브에이전트 → "EQP_CH 공통성 성립. 챔버 B가 원인. confidence 0.85"
분포 서브에이전트 → "메트로 이상 없음. confidence 0.7"
EDS 서브에이전트   → "엣지 집중. 세정 계열. confidence 0.9"
```

**장점**: 구현 단순, 축별 전문 프롬프트, 메인 컨텍스트 경량

**문제 4가지**:
1. **confidence가 계층마다 곱해진다.** 실 LLM이 3대3 비교에서 `confidence: 1.0`을 자기보고한 전례. 서브 3개 + 메인 = 4중 누적. 게이트가 검증할 원자료는 이미 서브에이전트 안에서 소각됨.
2. **축 간 순위 불가.** 서로 다른 프롬프트가 만든 서로 다른 척도라 코드가 비교할 근거가 없음.
3. **잔차가 사라진다.** 등록된 가설 이름으로 결론 내는 순간 "이름 없는 이상"이 축 내부에서 폐기. 신규 제품 탐색이 목표인데 가장 중요한 신호가 메인에 도달 못 함.
4. **약한 신호의 조합 불가.** 세 축이 각각 "미달"이어도 **동일 웨이퍼 집합**을 가리키면 강한 신호. 원자료 없이는 교차 검증 불가.

### 방식 B: 증거 반환형 (권장)

서브에이전트는 판정하지 않고 **공통 스키마의 증거 레코드 목록**을 반환.

레코드가 담아야 할 필드(초안):

- **축 / grain**: `eqp_ch` / 챔버 수준, `metro` / 측정항목 수준
- **대상 식별자**: `PHOTO_02.CH_B`
- **영향 웨이퍼 집합**: 실제 wafer id 목록 ← **교차 검증의 핵심**
- **대조 구조**: 타깃 12/14, 대조군 3/40, 대조군 선정 방식
- **효과 크기**: 축 무관 비교 가능한 공통 척도
- **분포 형태**: 연속형 축에서 통과/실패가 아니라 시프트/분산확대/이봉 구분
- **커버리지·신뢰도**: 표본 부족, 대조군 부실 여부
- **기존 가설 매칭**: 등록 패턴 해당 여부, 아니면 **미설명 잔차 표시**

메인과 코드 게이트는 이 레코드들을 받아 **효과 크기와 웨이퍼 집합 겹침으로 순위**를 매긴다. 세 축이 같은 12장을 가리키면 **코드가** 발견한다(LLM 자기보고 아님).

**얻는 것**: 축 간 비교 가능 / `finalize` 다축 집계 자연 해결 / 메트로를 이진으로 누를 필요 없음 / 미설명 잔차가 1급 출력

**대가**: 스키마 설계가 선행 작업, 축 간 효과 크기 척도 통일이 난제, 메인 컨텍스트가 A보다 무거움(단 요약 레코드라 감당 가능)

### 실무적 절충

서브에이전트가 **증거 레코드 + 해석 노트**를 분리 반환.

- **레코드**: 게이트가 소비하는 구속력 있는 데이터
- **노트**: 최종 보고서 서술에만 쓰이는 참고 텍스트

축별 전문성은 노트로 살리되 판단은 레코드에서 코드가 한다. 계층이 늘어나도 **"LLM 제안, 코드 결정"이 유지되는 유일한 형태.**

메인 에이전트는 판사가 아니라 **서기**에 가깝다.

### 절단면

도구 단위가 아니라 **축 단위**로 쪼갤 것. 도구 1개당 에이전트 1개는 도구 호출에 LLM 껍데기만 씌우는 셈.

- 경로 공통성 (EQP_CH / PPID / step_passage / skip)
- 분포 비교 (메트로 / FDC)
- 유사 군집 (EDS)

## 5. 최종 목표와의 연결

목표: **에이전트가 원인 추정을 위해 새로운 데이터나 방안을 추천**하는 수준.

성립 조건 3가지:
1. **무엇을 모르는지 아는 것** — 지금 증거로 A와 B를 구분 못 한다는 인식
2. **어떤 데이터가 그걸 가를지 아는 것** — A면 이 값, B면 저 값
3. **획득 비용을 아는 것** — 얼마나 걸리고 누가 하는지

결정적인 건 1번. **"모른다"를 표현할 수 없는 시스템은 다음 측정을 추천할 수 없다.** 현재 미확정은 `no_signal`이라는 단일 실패 상태로 붕괴하며, "챔버 B가 의심되나 온도 문제인지 파티클인지 현재 증거로 구분 불가"를 담을 자리가 없다.

증거 레코드 스키마의 잔차·커버리지 부족·대조군 부실 필드가 훗날 **"그래서 무엇을 더 봐야 하는가"의 입력**이 된다. 추천 기능은 이 위에 얹히는 것이지, 없이는 얹힐 데가 없다.

### 서브에이전트가 미래 지향인 진짜 이유

에이전트가 여러 개라서가 아니라 **반복 탐색이 가능해지기 때문.** 닫힌 목록에서 고르는 건 1회 조회로 끝나지만, 이름 없는 이상을 찾는 건 "여기가 이상하네 → 이 각도로 다시 → 아니네, 저 각도로"의 반복이 필요하다. 이 반복 능력이 본질이고 서브에이전트는 그것을 담는 한 형태.

단, 반복이 성립하려면 **중간 상태를 표현할 수 있어야** 한다. 그래서 증거 스키마가 먼저다.

## 6. 실행 순서

0. **데이터 품질 · config 버그 정리** — 지금 무엇을 측정 중인지 신뢰 가능하게
   - `commonality.py` config 속성명 불일치(`MIN_TARGET`, `TOP_K`, `MIN_SCORE`) → 현재 튜닝 자체가 무효
   - 고아 웨이퍼, 중복 wafer×step
   - *어떤 아키텍처를 얹어도 그대로 올라오며, 구조를 먼저 바꾸면 분산되어 더 잡기 어려워짐*

1. **증거 레코드 스키마 정의 + `finalize` 다축 집계 리팩터** — 문 넓히기
   - `hypotheses.yaml`, `domain/evidence.py`, `domain/registry.py`가 단일 claim 전제로 얽혀 있음. **영향 범위 조사가 선행**

2. **현재 도구들로 계약을 채우게 하고 보고서 확인** — 계약 검증
   - 서브에이전트를 만들기 **전에** 스키마 결함을 드러내면 고치는 비용이 훨씬 쌈

3. **조건부 도구 등록** — 싼 해결책으로 루프 예산 확보
   - `SENSOR_MODE`, `EDS_MODE` 플래그에 따라 미사용 도구 제외
   - `compare_sensor_distribution`이 센서 미연결에도 `_BASE_TOOLS` 점유하는 문제 해결

4. **축별 서브에이전트 전환** — 반복 탐색으로 깊이 확보
   - 반환 계약이 이미 정의돼 있으므로 계약을 채우는 실행 껍데기로 붙임

5. **새 도구 추가** — 폭 확보 (FDC 센서 계층, DBKM, dwell time)

> 순서를 뒤집으면(4를 먼저) 나중에 세 에이전트의 프롬프트와 반환 형식을 전부 다시 손봐야 한다.

## 7. 미결 사항

- **축 간 효과 크기의 공통 척도** — 경로 공통성(범주형 편향)과 메트로 분포 시프트(연속형)를 같은 자에 올려야 순위가 성립. 이 설계에서 가장 까다로운 지점.
- **`finalize` 계약 변경의 영향 범위** — `hypotheses.yaml` / `evidence.py` / `registry.py` 결합도 조사 필요
- **`no_signal`의 재정의** — 실패 상태에서 "미확정 + 다음 필요 증거" 상태로 분해
- **잔차 판정 기준** — 무엇을 "등록 패턴으로 설명됨"으로 볼 것인가의 코드 기준

## 8. 한 줄 요약

문제는 실행 구조가 아니라 **출력 계약**이었다. 서브에이전트는 필요하지만 시작점이 아니라 중간 단계이며, 시작점은 **"LLM이 무엇을 반환해야 하는가"의 재정의**다.
