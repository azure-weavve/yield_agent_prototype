## A. 데이터 모델

### A-1. `wafer_id` 는 합성 키가 아니라 두 자리 순번이다

| | |
|---|---|
| 기존 | `wafer_id` 컬럼 값 자체가 `{root_lot}_{no}` 형태의 합성 키라고 문서화 |
| 변경 | **원천** `wafer_id` = 두 자리 순번(`"01"`, `"14"`, `"25"`). **타깃** `wafer_id` = 합성 조인 키(`A45Z5_01`) |

**이유.** 현업 엔지니어가 실제로 쓰는 매핑 키는 `root_lot_id` + `_` + `wafer_id` 조합이다.
EDS 인덱스도 이 형태로 구축되어 있다. 원천 컬럼명과 타깃 컬럼명이 겹치는 것이 혼란의 원인.

**규칙 (확정).**

```
조인 키 = root_lot_id + "_" + zero-pad(wafer_no, 2)      예) A45Z5_01
```

- 제로 패딩 **필수**. EDS 응답이 패딩된 형태로 확인됨(`ㅇㅇㅇㅇㅇ_07`).
- 패딩 관행은 엔지니어마다 다르므로, 원천이 `"01"` 로 오더라도 ETL 이
  `int()` 캐스팅 후 `f"{n:02d}"` 로 **재포맷**한다. `"1"` 과 `"01"` 이 섞이면
  조인이 **에러 없이** 깨진다.
- `yield` · `step_history` · EDS 3곳이 바이트 단위로 일치해야 한다.

**코드 영향.** `data/load_internal.py` 의 `build_wafer_id()`. 하위 코드는 ID 를
파싱하지 않고 문자열로 들고 다니므로 수정 불필요.

### A-2. `yield.process_step` 은 정답 누출이다

| | |
|---|---|
| 기존 | `yield` 테이블의 입력 컬럼 |
| 변경 | **항상 NULL.** 원천에 있어도 적재하지 않는다 |

**이유.** "어느 스텝이 원인인가"는 이 시스템이 **추론해야 할 결론**이지 입력이 아니다.
더미 생성기에서 "이 스텝에 이상을 심겠다"는 ground truth 로 쓰던 값이 그대로
입력 스키마에 남아 있었다. 실데이터에는 존재하지 않으며, 있어서도 안 된다.

**코드 영향.** 컬럼 자체는 기존 SQL 호환을 위해 남겨두되 값은 NULL.
`find_low_yield_lots` 의 `worst_wafer.process_step` 에 NULL 이 담기므로,
**이 값에 의존하던 코드는 수정 대상**이다.

### A-3. `defect_type` 라벨은 없다 — EDS 로 대체한다

| | |
|---|---|
| 기존 | NOT NULL, `'none'` 정규화, 그룹핑의 **완전일치 키** |
| 변경 | **nullable 메타데이터.** 그룹 구성은 **EDS top-k** 로 |

**이유.** 사내에 정확히 라벨링된 불량 유형이 없다. 새로 만들려면 공수가 과다하다.
그런데 애초에 라벨은 "같은 불량 패턴 wafer 를 묶는다"의 대리 지표였고,
**EDS 가 이미 연속 공간에서 그 일을 하고 있다.** 유사도 top-k 가 곧 "같은 패턴 이웃"이며,
라벨은 EDS 임베딩을 이산 카테고리로 뭉갠 열화 버전이다.

**중요: NULL 로 두고 `'none'` 을 채우지 말 것.**
`'none'` 을 넣으면 라벨 없는 wafer 가 전부 "정상"으로 둔갑해 대조군에 조용히 섞인다.
NULL 이면 `find_normal_wafers` 의 `WHERE defect_type = 'none'` 이 빈 리스트를 반환하여
**눈에 띄게 실패한다.** 이는 버그가 아니라 의도된 가시적 실패다.

**코드 영향.**
- `status_node` 의 `defect_type` 문자열 완전일치 그룹핑 → **폐기 대상**
- `find_normal_wafers` → 대조군 구성을 root_lot 기반으로 재작성 필요
- 07-18 문서의 열린 질문 "형제 그룹핑 방법" → **EDS 로 확정, 종결**

### A-4. `process_log` 단일 테이블 → 2층 분리

| | |
|---|---|
| 기존 | `process_log` 하나. wafer 당 (스텝×파라미터) 몇 줄 |
| 변경 | `step_history`(선적재) + `sensor_log`(온디맨드) |

**이유 — 규모.** 실제 fab 데이터:

- 1 wafer = **1000+ 메인스텝** (metro 계측 스텝은 별도)
- 1 메인스텝 = **spec 보유 센서 수백 개**, spec 없는 것까지 하면 수천 개
- → wafer 당 10⁵ ~ 10⁶ 파라미터

전수 적재도, 전수 비교도 불가능하다.

| 테이블 | 적재 | 규모 | 용도 |
|---|---|---|---|
| `step_history` | **선적재** (배치) | wafer 당 ~1000행 | 1단 commonality |
| `sensor_log` | **온디맨드** (지목된 스텝만) | 분석당 수만 행 | 2단 센서 비교 |

`sensor_log` 는 별도 캐시 DB(`sensor_cache.db`) + `SensorStore` 계층으로 붙인다.
**아직 미구현.**

### A-5. 설비는 `eqp_id` + `ch_id` 두 컬럼이다

| | |
|---|---|
| 기존 | `equipment_id` 단일 컬럼 |
| 변경 | `eqp_id`, `ch_id` 분리 저장. **합성은 tool 에서** |

**이유.** 현업은 둘을 나눠 저장하고 볼 때 합쳐서 본다(ETCH9호기 3번 챔버 → `ETCH9_3`).
ETL 에서 미리 합치면 설비 레벨 롤업을 다시 파싱해야 한다.

**granularity 2종 (둘 다 계산한다).**
- **챔버 레벨**(주): `f"{eqp_id}_{ch_id}"` — 실제 원인이 챔버 단위인 경우가 많음
- **설비 레벨**(롤업): `eqp_id` — 타깃이 여러 챔버에 흩어지면 챔버 score 는 희석되지만
  설비 레벨에서 살아난다. 롤업이 더 강하면 설비 공통 원인(가스 공급·PM 이력 등) 신호

`ch_id` 는 NULL 허용(단일 챔버 설비, 챔버 개념 없는 스텝). NULL 이면 챔버 레벨을
건너뛰고 설비 레벨만 계산한다. **`"ETCH9_None"` 같은 가짜 키를 만들지 말 것.**

## B. 분석 구조

### B-1. 2단 깔때기 도입 (commonality 신설)

기존 설계는 파라미터 분포 비교로 직행했다. 10⁵ 규모에서는:

- wafer 수십 장 대비 특징 10⁵개 → 다중비교로 거짓양성에 파묻힘
- LLM 에 넘기기 전에 tool 이 소수 용의자로 줄여야 함

**변경된 흐름.**

```
1단  find_commonality       설비/챔버 이력만 (차원 ~1000)  → 의심 스텝 3~5개로 축소
2단  센서 분포 비교           지목된 스텝 한정 (수백 개)     → 최종 용의자
```

`compare_parameter_distribution` 의 역할이 "전 파라미터 비교" →
**"지목된 스텝 한정 top-K 용의자 생성기"** 로 바뀐다.

**통계 원칙.** 2단 출력은 p-value 컷이 아니라 **효과크기 랭킹 top-K**.
센서를 수백 개로 줄여도 다중비교 문제는 남는다(300개 × α=0.05 → 우연히 15개 유의).
tool 결과에 "후보이지 결론이 아님"이 명시되어야 한다.

### B-2. metro 가 아니라 FDC 가 주 기질이다

한때 metro(계측) 데이터를 주로 쓰는 방향을 검토했으나 **철회.**

| | FDC (메인스텝 센서) | metro (계측) |
|---|---|---|
| 커버리지 | **전 wafer** | **sparse** — metro 스텝 2000개 중 wafer 당 200개 미만 계측되는 경우도 |
| spec | **있음** (수백 개/스텝) | 있음 |
| 답하는 질문 | 어느 설비/챔버가 드리프트했나 | 어느 스텝의 출력이 벗어났나 |

**결정적 이유.** 의도한 인터페이스는 `root_lot + wafer` 단일 wafer 입력이다.
metro 는 그 wafer 가 계측 대상이 아니면 **0행**이고, 이것이 예외가 아니라 다수 사례다.
FDC 는 전 wafer 보유 → 인터페이스가 항상 성립한다.

→ **FDC(spec 보유 센서 한정)를 주 기질로, metro 는 있을 때만 쓰는 보강 증거.**

### B-3. 대조군은 같은 root_lot 의 비타깃 wafer (방식 a)

현업에서도 정답이 없는 영역. 세 후보 중 **(a) 를 우선 채택**, 추후 (b)+(c) 로 확장.

- **(a) 같은 root_lot 내 비타깃 wafer** ← 채택. route·시간 교락이 구조적으로 제거됨
- (b) 같은 제품·비슷한 시기의 정상 수율 wafer — N 은 크지만 route 차이 유입
- (c) EDS 상 비유사 + 시기·제품 매칭

**(a) 가 눈감는 것 (반드시 인지할 것).**
원인이 root_lot 전체에 걸리면 타깃도 대조군도 같은 챔버를 거치므로 **score 가 전부 0** 이다.
즉 "원인 없음"과 "원인이 lot 전체라 안 보임"이 같은 출력이 된다.
→ commonality 는 빈 결과를 그냥 반환하지 않고 **`no_signal`** 상태로
"lot 내부 대조로는 안 보인다, lot 밖 대조군이 필요하다"를 명시한다.
이 상태가 향후 (b)+(c) 확장의 트리거다.

**타깃 크기에 따른 모드 분기.**

| 타깃 크기 | 모드 | 방식 |
|---|---|---|
| 임계 이상 | A | 같은 root_lot 안에서 타깃/대조군 분리 (가장 깨끗) |
| 1~2장 | B | EDS top-k 로 타깃 확장 + root_lot 별 **층화** 계산 후 합산 |

모드 B 는 route 교락 위험을 안고 계산하므로, **모드가 갈렸다는 사실이 결과에 드러나야**
finalize 게이트가 신뢰도를 다르게 평가할 수 있다.
임계값은 정답이 없으므로 config 상수로 빼고 실데이터 보며 조정한다.

### B-4. 평가랏은 배제 대상이 아니라 해석 재료다

| | |
|---|---|
| 기존 | 대조군에서 평가랏 제외 (route 가 다를 수 있으므로) |
| 변경 | **필터하지 않는다.** `lot_type` 을 meta 로 실어 보낸다 |

**이유.** 평가랏에는 엔지니어 평가뿐 아니라 **설비 작업 후 정상 동작을 검증하는 랏**이
포함된다. 즉 원인 후보와 붙어 있는 wafer 이므로 배제하면 단서를 버린다.
게다가 실무상 양산/평가가 깔끔히 나뉘는 경우가 드물어, 필터를 걸면 대조군 N 만 깎인다.

`classify_lot_type()` 은 격리 함수로 유지(보안상 실제 규칙은 저장소에 두지 않음).
용도가 **필터 → 컨텍스트**로 바뀌었을 뿐이다.

## C. EDS 인터페이스

### C-1. 응답 스키마가 코드 가정과 달랐다 (조용한 전멸 상태였음)

실제 응답 구조:

```python
{
  "query_wafer":    {"wafer_id": "...._14", "line_id": ..., "product": ..., "tkout_time": ...},
  "similar_wafers": [
    {"rank": 1, "wafer_id": "...._07", "similarity": -0.18433594703674316, ...},
    ...
  ]
}
```

| 항목 | 코드 가정 | 실제 | 영향 |
|---|---|---|---|
| 봉투 키 | `resp.json()["results"]` | **`similar_wafers`** | 파싱 실패 |
| 식별자 | `wafer_id` | `wafer_id` ✓ (패딩된 합성 키 ✓) | 이상 없음 |
| 유사도 | `score` | **`similarity`** | `None` → **전량 필터링** |
| self 포함 | 포함 가정, `k+1` 조회 후 제외 | 서버가 이미 분리(`query_wafer`) | 무해한 중복 |

**가장 위험했던 것.** `r.get("score")` 가 모든 후보에서 `None` → 전부 `continue` →
**에러 없이 항상 빈 결과.** 실제 응답을 보지 않았으면 유사도 검색이 조용히 죽은 채로
굴러갔을 것이다.

### C-2. 절대 유사도 임계는 **보류** (rank 기반 top-k 만 사용)

`similarity` 값이 **음수 스케일**(-0.184 / -0.216 / -0.227)이고 rank 1 이 가장 큰 값이다
(= 클수록 유사, 이미 rank 오름차순 정렬).

이 스케일에서 기존 상수는 전부 무력하다:

- `EDS_MIN_SIMILARITY = 0.5` → **전량 컷**
- `SIBLING_MIN_SIMILARITY = 0.8` → 단일 wafer 형제 그룹이 **항상 빈 집합**

값의 부호·범위는 HNSW 거리 메트릭(L2 vs cosine) 선택에 따라 달라진다.
→ **절대 임계 필터를 끄고 서버 rank 순 + top-k 로만 자른다.** 부호가 어떻든 안전하다.

## D. 운영 / 적재 방식

### D-1. 선적재(batch pre-load)로 확정

`load_internal.py` 는 **에이전트가 호출하는 tool 이 아니라 독립 배치 스크립트**다.

```
[야간 배치]  load_internal.py  →  yield.db 갱신
                                     ↓ (읽기 전용)
[분석 시점]  LangGraph 루프 → commonality → SQL 조회
```

분석 중에는 실행되지 않는다. 분석이 아무리 많이 돌아도 사내 lib 에 부하가 없다.

**추출 범위 = 최근 N일 · 특정 제품.** 이것이 곧 분석 가능 범위다.
적재되지 않은 root_lot 은 EDS 가 이웃으로 지목해도 층화에서 조용히 빠진다
(EDS 는 fab 전체를 인덱싱하므로 범위가 어긋날 수 있다 — 현재는 EDS 적재 이력이
더 길어 문제되지 않는 상황).

**온디맨드가 아닌 이유.** 향후 대조군 확장 (b)/(c) 는 "조건에 맞는 정상 wafer 를 **찾는**"
작업이다. 후보 풀이 미리 있어야 하며, 온디맨드로는 구조적으로 불가능하다.

### D-2. full refresh + 원자적 교체

매 실행마다 `DROP TABLE` → `CREATE TABLE` → 전량 재적재(full refresh).
상태가 단순하다(DB 내용 = 마지막 `_extract()` 결과). 부분 갱신 실패로 인한 불일치가 없다.

**단, 운영 DB 를 직접 DROP 하지 않는다.**

```
<db>.tmp 에 적재 → 검증 → fatal 없으면 os.replace 로 원자적 교체
```

직접 DROP 하면 추출 실패·프로세스 중단·검증 실패 시 어제까지 멀쩡하던 데이터가
사라진 채 남는다(분석이 전부 `no_paired_stratum` 으로 끝나는데 원인이 안 보임).

**검증 2층.**

| 층 | 항목 | 동작 |
|---|---|---|
| fatal | yield 0행, `wafer_id` 형식 위반, `root_lot_id` 불일치, 고아 wafer 50%↑, 이력 없는 wafer 50%↑ | **교체 차단**, 기존 DB 유지 |
| warning | 소수 고아·결측, yield 범위 이탈, wafer×스텝 중복(rework), 양산 lot 0건 | 교체하되 출력 |

고아/결측은 소수면 흔하지만 **절반을 넘으면 조인 키 자체가 어긋난 것**이므로 fatal.
`--force` 로 무시 가능. 종료 코드 0 = 교체됨, 1 = 차단됨.

### D-3. 규모 한계

`step_history` 는 wafer 당 ~1000행:

| wafer 수 | 행 수 | full refresh |
|---|---|---|
| 1천 장 | 100만 | 수 초 |
| 1만 장 | 1천만 | 수십 초 ~ 수 분 |
| 10만 장 | 1억 | **무리** — 증분 적재 또는 DB 이전 필요 |

**만 장 근처까지는 현 구조로 충분.** 그 이상은 증분(root_lot 단위 삭제-재삽입)을 고려한다.
완료된 root_lot 의 step_history 는 **불변**이므로 증분에 잘 맞는다
(갱신 누락 위험이 거의 없음).

### D-4. 추출 성능 — OR 체인 금지 (미해결)

현재 원천 추출이 `(eqp_id='...' AND wafer_id='01') OR (...) OR ...` 형태로,
심각하게 느리다.

**문제.** 수백~수천 개 OR 분기는 옵티마이저가 인덱스 레인지 스캔을 포기하게 만들고,
날짜 파티션 프루닝도 타지 못한다(전 기간 스캔). SQL 텍스트 자체의 파싱 비용도 크다.

**해법 (우선순위 순).**
1. **범위 술어로 전환** — 선적재이므로 조건은 "이 wafer 들"이 아니라 범위여야 한다.
   `WHERE product = :p AND tkout_time >= :from` — 키 목록이 통째로 사라진다.
2. **불가피하면 root_lot 단위로 축약** — 어차피 root_lot 전체가 필요하다(대조군이
   같은 root_lot 이므로 wafer 단위로 거를 이유가 없다). `WHERE root_lot_id IN (...)`
   → 25매 기준 OR 분기 500개가 IN 항목 20개로 축소.
3. 목록이 매우 크면 임시 테이블 + 조인 (해시 조인으로 풀림).

**추가 축소 여지.** 컬럼은 6개만 필요(`root_lot_id, wafer_id, process_step, eqp_id,
ch_id, timestamp`). 설비가 갈리지 않는 스텝(전 wafer 동일 설비)은 coverage 차이가 0 이라
후보가 될 수 없으므로 원천에서 걸러낼 수 있으면 행 수가 크게 준다.

## F. 요약 — 가장 중요한 두 가지

1. **`defect_type` 라벨을 버리고 EDS 로 대체한 것**이 가장 큰 전환이다.
   라벨링 프로젝트 하나가 통째로 사라졌고, 07-18 문서의 "형제 그룹핑 방법"
   열린 질문도 함께 종결됐다.

2. **EDS `score` / `similarity` 불일치가 가장 위험했다.**
   실제 응답을 확인하지 않았다면 유사도 검색이 **에러 없이** 빈 결과만 내는 채로
   운영에 들어갔을 것이다. 스키마 가정은 반드시 실측으로 확인해야 한다.

공통 교훈: **설계가 아니라 원천 데이터의 실제 형태가 결정하는 영역이 넓다.**
