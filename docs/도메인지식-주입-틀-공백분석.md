# 도메인 지식 주입 틀 — 공백 분석

> **작성 관점**: 이 문서를 쓰는 사람의 역할은 "분석 방법(도메인 분석)"을 짜는 게 아니라,
> **도메인 전문가가 자기 지식을 넣을 자리(surface)를 만드는 것**이다.
> 그 관점 하나로만 이 프로토타입을 평가한다.
>
> **평가 기준 (단 하나)**:
> *지금 이 코드에서 "도메인 지식"은 어디에 살고 있고, 전문가가 개발자 없이 거기에 손댈 수 있는가?*

---

## 핵심 진단 — 도메인 지식이 "개발자 코드" 안에 흩어져 있음

구조는 훌륭하지만, **전문가가 지식을 주입할 선언적 자리가 거의 없다.**
지금 도메인 판단은 세 곳에 하드코딩돼 있고, 셋 다 전문가가 못 건드리는 개발자 영역이다.

### ① 상수 (`config.py`) — 사실 전부 도메인 판단이다
| 위치 | 값 | 실제 의미 (도메인 지식) |
|------|----|----|
| `config.py:18` | `YIELD_THRESHOLD = 90` | "수율 몇 %부터 이상인가" — 제품·공정별로 다름 |
| `config.py:38` | `SIBLING_MIN_SIMILARITY = 0.8` | "얼마나 닮아야 같은 사건인가" |
| `config.py:34` | `CONFIDENCE_THRESHOLD = 0.8` | "얼마나 확신해야 결론인가" |
| `config.py:41` | `CONTROL_MIN_SIZE = 3` | 통계적 유효 최소 표본 |

→ 이건 파이썬 상수가 아니라 **전문가가 튜닝해야 할 노브**다.
지금은 `.py` 안에 있어 전문가가 손대려면 개발자를 불러야 한다.

### ② 분석 전략 (`nodes.py:23` 시스템 프롬프트)
`ANALYZE_SYSTEM_PROMPT` 문자열에 "그룹을 대조해라, compare_process_logs 가 핵심이다"라는
**분석 방법론 전체**가 박혀 있다. 전문가의 실제 사고 순서
("center_spot 이면 먼저 Etch rf_power 부터 본다")를 넣을 자리가 없다.

### ③ 종료 판정 규칙 (`nodes.py:180` 게이트)
"suspect 장비와 가설이 일치해야 승인" — 이 **증거 충분 기준**도 하드코딩이다.
하지만 도메인에서 "충분한 근거"는 defect 종류마다 다르다.

---

## 구체적 공백 (전문가 주입 관점 우선순위 순)

### 1순위 — 인과 가설 공간이 닫혀 있음 (가장 근본적)
지금 이 시스템이 내릴 수 있는 결론은 사실상
**"불량 그룹만 거친 장비 + 스펙 이탈" 딱 하나**다
(`compare_process_logs` + 게이트). 도구 8개가 있어도 인과 계열은 하나로 수렴한다.

실제 전문가는 훨씬 많은 가설 계열을 안다 — 챔버 A/B 매칭, PM(정비) 타이밍,
소재 lot, 레시피 변경 이력, 온도 드리프트, seasoning 상태 등.
**지금 구조에서 새 인과 가설을 추가하려면 개발자가 매번 새 tool 을 짜고 배선해야 한다.**
전문가가 "이런 것도 확인해봐"를 **데이터로 등록**할 방법이 없다.

→ 틀 만드는 사람의 핵심 과제: **"도메인 체크/가설을 선언적으로 등록하는 레지스트리"**.
tool 을 코드가 아니라 명세(어떤 컬럼을 어떻게 비교 → 어떤 결론)로 기술하게 만드는 것.

### 2순위 — 도메인 온톨로지(용어 지도)가 아예 없음
`defect_type ↔ 의심 공정 ↔ 핵심 파라미터`의 **연결 지도**가 코드 어디에도 없다.
전문가 지식의 가장 값진 형태인데 담을 그릇이 없다.

오히려 `grouping.py:6` 에 **"defect 라벨은 판정 기준이 아니라 참고 정보"** 라고 적혀 있다 —
즉 도메인 지식(불량 라벨)을 **일부러 안 쓰고** 유사맵에만 의존한다.
프로토타입으로선 합리적이지만, 전문가 지식을 넣는 틀 관점에선
"가장 귀한 지식을 버리는 자리"가 된다.

### 3순위 — 전문가 피드백을 담을 곳이 없음 (단방향)
`findings` 감사 기록은 훌륭하지만 **한 방향으로만 흐른다.**
전문가가 리포트를 보고 "이 결론 틀렸어, 진짜 원인은 Y 였어"라고 해도,
그 교정을 **포착해서 다음 분석에 반영하는 경로가 없다.**
도메인 지식 틀의 핵심은 이 피드백 루프다
(교정 → 알려진 사례/규칙 → 미래 분석에 영향).

### 4순위 — 임계값이 전역 단일값
`YIELD_THRESHOLD=90` 이 전 제품 공통이다.
전문가는 제품/디바이스별로 다른 기준을 안다.
컨텍스트별로 임계를 **전문가가 저작(author)** 할 자리가 필요하다.

## 이미 잘 만들어둔 "주입 자리" (계속 살릴 것)

- **`agent_tools.py` 의 docstring** — 사실 **가장 깨끗한 지식 주입점**이다.
  "이 tool 을 언제 쓰는가"라는 도메인 판단이 docstring 에 들어가고 LLM 이 그걸 읽는다.
  여기를 전문가가 저작하게 만드는 게 가장 현실적인 첫걸음.
- **`findings` 감사 기록** — 지식 축적의 좋은 기반(substrate). 피드백 루프만 붙이면 됨.
- **인터페이스 뒤 추상화(EDS/LLM mode)** — 구현 교체는 이미 깔끔함.

## 방향 제안 — 그어야 할 선

틀 만드는 사람으로서 그릴 **가장 중요한 선**:

> **"개발자가 하드코딩하는 것"과 "전문가가 데이터로 저작하는 것"의 경계가
> 지금 어디에도 안 그어져 있다.**

지금은 도메인스러운 모든 게 개발자 코드에 섞여 있다.
틀의 역할은 이 선을 긋고 전문가에게 **선언적 지식 레이어**
(YAML/DB 같은, 코딩 아닌 저작 대상)를 주는 것.

최소한 세 가지를 그 레이어로 뽑아내는 것부터 시작:

1. **임계값·판정 노브** (config → 컨텍스트별 저작 가능한 데이터)
2. **인과 가설/체크 명세** (tool 코드 → 선언적 규칙, 확장 가능한 레지스트리)
3. **알려진 사례/교정** (피드백 루프 유입구)

**특히 1순위(인과 가설 레지스트리)가 이 프로젝트의 성패를 가른다** —
여기가 막히면 아무리 tool 을 늘려도 결론은 하나로만 나온다.
