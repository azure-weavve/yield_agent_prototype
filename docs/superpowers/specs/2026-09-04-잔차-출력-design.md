# 잔차 출력 — 판별선의 이진 붕괴 완화 (B)

조사 문서 `docs/2026-08-31-finalize-계약-영향범위.md` §B 의 권고를 설계로 확정한다.
순서상 **C(공통 척도) → A(발급 자격) → B(여기) → D/E(어휘·서술)** 의 세 번째다.

기준선: main `250c0ac`, 472 passed.

---

## 1. 문제 — 약한 신호와 무신호가 같은 출력이다

`passes` 는 `domain/engine.py:_passes()` 가 `status == ok` · `score >= 0.5` ·
`target_pass >= 2` 로 정하는 **부울**이고, 그 하나가 출력 유무를 정한다:

```
_record_evidence  <-  ranked_groups()  <-  Bundle.passing()   # passes=True 만 통과
```

조사에서 실측된 결과 — 4축을 전부 돌리고 그중 한 축이 `score 0.4 · p 0.2` 후보를
냈는데 판별선(0.5)을 못 넘으면:

| 상황 | 판정 | `final_claims` |
|---|---|---|
| 4축 ok + 미통과 후보만 | (loop 1) 반려 → (loop 7) `inconclusive` | `[]` |
| ok + no_signal 섞임 | `no_signal` | `[]` |

즉 **"약한 신호가 있다" 와 "아무것도 없다" 가 같은 출력**이다. 수치는 `findings`
JSON 으로 리포트 LLM 프롬프트에 흘러가지만, 코드가 붙이는 `[근거]` 줄과 `claims`
블록에는 0건이고 sys 프롬프트는 동시에 "신호 없음으로 서술하라" 를 건다.

부수 결함: 미통과 후보만 있으면 `_no_candidate_action` 의 물러설 안내(`step_back`)도
안 붙는다 — (2)(3)(3b) 어느 것도 안 열리므로. LLM 은 종료할 길이 없어 `MAX_LOOPS`
까지 왕복하다 `inconclusive` 로 끝난다. **예산 낭비 경로이기도 하다.**

## 2. 확정된 결정 (사용자 승인)

1. **출력과 종료를 둘 다 고친다.** 잔차를 리포트·프롬프트에 싣고, 잔차만 있는
   상태에서 게이트가 물러설 길을 연다.
2. **잔차는 `final_claims` 에 함께 싣는다.** 센서(A)의 전례를 따른다 — 순위·접기·
   렌더러를 재사용하고, 항목의 필드로 가른다.
3. **자격은 "아랫선 신설 + 지목 가능한 통과 후보가 0건일 때만".** 확정(confirmed)
   경로는 손대지 않는다.
4. **새 판정 `weak_signal` 을 신설한다.** `no_signal` 을 넓히지 않는다.

## 3. 어휘 — 잔차란 무엇인가

**잔차 = 판별선을 넘지 못했지만 아랫선은 넘은 1단 후보.** 사람에게 하는 말은
"봤고, 후보도 났고, 다만 이 표본으로는 확정할 만큼 갈리지 않았다" 이다.

`no_signal`("대조한 축에서 갈리는 것이 없었다")과 다른 사실이고, 조치도 다르다:
잔차는 **표본을 늘리거나 대조군을 바꾸면 갈릴 수 있다.**

### 새 필드를 만들지 않는다

`Claim` 에는 이미 `passes: bool` 과 `reject_reason: str | None` 이 있다. 잔차는
`passes=False` 인 Claim 이고, 렌더러와 프롬프트는 그 두 필드로 가른다.

`kind` 를 새로 만들지 않는 이유: `kind` 는 **"어느 도구가 냈나"**(`statistical` /
`sensor`)이고 잔차는 **"판별선을 넘었나"** 라 축이 다르다. 겹쳐 놓으면 "미통과
센서" 를 어느 쪽으로 부를지가 곧바로 모순이 된다.

## 4. `Bundle.residuals()` — 새 관문

```python
def residuals(self) -> list[Claim]:
    """판별선 아래의 1단 후보 중 '약한 신호' 라고 부를 수 있는 것."""
```

자격 (전부 만족):

| 조건 | 이유 |
|---|---|
| `not c.passes` | 통과한 것은 근거지 잔차가 아니다 |
| `c.kind != "sensor"` | 센서는 자기 판별선(0.8)을 갖고 이미 근거 전용이다. 미통과분까지 실으면 '왜' 후보가 두 겹이 된다 |
| `c.status_ok`(= 후보를 낸 실행의 `status == "ok"`) | `no_paired_stratum`·`no_signal` 은 "약한 신호" 가 아니라 "볼 것이 없었다" 다 |
| `c.target_pass >= COMMONALITY_PASS_MIN_TARGET` | 타깃 1장짜리 후보는 표본 문제지 신호가 아니다 |
| `c.score >= RESIDUAL_MIN_SCORE` | 0.05 짜리를 '근거' 란에 찍으면 엔지니어가 그것으로 설비를 세운다 |

> **status 는 `Bundle.statuses[c.tool]` 로 본다.** `Claim` 은 status 를 안 들고 있고,
> `passes=False` 의 사유는 `reject_reason` **문자열**에만 남는다 - 그것을 파싱하는 것은
> 이 저장소가 `claim_id` 에서 금지한 짓이다. 번들이 이미 도구 단위로 status 를 들고
> 있으므로(`statuses: dict[tool, status]`) 거기서 읽는다. status 는 후보가 아니라
> **그 실행**의 성질이라 도구 단위가 맞는 단위다. `Claim` 스키마도 `_FIRST_CLASS_FIELDS`
> 도 안 건드린다.

### `passing()` 은 건드리지 않는다

A 리뷰에서 확인된 사실: `passing()` 을 넓히면 **두 경로로 즉시 샌다.**

- `statistical_passing()` = `passing()` 에서 센서를 뺀 것 → 잔차가 **지목 가능**해진다.
- `ranked_groups()` = `passing()` 을 접어 줄 세운 것 → 잔차가 **1등 층**에 들어가고,
  게이트 승인 조건이 1등 층 멤버십이므로 **잔차로 confirmed 가 나간다.**

그래서 잔차는 별도 관문으로 들어오고, `passing()` 의 정의는 그대로 둔다.

## 5. 게이트 — `weak_signal` 을 (2) 앞에 넣는다

```
(1)  승인            claim.passes and kind != sensor and picked_rank == 1 and conf >= 0.8
(2a) weak_signal     not statistical_passing() and not claim_id and residuals()   <- 신설
(2)  no_signal       not statistical_passing() and not claim_id and "no_signal" in statuses
(3)  no_comparable_data / (3b) tool_failure
(4)  루프 한계 → inconclusive
```

**`no_signal` 보다 앞인 이유:** 한 축은 침묵하고 다른 축은 ok + 약한 후보를 낸
상태에서 두 조건이 **동시에 참**이 된다. 그때 "봤고 후보도 났는데 약하다" 가 더
많은 정보를 담은 사실이므로 그쪽이 이겨야 한다. 뒤에 두면 같은 상태가 `no_signal`
로 먼저 빠져나가 잔차가 또 소각된다.

`not claim_id` 하한은 (2)(3)과 같은 이유로 유지한다 — **지목을 제출한 것은 물러선
것이 아니다.** 확신도는 보지 않는다(물러섬 선언에 높은 확신도를 요구하면 모순이다).

판정은 `finalize_accepted=True` · `finalize_status="weak_signal"` 이다.

⚠️ **`_record_evidence` 에는 `passing() + residuals()` 를 함께 넘긴다.** (2a)의 하한은
`statistical_passing()`(지목 가능한 것)이라, **센서만 통과한 상태에서도 열린다** -
그때 잔차만 실으면 판별선을 넘은 센서 근거가 리포트에서 사라진다. A 가 만든
"근거로 실을 것(`passing()`)과 지목 가능한 것(`statistical_passing()`)은 다르다" 를
여기서도 그대로 지킨다. 잔차는 근거를 **밀어내는 것이 아니라 더하는 것**이다.

## 6. 잔차를 싣는 경로

`ranked_groups()` 에 대상 목록 인자를 연다(기본값은 지금대로 `self.passing()`):

```python
def ranked_groups(self, claims: list[Claim] | None = None) -> list[ClaimGroup]:
```

잔차도 **같은 접기·순위 함수를 탄다** — 교락(같은 wafer 를 두 이름으로)과
포함관계(설비 ⊃ 챔버)는 잔차에서도 똑같이 일어나고, 여기서 규칙을 다시 구현하면
C(축 간 순위)가 없앤 "두 곳에 쓰인 순위 규칙" 이 되살아난다.

`_record_evidence` 는 그대로 쓴다 — `REPORT_MAX_EVIDENCE`(8) 상한과 "지목한 묶음은
안 자른다" 규칙이 잔차에도 그대로 필요하다.

## 7. 렌더링 — `[잔차]` 라벨

`report_node` 는 지금 모든 항목을 `[근거 {rank}]` 로 찍는다. 항목의 대표
(`asdict(Claim)`)에 `passes` 가 실려 있으므로 거기서 갈라:

```
[잔차 1] eqp_ch_commonality:chamber:CC002000:ETCH9_B · 분리 점수 0.4 · 타깃 4/4 통과 ·
         대조군 3/5 통과 · 순열 p 0.2 (판별선 미달: 분리 점수 0.4 < 0.5)
```

**라벨이 없으면 통과 근거와 글자 하나 다르지 않다** — 이 기능이 만드는 가장 큰
위험이 그것이고, 엔지니어는 그 줄을 보고 설비를 세운다. `reject_reason` 을 줄
끝에 그대로 단다(문구를 새로 짓지 않는다 — `_passes` 가 만든 문장이 이미 정확하다).

`format_evidence_line` 이 아니라 `report_node` 에서 라벨을 가르는 이유: 근거 줄
본문(`format_group_line`)은 승인 verdict 와 리포트가 **같은 문자열을 공유**하고,
게이트 verdict 는 `[근거 N]` 접두어를 안 쓴다.

## 8. LLM 계약 4곳 — 반드시 같이 넣는다

판정 하나를 신설하면 대응하는 자리가 정해져 있다(조사 §D).

| 자리 | 파일 | 넣을 것 |
|---|---|---|
| 게이트 verdict | `graph/nodes.py::_finalize_gate` | "약한 신호(판별선 미달) N건을 잔차로 싣는다" + 커버리지 |
| mock 결론문 | `llm/client.py` (status 분기 10종) | `weak_signal` 분기 |
| 운영 리포트 sys 프롬프트 | `llm/client.py` (status 분기 10종) | "판별선 미달이라 원인으로 단정하지 마라. **무엇을 하면 갈리는지**(표본·대조군)를 적어라" |
| 분석 sys 프롬프트 | `graph/nodes.py::ANALYZE_SYSTEM_PROMPT` | "미통과 후보만 있으면 지목하지 말고 claim_id 를 비워 물러서라 — 게이트가 잔차로 싣는다" |

마지막 것이 이번 계약의 핵심이다. 없으면 LLM 은 약한 후보를 계속 지목하고
`_gate_rejection` 이 계속 반려해 왕복이 남는다 — 예산 낭비 경로를 반만 닫는 셈이다.

`domain/hypotheses.yaml` 은 **안 건드린다.** 잔차는 도구가 발급하는 것이 아니라
게이트가 만드는 출력이라, 도구 설명에 적을 사실이 없다.

## 9. 새 노브

```python
# 잔차 아랫선 - 판별선(0.5)을 못 넘은 후보 중 이 값 이상만 '약한 신호' 로 싣는다.
# 0.25 는 판별선의 절반이며 실데이터를 본 값이 아니다 - COMMONALITY_PASS_* ·
# SENSOR_PASS_MIN_EFFECT 와 같은 성격의 조정 노브다.
RESIDUAL_MIN_SCORE = float(os.getenv("RESIDUAL_MIN_SCORE", "0.25"))
```

## 10. 안 하는 것 (YAGNI)

- **판별선을 없애지 않는다.** 연속값 순위만으로 전부 실으면 게이트 승인 조건과
  `REPORT_MAX_EVIDENCE` 가 유일한 방어선이 되고, 노이즈 후보가 승인 대상이 된다.
- **지목 가능한 통과 후보(`statistical_passing()`)가 있을 때는 잔차를 안 싣는다.**
  진단된 결함이 일어나는 상황이 정확히 "지목할 것이 0건" 이고, 확정 리포트에서
  강한 근거 옆에 약한 것이 나란히 서면 같은 무게로 읽힌다. (센서만 통과한 상태는
  잔차와 함께 실린다 - §5 의 ⚠️ 를 볼 것.)
- **미통과 센서는 잔차가 아니다**(§4).
- **D/E 는 여기서 하지 않는다.** `final_hypothesis` 단수 문제와 "구분 불가" 판정은
  이 브랜치 범위 밖이다. `weak_signal` 신설이 D 의 앞자락을 건드리지만, 어휘를 하나
  더 만드는 것과 서술 스키마를 복수로 바꾸는 것은 다른 작업이다.

## 11. 훼손 실험 (계획서에서 표로 확정)

A 에서 얻은 규칙을 처음부터 건다: **한 규칙을 N 자리에 옮겼으면 N 자리를 전부
훼손한다.** 최소 목록:

| # | 훼손 | 잡아야 하는 이유 |
|---|---|---|
| 1 | `residuals()` 가 `passes` 를 안 본다 | 통과 근거가 잔차로 두 번 실린다 |
| 2 | 아랫선(`RESIDUAL_MIN_SCORE`) 조건 제거 | 0.05 짜리가 `[잔차]` 로 찍힌다 |
| 3 | `target_pass` 하한 제거 | 타깃 1장짜리가 근거란에 온다 |
| 4 | 센서 제외 조건 제거 | 미통과 센서가 잔차로 샌다 |
| 5 | `status != ok` 후보를 잔차에 넣는다 | "볼 것이 없었다" 가 "약한 신호" 로 둔갑한다 |
| 6 | `passing()` 이 잔차를 포함하게 | **잔차로 confirmed 가 나간다** (§4) |
| 7 | (2a)를 (2) 뒤로 옮긴다 | 혼합 상태가 `no_signal` 로 빠져 잔차가 소각된다 |
| 8 | (2a)의 `not claim_id` 제거 | 환각 지목이 물러섬으로 둔갑한다 |
| 9 | `report_node` 의 `[잔차]` 라벨 제거 | 미통과가 근거와 글자 하나 다르지 않다 |
| 10 | 줄 끝 `reject_reason` 제거 | 왜 약한지 못 읽는다 |
| 11~14 | §8 의 네 계약을 하나씩 지운다 | 계약의 반쪽만 남으면 거짓이다 |
| 15 | `ranked_groups()` 의 기본값을 잔차로 | 통과 근거 경로가 조용히 바뀐다 |

## 12. 성공 기준

1. 4축 ok + `score 0.4` 후보만 있는 상태에서 `finalize_status == "weak_signal"`,
   `final_claims` 에 그 후보가 `[잔차]` 로 실리고, **루프를 다 태우지 않는다.**
2. 통과 후보만 있으면 판정·근거 목록·수치·순서가 지금과 **불변**이다(확정 경로
   불변). 다만 이 브랜치는 확정 경로의 어휘 **두 곳**을 의도적으로 중립어로 바꿨으므로,
   출력이 **바이트 동일**한 것은 그 둘이 다 안 나올 때다: (가) `REPORT_MAX_EVIDENCE`
   상한에 걸려 잘리면 요약 줄이 `[생략] 상한 밖 N건` 이다(근거든 잔차든 잘려 나간
   항목을 어느 한쪽 이름으로도 부르지 않는다) · (나) 동점 묶음이 있으면 그 줄이
   `같은 등수의 항목이 더 있다` 이다(`weak_signal` 경로에서 이 줄이 `[잔차]` 위에도
   찍히므로 `근거` 라고 쓸 수 없다). 둘 중 하나라도 나오면 바이트 동일을 약속하지 않는다.
3. 잔차는 `finalize` 로 지목해도 원인으로 확정되지 않는다. 통계 통과 후보가 없고
   아랫선을 넘은 잔차가 남아 있을 때는 지목해도 반려로 왕복시키지 않는다 - 후속
   `2026-09-06-잔차-지목-종료-design.md` 가 `(2a)` 하한을 "정직한 제출" 로 넓혔다.
   통계 통과 후보가 있거나 지목한 후보가 아랫선에도 못 미쳐 잔차 자격조차 없으면
   지목은 여전히 반려된다.
4. 훼손 15건이 전부 잡힌다.

## 13. 알려진 트레이드오프

`(2a)` 는 커버리지 하한(`unrun`/`failed`)을 보지 않는다. 잔차가 하나라도 있으면,
축을 하나만 돌리고 나머지 셋은 안 돌린 상태(`loop=2`)에서도 즉시 `weak_signal`
로 종료가 열린다 — 예전에는 이 상태가 반려로 돌아가 남은 축 호출을 강제했다.

이 대가로 얻는 것이 이 기능의 목적이다: 판별선 아래 신호가 축 커버리지와
무관하게 **소각되지 않는다.** `(2)` 가 이미 같은 선택을 했다("전축 실행은
전제 조건이 아니다", §1) — 등록 가설을 다 돌리기 전에는 물러설 수 없게 하면
루프 예산이 체크리스트 소화에 강제 배정돼 깊이 탐색이 구조적으로 막힌다는
것이 그 판정의 근거였고, `(2a)` 는 같은 근거를 잔차에도 적용한 것뿐이다.
그리고 `not claim_id` 하한이 있어 이 조기 종료는 **LLM 이 스스로 빈손
finalize 를 제출한 뒤**에만 열린다 - 게이트가 탐색을 잘라먹는 것이 아니라,
이미 포기를 선언한 상태에 이름을 붙이는 것이다.

완화 장치는 리포트에 실리는 커버리지 고백뿐이다 - `_coverage_phrase` 가
"안 돌린 축 N 개" 를 그대로 문장에 남겨, 조기 종료가 "전축을 봤다" 로 오독되지
않게 막는다(이 정직성은 `test_a_weak_only_state_ends_as_weak_signal` 이 잠근다).

되돌리려면 `(2a)` 조건에 `not unrun` 을 더하면 된다. 다만 그러면 브리프 Step 1
의 첫 시나리오(단일 축만 돌린 상태, `EQP_CH_BELOW_LINE` 하나)에서 잔차가 다시
소각되고, 이 기능이 고치려던 문제(약한 신호와 무신호가 같은 출력)가 부분
커버리지 구간에서 그대로 재발한다.

## 14. 안 한 것 — 후속 "잔차를 inconclusive 로 넓히기"

**잔차는 `(2a)` 에만 실린다.** `(4) inconclusive`(`graph/nodes.py`)와 게이트를
안 타는 `report_node` 백스톱은 여전히 인자 없는 `bundle.ranked_groups()`
(통과 후보만)를 넘긴다. 최종 리뷰가 이것을 지적했고, 2026-09-06 에 사용자가
**후속으로 미루기로 결정**했다.

그래서 아직 잔차가 타는 경로가 남아 있다. `(2a)` 의 하한이 `not claim_id` 이므로,
LLM 이 `ANALYZE_SYSTEM_PROMPT` 의 물러서기 지시를 따르지 않고 약한 후보를 계속
지목하면 `(5)` 반려를 반복하다 루프 한계에서 `inconclusive` + `final_claims=[]`
로 끝난다 — §1 의 증상 표 그대로다. **그 협조율은 측정되지 않았다.** 테스트가
잠근 것은 "프롬프트에 그 문장이 있다" 이지 "LLM 이 따른다" 가 아니다(mock 은
스크립트대로 움직인다). 사내 데이터로 돌려 봐야 안다.

미룬 이유는 이것이 구현 누락이 아니라 **계약 확장**이기 때문이다. §5 가 잔차를
`(2a)` 로 한정했으므로 `(4)` 가 잔차를 실어야 한다는 약속은 어디에도 없다.
착수하면 네 가지가 한 묶음이다:

1. `(4)` 와 백스톱의 `_record_evidence` 인자를 합집합으로 바꾼다.
2. **`_fold_key` 에 `passes` 를 반영한다**(= 접기 계약 수정). 지금 안전한 것은
   `(2a)` 의 `not statistical_passing()` 하한 덕분에 합집합의 비센서 claim 이
   전부 미통과이기 때문이다. `(4)` 에서 합집합을 쓰면 통과한 statistical claim 과
   잔차가 한 묶음에 섞일 수 있고, p 가 작은 잔차가 lead 를 차지하면 통과 근거가
   `passes` 키도 없는 `confounded_with` 로 강등돼 묶음 전체가 `[잔차]` 로 찍힌다.
   이 위험은 `graph/evidence.py` 의 `_fold_key` docstring 에도 적어 두었다.
3. LLM 계약 다섯 곳이 지금 `weak_signal` 만 설명하므로 전부 다시 본다.
4. `(4)` 의 판정문("확정 근거 없이 리포팅으로 진행한다")이 잔차를 싣고도 참인지
   고쳐 쓴다.

2 가 다른 브랜치에서 확정한 접기 계약을 건드리므로, 착수는 브레인스토밍부터 밟는다.
