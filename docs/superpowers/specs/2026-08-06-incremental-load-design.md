# step_history 증분 적재 설계 (2026-08-06)

## 문제

사내 첫 적재 이후 매일 갱신을 돌리려는데 전체 재적재가 감당이 안 된다.

- 추출: 약 3분 (사내 lib → DataFrame)
- 적재: **수십 분**, 그 동안 메모리 32GB 를 거의 다 쓴다
- 규모: 1개 제품 3개월 = **약 3GB / 2,800만 행** (`yield` + `step_history`)

원인은 두 겹이다.

**1. 전달 방식.** 사내 `_extract()` 가 DataFrame 을 `to_dict()` 로 바꿔 2,800만 개짜리
dict 리스트를 만들어 `load()` 에 넘긴다. `load()` 안의 변환은 제너레이터고 삽입도
2만 행 배치라 적재 코드 자체는 메모리를 안 쌓지만, **호출부가 들고 있는 리스트가
적재 내내 살아 있다.** dict 하나에 400바이트만 잡아도 11GB 이고 DataFrame 원본까지
남아 있으면 그 위에 더 얹힌다. 스왑이 시작되면 삽입은 빠른데 전체가 수십 분이 된다.

**2. 매일 전량을 다시 넣는다.** 하루에 늘어나는 lot 은 소수인데 3개월치를 통째로
다시 만든다.

## 결정 요약

| 항목 | 결정 |
|---|---|
| 증분 축 | **root_lot 단위** (분석 단위와 일치, 조인 완결성 유지) |
| 변경 발견 | **최근 N일 재확인 창** (원천에 수정일자가 없어도 돈다) |
| 멱등성 | lot 단위 **삭제 후 삽입** (재작업이 뒤달려 붙으므로 필수) |
| 안전성 | 라이브 DB + **단일 트랜잭션**, 검증 실패 시 롤백 |
| 전체 재적재 | **유지** (`--rebuild`, 지금의 tmp + 원자적 교체 그대로) |
| 메모리 | `_extract()` 를 **lot 청크 단위로 여러 번** 호출 |
| 보존 정리 | **이번 범위 밖** (성장률만 기록) |

### 왜 날짜 축이 아니라 root_lot 축인가

`yield.date` 는 검사(EDS) 시점이고 `step_history.timestamp` 는 공정 처리 시점이라
둘이 몇 주씩 벌어진다. "어제 처리된 스텝만" 당기면 아직 검사 전인 wafer 의 이력이
대량으로 들어와 `yield` 에 짝이 없는 고아 행이 된다. 지금 검증은 고아 비율 50%
초과 시 교체를 막으므로, 이 축을 쓰면 매일 적재가 차단되거나 안전장치를 꺼야 한다.

root_lot 축은 "검사가 끝나 `yield` 가 생긴 lot 의 이력을 통째로" 당기므로 고아가
생기지 않고, commonality 가 root_lot 안에서 대조군을 만드는 것과도 단위가 맞는다.

### 왜 안 1(증분 추가)이고 일원화나 파일 복사가 아닌가

- **증분 일원화**(전체 재적재 제거): 백필이 지금보다 느려진다. 인덱스를 유지한 채
  2,800만 행을 넣고 lot 마다 DELETE 가 헛돈다. tmp + 교체 안전망도 사라져서 백필
  중 실패하면 반쯤 찬 DB 가 남는다.
- **파일 복사 후 교체**: 기존 안전 모델을 글자 그대로 유지하지만 매일 3GB(1년 뒤
  12GB)를 복사한다. 트랜잭션으로 같은 보장을 얻는데 비용만 더 든다.

## 1. 실행 모드

상호배타이고 **하나는 반드시 지정**해야 한다.

```
python -X utf8 -m data.load_internal --rebuild
python -X utf8 -m data.load_internal --since 7
python -X utf8 -m data.load_internal --lots A45Z5,B12X3
```

| 모드 | 동작 |
|---|---|
| `--rebuild` | 전체 재적재. tmp DB 생성 → 검증 → 원자적 교체 (지금 동작 + 청크 순회) |
| `--since N` | 최근 N일 재확인 창. **매일 도는 것** |
| `--lots ...` | 지정 lot 만. 수동 교정용 |

**모드를 필수로 두는 이유**: 지금은 인자 없이 실행하면 전체 재적재다. 매일 도는
스크립트에서 인자가 빠지면 수십 분짜리 전체 재적재가 조용히 돈다.

`--force` 는 지금 의미를 유지한다 (치명적 검증 결과를 무시하고 확정).

`--since` 는 일수를 인자로 받고, 값을 생략하면 `LOAD_SINCE_DAYS`(기본 7)를 쓴다.
호출부가 `오늘 - N일` 을 날짜 문자열로 계산해 `_extract_lot_ids()` 에 넘긴다.
청크 크기는 `LOAD_LOT_CHUNK`(기본 20). 둘 다 env 로 조정하며 실측 후 정할 값이다.

종료 코드는 지금 규약을 잇는다. `--rebuild` 는 교체 여부, 증분은 **커밋 여부**로
0/1 을 낸다. 대상 lot 0개인 정상 종료는 0 이다.

## 2. 추출 계약 변경

`_extract()` 를 둘로 나눈다.

```python
def _extract_lot_ids(since_date: str | None) -> list[str]:
    """대상 root_lot 목록. None 이면 전체 (rebuild 용).

    since_date 가 주어지면:
        검사일이 since_date 이후인 lot  UNION  스텝 처리시각이 since_date 이후인 lot
    """


def _extract(root_lots: list[str]) -> tuple[Iterable[dict], Iterable[dict]]:
    """지정 root_lot 들의 (yield_records, step_records).

    반환 레코드 형태는 기존 입력 계약 그대로다 (파일 상단 docstring 참조).
    """
```

호출부는 lot 목록을 `LOAD_LOT_CHUNK` 개씩 잘라 `_extract()` 를 **여러 번** 부른다.
청크 처리가 끝나면 그 DataFrame 과 dict 리스트가 참조를 잃고 해제되므로 **메모리가
청크 하나 크기로 유계**가 된다. `--rebuild` 도 같은 순회를 타므로 32GB 문제는 두
경로 모두에서 사라진다.

### `--since` 를 두 축의 합집합으로 잡는 이유

조용히 틀리기 쉬운 자리다. 재작업 이력이 붙어도 `yield` 의 검사일은 그대로일 수
있다. 검사일만 보면 그 lot 이 재확인 창에 안 걸려서 **이력은 늘었는데 DB 에는
영영 안 들어온다.** 그래서 스텝 처리시각 축을 합집합으로 더한다.

### 사내 코드에 생기는 작업

이미 구현된 `_extract()` 에 `root_lot IN (...)` 절을 더하고, lot 목록 조회 함수를
하나 만든다. DataFrame → dict 변환 부분은 그대로 둔다.

## 3. 스키마 변경

`step_history` 에 컬럼 하나를 추가한다.

```sql
CREATE TABLE step_history (
    wafer_id     TEXT NOT NULL,
    root_lot_id  TEXT NOT NULL,   -- 추가: lot 단위 삭제의 키
    step_seq     TEXT NOT NULL,
    area         TEXT,
    eqp_id       TEXT NOT NULL,
    ch_id        TEXT,
    ppid         TEXT,
    timestamp    TEXT
);
CREATE INDEX idx_step_root ON step_history(root_lot_id);   -- 추가
```

값은 이미 입력 계약에 있으므로 `transform_steps` 가 그대로 실으면 된다.

**`generate_dummy.py` 의 DDL 과 INSERT 도 같이 고친다.** `tests/test_schema_contract.py`
가 사내 스키마와 더미 스키마를 컬럼 이름 + NULL 허용 여부까지 비교하고 허용 차이가
비어 있어서, 한쪽만 고치면 테스트가 잡는다.

**대안을 안 쓰는 이유**: `wafer_id LIKE 'A45Z5\_%'` 는 2,800만 행에서 인덱스를 못
타고, `yield` 를 거쳐 지우는 방식은 lot 의 wafer 구성이 바뀌었을 때 **지워지지 않은
행이 남는다.**

## 4. 멱등 적재

lot 청크마다:

```sql
DELETE FROM step_history WHERE root_lot_id IN (...);
DELETE FROM yield        WHERE root_lot_id IN (...);
-- 이어서 INSERT
```

같은 lot 을 몇 번 넣어도 결과가 같고, 재작업으로 이력이 늘어난 lot 은 새 내용으로
통째로 대체된다. `--rebuild` 는 DROP/CREATE 로 시작하므로 이 삭제를 타지 않는다.

## 5. 트랜잭션과 실패 처리

증분 실행 전체를 **트랜잭션 하나**로 감싼다.

```
BEGIN
  청크마다: DELETE → INSERT
  검증
COMMIT  (치명적 문제 있으면 ROLLBACK)
```

프로세스가 중간에 죽어도 SQLite 저널이 되돌린다.

> ⚠️ 지금 코드의 `PRAGMA journal_mode=OFF` / `synchronous=OFF` 를 **증분 경로에서는
> 쓰면 안 된다.** 저널을 끄면 롤백 자체가 불가능해서 "되돌릴 수 있다" 는 전제가
> 조용히 깨진다. 저 두 줄은 tmp 파일에 새로 만드는 `--rebuild` 전용이다.

트랜잭션 하나에 담기는 양은 매일 적재 기준 lot 수십 개라 저널 크기가 문제되지
않는다. `--lots` 로 대량 지정하면 커질 수 있으나 예외적 사용이다.

## 6. 검증 재설계

증분용 검증은 **이번에 넣은 lot 으로 범위를 좁힌다.**

| 검사 | 증분에서의 범위 |
|---|---|
| wafer_id 형식 / root_lot 교차검증 | 대상 lot 한정 |
| step_seq 형식 | 대상 lot 한정 |
| 고아 wafer 비율 | **대상 lot 한정** |
| 이력 없는 wafer 비율 | **대상 lot 한정** |
| ch_id / ppid / area 결측률 | 대상 lot 한정 |
| 총 행수 · lot 수 | 전역 (보고용) |

**성능 때문만이 아니다.** 고아 비율을 전역으로 재면 이번에 들어온 lot 23개가 통째로
깨져 있어도 기존 2,800만 행이 희석해 비율이 0.001 로 나온다. 안전장치가 있는데
아무것도 못 막는다. 전역 LEFT JOIN 을 매일 2,800만 행에서 도는 비용은 부차적 이유다.

### "빈 추출" 판정이 증분에서는 다르다

지금은 `yield` 0행이면 무조건 치명적(추출 실패)이다. 증분에서는 주말·비가동으로
대상 lot 이 0개인 것이 정상이다.

- 대상 lot 목록이 비었다 → **정상 종료**, 아무것도 안 함, 종료 코드 0
- 대상 lot 은 있는데 그 lot 들의 yield 가 0행 → **치명적**, 롤백

이 구분이 없으면 주말마다 실패로 끝나거나, 반대로 진짜 추출 장애가 조용히 넘어간다.

## 7. 출력

증분 모드 출력에 다음을 싣는다 (`ya_console.say`, em-dash 금지).

```
[증분] 대상 lot 23개 (기준: 최근 7일)
[삭제] yield 0행 / step_history 0행
[삽입] yield 575행 / step_history 561,000행
[전체] yield 84,000행 / step_history 27,900,000행 / root_lot 1,120개
```

삭제 행수가 0 이 아니면 재작업으로 다시 실린 lot 이 있다는 뜻이라 사람이 봐야 할
값이다. 정합성 경고·치명적 오류 출력은 지금 형식을 유지한다.

## 8. 보존 정리 (이번 범위 밖)

1개 제품 3개월이 3GB 니까 1년이면 약 12GB 다. SQLite 가 감당은 하지만 `--rebuild`
시간이 비례해 는다. 지금 아픈 문제가 아니므로 만들지 않는다. 필요해지면
`--purge-before` 를 같은 트랜잭션 패턴으로 붙인다.

## 9. 테스트

TDD 로 진행한다. 기존 201개는 그대로 통과해야 한다.

| 테스트 | 고정하는 것 |
|---|---|
| 멱등성 | 같은 lot 을 두 번 적재해도 행 수·내용이 같다 |
| 재작업 대체 | 같은 lot 을 다른 이력으로 재적재하면 옛 행이 안 남는다 |
| 롤백 | 치명적 검증을 유발하는 배치를 넣으면 DB 가 이전 상태 그대로다 |
| 청크 순회 | 청크 크기보다 많은 lot 을 주면 `_extract` 가 여러 번 불린다 |
| 빈 목록 | 대상 lot 0개면 정상 종료하고 DB 를 안 건드린다 |
| 검증 범위 (양방향) | 기존 데이터에 고아가 있어도 이번 배치가 깨끗하면 통과하고, 이번 배치가 더러우면 기존이 깨끗해도 막힌다 |
| 스키마 계약 | `root_lot_id` 가 사내·더미 양쪽에 있다 (기존 테스트가 자동으로 잡는다) |

**변이 확인을 필수로 한다** (2026-07-30 ppid 리뷰에서 습관으로 채택):

- `DELETE` 를 빼면 멱등성 테스트가 **단독으로** 죽어야 한다
- 검증 범위를 전역으로 되돌리면 "이번 배치가 더러우면 막힌다" 가 죽어야 한다
- 롤백을 커밋으로 바꾸면 롤백 테스트가 죽어야 한다
