# Stage 3 — 2단 센서 비교 설계 (그룹 대조)

작성일: 2026-07-25
선행: `docs/stages.md` (Stage 3 계약·결정 항목), `docs/2026-07-24-domain-corrections.md` B-1·B-2

---

## 0. 문제

1단(commonality)은 **"어느 스텝의 어느 챔버가 의심스럽다"** 까지만 말한다. **"왜 그런지"** 는
말하지 못한다. 2단 깔때기가 붙어야 분석이 완성된다.

현재 `compare_parameter_distribution`(`tools/yield_tools.py:256`)은 옛 `process_log` 스키마
위에서 돌아 실데이터에서 못 쓴다. 이 문서는 그것을 `sensor_log` 위로 재설계한다.

## 1. 결정

| # | 결정 | 근거 |
|---|---|---|
| 1 | 기준선은 **그룹 대조만** (같은 스텝의 타깃 wafer vs 대조군 wafer) | 시간 대조는 별도 Stage. §1.1 |
| 2 | 감사 추적은 **`findings` 에 재-fetch 키** | §5 |
| 3 | **`sensor_cache.db` 를 만들지 않는다** | §3.1 — 데이터가 트레이스가 아니라서 근거가 사라졌다 |
| 4 | 센서 데이터는 **wafer 1장의 구간 통계값** (트레이스 아님) | 사용자 확인 (2026-07-25) |

### 1.1 시간 대조를 분리하는 이유

시간 대조(지목 챔버의 과거 정상 구간과 비교)는 그룹 대조가 못 보는 것을 본다 — 원인이
전 구간에 걸리면(PM·부품 교체) 타깃도 대조군도 같이 영향을 받아 그룹 대조가 조용해진다.
1단의 `no_signal` 과 같은 사각지대다.

그런데 **그 사각지대에는 이미 다른 해법이 후보로 지정돼 있다** — corrections B-3 이 같은
트리거에 "lot 밖 대조군 확장 (b)+(c)" 를 걸어뒀다. 같은 구멍에 두 해법이 있고, 실데이터
없이는 어느 쪽이 나은지 정할 수 없다. 지금 확정하면 데이터 보기 전에 못 박는 것이 된다.

또한 시간 대조는 **"정상 구간" 정의**(Stage 2 에서 겪은 "라벨 없이 정상 판정" 문제의 재현)와
**PM·장비 이벤트 이력**(Phase 2 소관, 사내 데이터 확보가 별건)을 선행 과제로 끌고 들어온다.

**단, `SensorStore.fetch()` 는 시간축 조건을 나중에 받을 수 있는 모양으로 둔다** (§3.2).

## 2. 데이터 계약 — `sensor_log`

**트레이스가 아니다.** wafer 1장이 그 스텝을 진행했을 때의 **구간 통계값**이며, 구간과 통계
종류는 **센서 이름 안에 들어 있다** (사내 FDC 추출물 형태).

```sql
CREATE TABLE sensor_log (
    wafer_id     TEXT NOT NULL,
    process_step TEXT NOT NULL,
    sensor_name  TEXT NOT NULL,   -- 구간·통계 포함: rf_power_steady_avg
    value        REAL NOT NULL,
    tkout_time   TEXT             -- step_history 의 timestamp 와 다른 이름이다
);
```

| wafer_id | process_step | sensor_name | value | tkout_time |
|---|---|---|---|---|
| W2406_02 | Etch | rf_power_steady_avg | 512.3 | 2024-06-15 |
| W2406_02 | Etch | rf_power_steady_std | 4.1 | 2024-06-15 |
| W2406_02 | Etch | pressure_steady_avg | 12.7 | 2024-06-15 |

**이 형태가 주는 이득 하나.** `..._avg` 와 `..._std` 가 각각 **독립된 센서 이름**이므로,
"평균은 같은데 분산만 이동한" 케이스가 자동으로 후보에 오른다. 평균만 보는 설계가 아니다 —
비교 로직이 센서 이름을 해석하지 않고 전부 동등하게 다루기 때문이다.

**분석당 규모.** 지목 스텝 1개 × (타깃+대조군) wafer 수십~수백 × 센서 수백 =
**수천~수만 행.** 트레이스(분석당 수십만~수백만 행)와 자릿수가 다르다.

## 3. 구조

```
1단 commonality              2단 sensor
(스텝, 챔버) 지목  ──▶  SensorStore.fetch(process_step, wafer_ids)
                             ├ local : yield.db 의 sensor_log   (더미)
                             └ http  : 사내 FDC                  (인터페이스 뒤)
                                        ↓
                         compare_sensor_distribution(...)
                                        ↓
                    효과크기 top-K 후보 + 재-fetch 키 + note
```

`tools/sensor_store.py`(가져오기)와 `tools/sensor_compare.py`(집계·비교)로 나눈다. 저장과
계산이 한 파일에 섞이면 가져오는 방식을 바꿀 때 계산까지 흔들린다.

### 3.1 `sensor_cache.db` 를 만들지 않는다

`docs/stages.md` 는 캐시 DB 를 Stage 3 구성요소로 적어뒀다. 그 전제는 **"분석당 수만 행이라
한 번만 어겨도 컨텍스트가 터진다"**, 즉 원본이 트레이스라는 가정이었다. 원본이 wafer 단위
통계값이면 그 근거가 사라진다.

캐시는 **무효화 정책·수명 주기·용량 관리**라는 새 문제를 통째로 데려온다. 지금 그것을 짓는
것은 필요를 확인하기 전에 짓는 것이다. 사내 FDC 조회가 실제로 느린 것이 확인되면 그때
`SensorStore` **뒤에** 붙인다 — 인터페이스는 바뀌지 않는다.

**이 결정으로 Stage 3 은 "서브시스템 신설" 에서 "파일 두 개 + 더미 테이블" 규모로 줄어든다.**
`docs/stages.md` 의 Stage 3 규모 경고도 함께 갱신한다.

### 3.2 `SensorStore` 인터페이스

```python
class SensorStore(Protocol):
    def fetch(self, process_step: str, wafer_ids: list[str]) -> list[dict]:
        """지목된 스텝에서 주어진 wafer 들의 센서 통계값 전부.

        반환 원소: {wafer_id, process_step, sensor_name, value, tkout_time}
        """
```

EDS(`tools/eds_search.py`)와 같은 패턴이다 — `get_store()` + `config.SENSOR_MODE`("local"/"http")로
구현을 바꿔 끼운다. 새 개념을 만들지 않고 저장소에 이미 있는 모양을 따른다.

시간 대조가 붙을 때는 `fetch(process_step, wafer_ids=None, time_range=...)` 처럼 **인자만
늘어난다** — 호출부 계약이 깨지지 않도록 wafer 목록을 선택 인자로 받을 여지를 남긴다.

## 4. fetch·반환 계약 (기확정 — 그대로 이관)

1. **fetch 단위는 (지목된 스텝 × 타깃+대조군 전원).** 챔버 단위로 당기면 안 된다 — 1단이 그
   챔버를 지목한 근거가 "대조군은 안 거쳤다"(score=1.0 이면 control_pass=0)이므로, 지목된
   챔버만 뽑으면 대조군 표본이 0 이라 비교 자체가 성립하지 않는다.
2. **tool 반환은 집계값만.** wafer 별 원본값을 `ToolMessage` 에 싣지 않는다. 반환은
   **효과크기 top-K 로 절단**해 fetch 량과 무관하게 유계로 만든다 (commonality 의
   `top_k`·`truncated` 와 같은 구조).
3. **출력은 후보이지 결론이 아니다.** p-value 컷이 아니라 **효과크기 랭킹**을 쓴다. 스텝당
   센서가 수백 개라 α=0.05 면 우연히 수십 개가 유의하다. 이 사실을 결과 `note` 에 명시한다.

효과크기는 표준화 평균차(Cohen's d)를 쓴다. 두 그룹의 표본이 작을 때 값이 커지므로,
commonality 와 같이 **원시 카운트(각 그룹 표본 수)를 함께 실어** 해석자가 판단하게 한다.

---

## 5. 감사 추적 — 재-fetch 키

반환이 집계값만이면 `findings` 에도 집계값만 남아, 리포트의 "효과크기 3.6" 이 어디서 나왔는지
나중에 재현할 수 없다. 결과에 **그 숫자를 다시 만드는 데 필요한 키**를 함께 싣는다.

```python
"refetch_key": {
    "process_step": "Etch",
    "target_wafers": [...],
    "control_wafers": [...],
    "sensors": [...],          # 반환된 top-K 후보의 센서 이름
    "store_mode": "local",     # config.SENSOR_MODE
}
```

**한계를 명시한다:** 원본(사내 FDC)이 삭제·변경된 뒤에는 재현할 수 없다. 이 설계는 원본이
살아있는 동안의 재현을 보장하며, 원본 보존은 이 시스템의 범위 밖이다.

## 6. 더미 `sensor_log` — 심을 케이스 4종

Stage A 의 적대적 더미와 같은 정신이다. 케이스는 사용자가 선택했다.

| # | 케이스 | 심는 방법 | 시험하는 것 |
|---|---|---|---|
| 1 | **분산만 이동** | 타깃의 `..._avg` 는 대조군과 같고 `..._std` 만 이동 | 평균 중심 사고의 사각지대. §2 의 "이름이 독립 센서" 성질이 실제로 잡아내는지 |
| 2 | **미끼 센서** | 원인과 무관한 센서 몇 개가 우연히 큰 효과크기 | 계약 3(후보≠결론)과 top-K 절단이 의미 있는지. 진짜가 1위를 지키는지 |
| 3 | **공선성** | 연동된 센서 여럿이 함께 이동 (압력↔유량 같은) | 순위만으로는 무엇이 원인인지 못 가리는 상황이 드러나는지 |
| 4 | **센서 결측 / 2단 조용함** | 일부 wafer·센서가 비어 있고, 1단이 지목한 챔버가 센서로는 설명 안 되는 케이스 | 결측이 분모를 오염시키지 않는지, "모른다" 를 정직하게 보고하는지 |

**제약은 Stage A·2 와 같다:** 기존 wafer·기존 난수열 불변, 신규 데이터는 뒤에 붙인다.
`sensor_log` 는 신규 테이블이므로 기존 테이블은 건드리지 않는다.

**공선성 판별(어느 센서가 진짜 원인인지 가리기)은 이 문서 범위 밖이다.** 케이스 3 은 그
상황이 **드러나는지**만 시험한다 — 해결은 도메인 지식이나 시간축이 필요하다.

## 7. 실패 처리

fetch 실패·데이터 없음은 **조기 출구를 만들지 않고 tool 이 `status` 로 정직 보고**한다.
`no_signal`·`control_insufficient` 와 같은 관례다. LLM 이 그 상태를 읽고 다음 행동을 정한다.

| status | 뜻 |
|---|---|
| `ok` | 후보 있음 |
| `no_signal` | 계산은 됐으나 분리되는 센서가 없음 — 1단이 지목한 챔버가 센서로는 설명되지 않는다 |
| `insufficient_sample` | 한쪽 그룹의 센서 표본이 비교에 못 미침 |
| `fetch_failed` | 원본 조회 실패 — 결과 없음과 구분한다 |

## 8. 범위 밖

- **시간 대조** (§1.1) — 별도 Stage
- **PM·장비 이벤트 이력** — Phase 2
- **공선성 판별** — 케이스 3 은 드러내기만 한다
- **다인성(병렬 원인) 표현** — 게이트·리포트 설계가 별건
- **`sensor_cache.db`** (§3.1) — 필요가 확인되면 `SensorStore` 뒤에 붙인다
- **레지스트리 편입** — `hypotheses.yaml` 은 "어느 축(legend)으로 commonality 를 돌릴지" 를
  선언하는 모델이다. 센서 비교는 계산 자체가 달라 legend 로 표현되지 않는다. 억지로 넣으면
  레지스트리가 "가설 선언" 이 아니라 "아무 tool 이나 등록하는 곳" 이 된다. 별도 tool 로 둔다.
- `compare_parameter_distribution`(옛 `process_log` 기반) **삭제는 Stage 5** — 여기서는 손대지 않는다

## 9. 완료 기준

1. 1단이 지목한 스텝에 대해 2단이 효과크기 top-K 후보를 낸다.
2. 반환에 wafer 별 원본값이 없고, 크기가 fetch 량과 무관하게 유계다.
3. `findings` 의 재-fetch 키만으로 같은 집계값을 다시 만들 수 있다.
4. 더미 케이스 4종이 의도대로 동작한다 — 특히 **분산만 이동**이 후보에 오르고,
   **2단 조용함**이 `no_signal` 로 정직하게 보고된다.
5. `SENSOR_MODE=http` 로 바꿔도 호출부 코드가 그대로다.
6. 전체 회귀 green (기준선 140 + 신규).
