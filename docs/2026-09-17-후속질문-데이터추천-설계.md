# 근거에 연결된 후속 질문·데이터 추천

작성: 2026-09-17. 사용자 요청: 멀티에이전트 설계에 이어 질문·데이터 추천을 진행한다.
상태: **설계 완료, 구현 미착수.** 이번 범위는 앞서 제안한 병행 문서 설계다.
pooling 구현 중인 제품 코드·테스트·계획은 수정하지 않는다.

선행: [F 설계 §5.1](2026-09-17-F-설계정리.md),
[탐색기 방향 논의](2026-08-22-agent-direction-review.md).
기준은 F 조사 시점 HEAD `d1a07dc06af759b1233206de5485c5148be0b996`와 현재 코드의 아래
심볼이다. pooling 완료 후 최종 커밋으로 재대조한다. 사내 데이터·LLM 평가는 실행하지 않았다.

## 1. 목표와 결과물

분석 결과마다 사람이 다음에 물을 **구체적인 질문**, 이를 확인하는 **필요 데이터와 비교 조건**,
현재 가능한 **실행 경로**를 함께 제시한다. 추천은 확정된 원인이거나 새 측정 결과가 아니다.
멀티에이전트 구축은 확정된 목표이며 추천 기능의 비용 우위 입증을 착수 조건으로 두지 않는다.

최초 기능은 분석 종료 뒤 만드는 독립 추천 목록이다. 추천 생성 때문에 분석을 다시 열거나
도구를 자동 실행하지 않는다. F 워커가 나중에 같은 목록을 읽어 후속 행동을 제안할 수 있도록
계약을 공유한다. 추천 구현은 F 전체 워커 완성을 기다릴 필요가 없다.

첫 범위는 교락 해소·표본/비교 가능성 확인·미실행 도구·실패 복구·센서 후속 조회다.
새로운 조건부 통계 도구, 자동 SQL 실행, 새로운 타깃/대조군 선정, 원인 확정, 데이터 구매나
외부 의뢰 실행, 필요한 표본 수/실험 비용의 임의 계산은 포함하지 않는다.

## 3. 책임 분리와 데이터 흐름

```text
최신 findings + Bundle + coverage + 실제 도구 목록
  → 코드: 추천 근거와 허용되는 질문 유형 수집
  → 템플릿 초안 + 선택적인 LLM 질문 구체화
  → 코드: 출처·유형·식별자·도구 인자·상태 검증
  → followup_proposals (Claim과 별도)
  → 코드가 렌더링하는 [후속 질문·필요 데이터]
```

코드는 사실과 제약을 제공하고 LLM은 질문과 조건부 해석을 제안한다. LLM은 `passes`,
순위, coverage, 실행 가능 상태, 데이터 확보 상태를 결정하지 못한다. 검증은 제안의 모든
과학적 타당성을 보증하지 않으므로 검증된 출처와 아직 검증되지 않은 해석을 구분해 표시한다.

최초 구현은 사유별 템플릿으로 끝까지 동작하게 한다. LLM 구체화 실패·스키마 오류가 나도
검증된 템플릿 추천과 기존 리포트를 보존한다. 자유 생성만 가능한 제안은 실패 시 제외하고
누락 사실을 기록한다. 추천 0건이면 원인을 꾸며 채우지 않는다.

## 4. 추천 레코드 계약

각 레코드는 `schema_version`, `proposal_id`, `audit_revision`을 갖는다. 수치·식별자에는
원본 출처를 유지한다. 출력은 `proposals`, `omitted_count`, `generation_status`,
`validation_issues`를 포함한 묶음으로 반환한다.

| 필드 | 의미와 소유자 |
|---|---|
| `reason_code` | 코드가 고른 추천 사유: confounded, thin_sample, reference_resolution, missing_data, unrun_axis, tool_failure, sensor_followup 등 |
| `source_refs` | 코드 발급 참조. claim 또는 실행 기록 또는 등록 도구 목록/coverage의 특정 항목 |
| `observations` | 코드가 원본에서 뽑은 사실. 후보 상태·현재 표본 수 등. LLM 수정 금지 |
| `question` | 확인할 질문 1개. 없는 사실을 전제로 쓰지 않음 |
| `competing_explanations` | 구별하고 싶은 설명의 참조. 경쟁 설명이 없는 데이터 복구 질문은 빈 목록 |
| `required_data` | 아래 데이터 요청 계약. 실제 보유 여부와 필요성을 구분 |
| `expected_discrimination` | 어떤 결과가 어느 설명을 더 검토하게 하는지. 조건부 제안이며 원인 확정/효과 방향의 사실 주장 금지 |
| `action` | 후보 도구명과 허용된 비주입 인자 또는 사람이 할 일. 실행기가 최종 검증 |
| `capability_status` | 코드: available_tool / needs_new_tool / manual_check / unknown |
| `data_status` | 코드: observed_available / known_missing / unknown. 실제 검사한 범위와 출처를 동반 |
| `blockers` | 도구 부재·설정 off·데이터 미확인·장애·출처 만료 등. 동시에 여러 개 가능 |
| `proposal_status` | proposed / stale / invalid. proposed는 실행됐다는 뜻이 아님 |
| `origin` | template / llm_refined. 의미적 해석은 여전히 제안임을 표시 |

`required_data`의 최소 내용:

- **대상 범위:** 현재 실행의 타깃/대조군 참조, 공정 step_seq, 필요하면 root_lot 범위.
- **관측 단위와 항목:** wafer×step 등 단위와 실제 알려진 필드 또는 “원천 확인 필요”인 개념.
  존재하지 않는 테이블명·컬럼명을 확정적으로 발급하지 않는다.
- **비교 조건:** 고정할 조건과 바꿔 볼 조건. 누가 어떤 wafer를 제외할지는 아직 실행 제안이다.
- **짝맞춤/결측 확인:** 그룹 양쪽 관측 가능성, 이력·센서의 시점/반복 측정 처리 확인 사항.
- **충분성의 한계:** 현재 판정 하한과 통계적 충분성을 구분. “하한까지 N장만 모으면 확정” 금지.
- **획득 경로:** 기존 도구, 원천 추출 확인, 새 도구 구현 등. 담당자·비용·기한은 모르면 unknown.

도구와 데이터는 독립된 두 축이다. 예를 들어 센서 도구는 등록됐지만 해당 스텝의 관측은
미확인일 수 있고, 데이터가 없으면서 조건부 비교 도구도 없을 수 있다. F 초안의 단일
`execution_status`는 이 계약으로 구체화한다. `available_tool`은 성공이나 데이터 확보의 보증이 아니다.

### 4.1 출처와 수명

F 실행 ID가 있으면 `(dispatch_id, call_id)`를 참조한다. 아직 없는 단일 에이전트 경로에서는
동결된 감사 스냅샷의 `(audit_revision, finding_index)`를 사용한다. snapshot revision은
실행기 생성 UUID 등으로 식별하며 다른 실행의 index를 섞지 않는다.
claim 참조는 claim_id뿐 아니라 **그 후보의 현재 원본 실행 참조**를 포함한다.
같은 claim_id가 재실행으로 유지돼도 이전 수치로 만든 추천을 그대로 재사용하지 않는다.

추천은 해당 snapshot에만 유효하다. 새 결과가 병합되면 현재성 재검증 후 재생성하고,
이전 추천은 stale로 표시한다. 폐기된 후보·조작된 참조는 표시 목록에서 제외한다.
후보가 없는 실패/no_data/unrun 추천은 실행 기록 또는 coverage 참조로 성립할 수 있다.

## 5. 사유별 추천 규칙

| 코드가 관측한 사유 | 질문/필요 데이터 | 주의할 경계 |
|---|---|---|
| 서로 다른 설명이 confounded_with로 묶임 | 같은 챔버·다른 PPID 또는 같은 PPID·다른 챔버의 비교 가능한 이력이 있는가? wafer/step/root_lot 및 구조화된 해당 식별자와 수율 | 실제 칼럼값이 있는 쌍에서만 구체화. 비교군 존재·원인 인과성을 단정하지 않음 |
| rolled_up_as만 있음 | 기본적으로 경쟁 설명 추천을 만들지 않음 | 설비와 그 챔버를 독립 원인 두 개로 세지 않음 |
| thin_sample 후보 | 같은 비교 구조를 유지한 타깃 표본을 추가 확보할 수 있는가? 현재 관련 타깃 수와 결측/대조 짝 | 최소 하한 충족이 충분한 검정력이라는 주장 금지 |
| 해상도/귀무 참조 부족 | 참조 회차 부족이 관측 가능한 배치 한계인지 실행 회차/조건화 때문인지 먼저 확인 | n_reference와 n_permutations_total 두 숫자만으로 원인을 확정하지 않음. 실행 설정·전수/표본 모드·유효 참조 정보를 확인 |
| cross_axis 동점 | 두 후보를 직접 구별하는 비교 조건/데이터가 있는가? | p가 같은 이유만으로 어느 쪽을 우선 원인으로 추천하지 않음 |
| sensor_correlated | 센서가 함께 변하는지 원본 시계열·측정 시점·공통 운전 조건을 확인할 수 있는가? | top-K 평균/표준편차만으로 상관이나 분포 모양을 판정하지 않음 |
| no_data 또는 missing meta | 양쪽 그룹에 필요한 이력/계측이 존재하는가? 조인 키·추출 범위·해당 step 관측 확인 | 데이터가 없음을 무신호로 해석하지 않음. 원천에도 없다는 주장 금지 |
| failed 또는 센서 fetch_failed | 서비스/적재/인자 상태를 먼저 복구할 수 있는가? 실제 오류와 요청 범위 | 예외 표시와 dict 실패 status를 모두 확인. 단순 반복 조회 권고 금지 |
| 등록 hyp 도구가 unrun | 현재 그룹으로 그 축을 비교해 볼 것인가? | 전축 실행 의무나 결과 개선 보장 없음 |
| 실제 경로 후보 step에 센서 미조회 | 그 step의 센서 분포에서 추가 차이가 있는가? 현재 고정 그룹·실제 step_seq | 센서 off면 실행 가능으로 표시하지 않음. 센서 후보는 원인 확정 지목 대상이 아님 |

약한 후보라는 이유만으로 일괄 “표본 확대”를 추천하지 않는다. 분리 약화·표본 미달·참조
해상도·데이터 누락을 각각 원본 사유로 구분한다. 사유를 못 가리면 “먼저 확인할 것”을 낸다.
센서의 refetch_key는 데이터 담당자가 재조회 범위를 아는 재료일 뿐, 원본 조회 API가 연결됐다는
증거가 아니다. 기존 도구 스키마에 없는 원본/필터 요청은 needs_new_tool 또는 manual_check다.

## 6. 실행 가능 여부 검증

`available_tool`로 표시하려면 모두 충족해야 한다.

1. 현재 등록 목록에 도구가 있고, 질문에 요구되는 기능이 도구 스키마와 명시적 기능 정의에 있다.
2. 필수 비주입 인자를 현재 근거에서 구성할 수 있다. step_seq/wafer 식별자를 지어내지 않는다.
3. group_ids/control_ids는 추천이 소유하지 않으며 기존 고정 그룹을 실행기가 주입한다.
4. 동일 데이터·인자로 이미 얻은 답을 새 조사인 것처럼 제안하지 않는다. 장애 복구 후 재시도는
   복구가 선행 조건임을 명시한다.

도구명만 LLM이 고르는 것으로 충분하지 않다. 초기 기능 정의는 기존 등록 도구에 대해 작은
명시적 매핑으로 작성하고 등록 여부·인자 검증과 함께 사용한다. 미래 도구를 기능 정의에
추가하지 않으면 unknown으로 처리한다. finalize와 워커 제어 도구는 조사 도구 후보에서 제외한다.

조건부 비교를 지원하지 않는 hyp 도구에 새로운 필터를 몰래 추가하지 않는다. 해당 질문은
needs_new_tool이고 필요한 데이터도 unknown일 수 있다. 데이터 확보 후의 재분석은 별도 실행으로
기존 run과 연결한다. 이번 기능은 자동 실행·그룹 변경·현장 제어를 하지 않는다.

## 7. 정렬과 출력

코드가 다음 순서로 정리한다: (1) 비교를 막는 데이터/실행 장애의 확인,
(2) 실제 경쟁 설명을 구별할 질문, (3) 표본·참조 해상도 확인, (4) 아직 안 본 보완 축.
이는 **행동의 표시 순서**이며 원인 가능성이나 통계적 정보 이득 순위가 아니다.
동일 범주에서는 기존 근거 순서와 안정된 ID를 사용하고 LLM confidence로 정렬하지 않는다.

초기 출력 기본값은 3건(설정 가능)이며 초과 건수와 전체 구조화 목록을 보존한다. 중복은
사유·출처 집합·정규화된 action/비교 조건으로 접는다. 질문 문장의 유사도만으로 서로 다른
조사를 합치지 않는다. 관련 장애와 후속 비교가 함께 있으면 blocker 관계로 연결한다.
리포트의 근거 상한과 추천 상한은 독립이며, 추천이 기존 근거를 밀어내지 않는다.

각 항목은 **질문 / 현재 근거 / 필요한 데이터 / 실행 상태 / 확인 후 구분할 것**으로 표시한다.
후보 관계는 전체 bundle에서 읽으므로 기존 리포트 상한 밖 후보를 인용한다면 그 사실과
최소 식별 정보를 추천에 함께 싣는다. 관련 근거를 읽을 수 없는 포인터만 내보내지 않는다.

### 출력 예시 — 실제 실행 결과가 아닌 형식 예시

> **질문:** 현재 챔버 후보와 PPID 후보를 구별할 비교 이력이 있습니까?
>
> **현재 근거:** 두 후보가 같은 wafer 집합을 가리켜 현재 결과만으로는 설명을 구별하기 어렵습니다.
>
> **필요 데이터:** 해당 step에서 동일 챔버·다른 PPID 또는 동일 PPID·다른 챔버인 이력,
> wafer/root_lot 식별자와 수율. 비교 가능한 타깃·대조 관측이 있는지 먼저 확인합니다.
>
> **실행 상태:** 조건부 비교 도구 추가 필요. 해당 비교 이력의 보유 여부는 미확인입니다.
>
> **확인 후:** 비교 조건을 고정해도 차이가 남는지 검토할 수 있습니다. 차이가 남는 것만으로
> 원인이 확정되는 것은 아닙니다.

## 8. F와 리포트 연결

공통 추천기는 전체 최신 evidence snapshot을 읽는다. 특정 워커가 자기가 본 결과만으로
축 간 비교나 전체 unrun을 단정하지 않도록, 출처·실행 가능 검증은 부모에서 수행한다.
워커가 제안한 초안도 동일 검증을 거친다. F의 마무리 단계는 finalize 전용이므로 추천을
실행하려고 탐색을 다시 열지 않는다. 다음 분석에 넘길 제안으로 남긴다.

향후 구현 파일 경계(제안):

- `domain/followups.py`: 읽기 전용 snapshot 기반 추천 생성·검증. 그래프 전역 state에 쓰지 않음.
- `graph/state.py`: 별도 `followup_proposals` 출력. findings/Claim으로 섞지 않음.
- `graph/nodes.py`: 최종 근거 확정 뒤 추천 생성 및 별도 블록 렌더링 연결.
- `llm/client.py`: 선택적인 질문 구체화 인터페이스. 기존 산문 리포트와 추천 블록의 책임 분리.
- `tests/test_followups.py`: 사유/출처/실행 가능/비간섭 검증. 리포트 연결 테스트는 기존 테스트에 추가.

최초 연결은 기존 산문 생성 결과 뒤에 코드 렌더링 추천 블록을 붙인다. 산문 LLM에 추천을
중복 작성하게 하지 않는다. 산문 생성 실패에도 코드 추천 블록은 남는다. 추천 모듈이 실패해도
기존 판정·근거·리포트는 남고 “추천 생성 실패”만 따로 기록한다.
위 파일 일부는 pooling/F와 겹치므로 현재 동시에 수정하지 않는다. 구현 plan에서 최종 기준선,
owner, 순서와 리뷰 범위를 고정한다. 문서상의 파일 제안은 현재 변경 완료를 뜻하지 않는다.

## 9. 수용 기준

| ID | 잠글 내용 |
|---|---|
| Q1 | 동일 집합의 서로 다른 설명에만 비교 질문 생성. rolled_up_as만 있는 쌍과 부분 겹침을 동일 교락으로 오인하지 않음 |
| Q2 | thin_sample/약한 후보/참조 해상도/no_data/실패/unrun의 질문 구분. 모르는 원인은 미확인 표시 |
| Q3 | 후보 없는 장애·미실행 축에도 실행/coverage 출처가 있고, 없는 후보를 만들어 붙이지 않음 |
| Q4 | 같은 claim_id가 재실행된 경우 snapshot/원본 실행 변경으로 이전 추천 만료 |
| Q5 | 등록 도구·스키마·기능·센서 off·조건부 필터·원본 조회 부재를 검증. 도구 가능성과 데이터 보유를 독립 표시 |
| Q6 | 추천 전후 입력 findings/Bundle/그룹/최종 판정·근거·coverage 동일. 외부 도구 호출 0회 |
| Q7 | LLM의 조작된 참조·식별자·수치·도구 인자/상태를 거부하고 템플릿 fallback |
| Q8 | 평균·표준편차로 분포 형태를 단정하거나 표본 하한 충족을 통계적 충분성으로 표현하지 않음 |
| Q9 | 안정된 순서·중복 처리·상한과 초과 건수. 기존 근거 상한의 절단과 독립 |
| Q10 | 추천/산문 LLM의 각각 실패에도 기존 판정과 코드 근거 보존. 추천 미생성과 추천 없음 구분 |
| Q11 | 최초 단일 에이전트 snapshot과 F 실행 참조를 모두 지원. 원본 ID를 문자열 파싱하지 않음 |
| Q12 | pooling 상세는 그대로 인용하고 score_pooled로 추천 대상의 기존 판정/순위를 뒤집지 않음 |

Q1~Q12는 향후 구현 검증 항목이며 이번 문서 작업에서 실행한 제품 테스트가 아니다.
사내 평가는 출처 정확성, 질문 구체성, 필요한 데이터의 명확성, 실행 상태의 정직성,
동일 조회 반복 여부를 본다. “새로운 질문을 많이 생성했다”만으로 성공으로 세지 않는다.

## 10. 구현 순서

1. pooling 완료 코드로 사실/인터페이스 재확인 후 구현 plan 작성. 첫 추천 범위를 위 규칙으로 고정.
2. snapshot 어댑터·결정론적 추천 템플릿·출처/실행 가능 검증과 Q1~Q9/Q11~Q12 구현.
3. 별도 리포트 블록과 실패 fallback 연결, Q10 및 기존 리포트 회귀 검증.
4. 선택적 LLM 구체화와 사내 출력 사례 평가. 도입 필요성이나 비용 우위 심사는 하지 않음.
5. F 워커 초안의 부모 검증 연결. 새 조건부 도구는 별도 질문·통계 계약으로 확장.

설계상의 선택은 정리됐고 다음 산출물은 구현용 plan이다. 사내 데이터의 실제 보유 범위와
담당 부서/획득 시간은 현시점에 모르므로 unknown을 정상값으로 유지한다.
