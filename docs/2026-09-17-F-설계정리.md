## 1. 이번에 정리한 범위

F의 목적은 축별로 도구 결과를 잘 해석하고 필요한 후속 조회를 선택하게 하는 것이다.
워커는 도구 실행 기록과 해석을 반환하며, 최종 판정은 기존 코드가 수행한다.

목표 구성은 메인 오케스트레이터와 경로·분포·EDS 워커다. 첫 구현 단계는
**순차 실행·경로 워커 1개·분석 그룹 고정**이다. 이는 통합 계약을 먼저 검증하는 순서다. 동시성은 별도
확인 뒤 검토한다. 분포 형태 분류, 새로운 grain/필터 인자, 타깃 재선정, metro pooling,
판별 임계 조정은 F 첫 단계에 넣지 않는다. 자유 해석 노트도 첫 단계의 필수 조건에서 뺀다.

이번에 수정하는 것은 F 문서뿐이다. Claude 소유 pooling 코드·테스트·계획은 수정하지 않는다.
이 문서는 구현 위임용 `plan.md`가 아니다. 구현 단계별 ownership과 실행 가능한 완료 기준은
아래 계약을 바탕으로 별도 `docs/tasks/<task>/plan.md`에 작성한다. 사내 오독 평가 전에도
로컬 구현·계약 테스트를 진행할 수 있다.

## 2. 코드에서 확인한 사실과 기존 조사 정정

| 확인한 코드 | 현재 사실 | F에 주는 제약 |
|---|---|---|
| `domain/registry.py::build_tools` | `_run`은 고정 spec과 주입 그룹으로 `engine.evaluate`를 호출한다. grain/필터를 선택하는 명시적 탐색 인자가 없다 | 같은 도구를 reason만 바꿔 반복해도 새로운 질문이 되지 않는다 |
| `graph/state.py::AgentState` | findings는 `operator.add`로 누적된다 | 전체 기록을 다시 반환하면 중복 누적된다 |
| `graph/nodes.py::tools_node` | 그룹 주입, 오류 분류, ToolMessage, 감사 기록을 함께 만든다 | 워커가 도구를 직접 invoke하면 이 계약을 우회한다 |
| `graph/nodes.py::_with_pipeline_groups` | 코드가 그룹을 덮어쓰며, 그룹 state 누락은 RuntimeError다 | 누락을 빈 그룹/no_data로 바꾸면 안 된다 |
| `graph/evidence.py::build_bundle` | 리스트 순서로 가설 도구 재실행을 처리한다. 실패 뒤 성공은 `crashed - ran`으로 실패 집계에서 빠진다 | 병합 시 시간 문자열 정렬·결과 요약·실패 표식 재해석을 하지 않는다 |
| `graph/nodes.py::_coverage` | 등록 `hyp_*` 도구 단위로 집계한다 | 워커 완료와 축 실행 완료는 다르다 |
| `llm/client.py::OpenAILLMClient` | analyzer가 ALL_TOOLS를 바인딩한다 | 프롬프트만으로 워커 도구 권한을 제한할 수 없다 |
| `graph/nodes.py::analyze_node`, `graph/build.py` | 분석 호출마다 loop_count 증가, MAX_LOOPS로 종료한다 | 워커 내부 호출에 별도 무제한 예산을 주면 기존 한계를 우회한다 |

기존 준비 문서의 다음 표현은 수정해서 읽는다.

- **“grain을 바꾸며 재확인”은 현재 기능이 아니다.** equipment/chamber 등의 legend는
  spec에 고정돼 있다. 질문을 바꾸는 기능은 별도 설계가 필요하다. 현재 F에서 먼저 검증할
  이득은 해석 품질과 기존 도구 사이의 후속 선택이다.
- `p_permutation`과 `p_min_possible`은 공통 **효과 크기**가 아니다. 코드가 축 간 우열을
  판정할 때 사용하는 통계 정보다. 기존 `dominates`와 `ranked_groups`를 재사용한다.
- EDS 워커의 조회가 분석 타깃을 자동으로 바꾸어서는 안 된다. `status_node`가 확정한
  그룹과 이후 후보의 분모는 동일해야 한다. 재선정은 별도 분석 실행의 입력이다.
- 분포 형태와 해석 노트는 F의 필수 신규 기능으로 확정되지 않았다. 분포 형태는 원자료와
  별도 검증이 필요한 도구 기능이고, 노트는 이후 독립적으로 추가할 수 있다.
- 클라이언트를 나누면 생성되는 Msg-Id는 달라지지만, 게이트웨이 규약 충족이나 동시 호출
  안전이 입증되는 것은 아니다. 요청별 ID/재시도 처리 규약은 사내 확인이 필요하다.
- 기존 방향 문서의 **미설명 이상**과 현재 `residuals()`의 **판별선 아래 약한 후보**는
  다른 개념이다. 약한 후보 출력이 있다고 미지의 이상 탐색이 완성됐다고 표현하지 않는다.
- 여러 축이 동일 wafer를 가리킨다는 사실만으로 증거 강도를 올리지 않는다. 현재 코드의
  집합 동일성 접기와 교락/포함관계 표시는 유지하며, 서로 다른 설명을 가를 질문의 입력으로 쓴다.

## 3. 첫 단계의 경계

| 담당 | 허용 도구/권한 | 반환 |
|---|---|---|
| 경로 워커 | 실제 등록된 EQP_CH·PPID·step_passage 가설 도구 | 실제 실행 findings의 증분, 워커 종료 사유 |
| 메인 | 기존 나머지 분석 도구, 워커 호출, finalize 제안. 워커 인계 시 해당 도구 권한 회수 | 기존 게이트에 제출할 지목 및 서술 |
| 공통 실행기 | 허용 목록 검증, 그룹 주입, 도구 실행, 오류 분류, 감사 기록 | 대응 ToolMessage와 finding |
| 기존 게이트/리포트 | 전체 findings에서 재계산 | 기존 종료 상태·근거·커버리지 |

워커 실행 중 메인은 같은 도구를 실행하지 않는다. 워커 종료 후 메인이 이어받아
재실행할 수는 있으며, 그때도 기존 findings 뒤에 누적하고 기존 대체 규칙을 적용한다.
워커는 `finalize`, `finalize_status`, `final_claims`, `coverage`, 그룹 state를 쓰지 못한다.
`done`은 워커 제어 신호이며 분석 종료나 `no_signal` 판정이 아니다.

후속 분포 워커는 metro와 활성화된 센서 도구만 받는다. 센서 조회에 필요한 step_seq는
경로 결과 등 실제 근거에서 전달한다. `SENSOR_MODE=off`이면 노출/실행 양쪽에서 제외한다.
EDS 워커는 조회 전용 후보이며 타깃 변경 권한을 갖지 않는다. 첫 단계에서는 둘 다 만들지 않는다.

## 4. 감사 기록 병합 계약

### 4.1 실행과 출처

향후 구현에서는 `tools_node`의 일반 도구 실행 부분을 공통 실행 경로로 추출한다.
메인과 워커가 같은 그룹 주입·오류 분류를 사용해야 한다. finalize 분기는 메인에 남긴다.
실행 전에 코드의 allowlist를 검사하고, 워커의 도구 바인딩도 같은 목록으로 제한한다.
목록 밖 호출은 실행하지 않고 오류 응답을 남기며 등록 축 실패로 계산하지 않는다.

기존 finding 필드는 그대로 유지한다.

```text
{loop, tool, args, result, thought, failed?}
```

`args`는 주입 후 실제 실행 인자, `result`는 도구 반환값 그대로다. LLM이 findings를
작성하거나 요약한 JSON을 그 자리에 넣지 않는다. 추가 후보 키도 필터링하지 않는다.
pooling의 `n_strata`, `score_pooled`, `strata_detail`을 포함한 도구 결과가 그대로 전달돼야 한다.

신규 워커 도구 기록에는 `worker_id`, `worker_turn`, `dispatch_id`, `call_id`를 **필수**로 둔다.
실행기가 부여하며 `(dispatch_id, call_id)`를 해당 분석 실행 내 병합 식별자로 사용한다.
`call_id`는 모델이 보낸 ID를 그대로 신뢰하지 않고 실행기가 발급한다. 모델의 요청 ID는
별도 `tool_call_id`로 보존해 ToolMessage 대응에 사용한다. 워커 제어 사건은 별도의 event ID를
사용한다. 기존 워커 외 기록은 새 필드 없이 읽을 수 있어야 한다.
외부 저장소 재시작까지 보장하는 스키마는 아니다.

### 4.2 순서와 중복

1. 첫 단계는 워커 1개를 순차 실행한다. 한 메시지의 도구 호출은 제시된 순서대로 처리한다.
2. 실행 결과마다 부모 findings에 증분을 한 번만 추가한다. 워커는 부모 전체 목록을 반환하지 않는다.
3. 워커 중간 실패에도 이미 실행된 도구 기록은 부모에 남아야 한다. 완료 때까지 지역 변수에만
   보관했다가 실패 시 통째로 잃는 실행 형태는 허용하지 않는다.
4. 동일 dispatch/call 결과의 재전달은 중복 추가하지 않는다. 새로운 call ID로 실제 재실행한
   결과는 별도 기록이다. result 내용이 같다는 이유로 제거하지 않는다.
5. 구현 첫 단계에서는 자동 워커 재시도와 재시작 복구를 제공하지 않는다. 도입하려면
   중복 실행/중복 병합과 체크포인트 경계를 별도로 설계한다.
6. `superseded`는 병합기가 만들지 않는다. `build_bundle`의 기존 결과를 리포트 사본에만 적용한다.

부모 오케스트레이터만 findings를 추가한다. 워커는 도구 결과 사건을 부모에 전달하고,
부모는 해당 식별자의 미반영 여부를 확인해 findings와 반영 장부를 같은 상태 갱신에서
기록한 뒤 다음 워커 턴을 허용한다. 이미 반영된 ID의 동일 payload는 무시하고,
같은 ID에 다른 payload가 오면 계약 오류로 중단한다. 워커 완료 응답에서 결과를 다시 붙이지 않는다.
워커 전체를 한 번의 불투명한 함수 호출로 감싸지 않고, 도구 결과 반영을 부모의 실행 단계로
노출한다. reducer는 일반 목록 덧셈을 유지하되 중복 검사는 그 앞에서 수행한다.

실행 후 병합 실패가 발생하면 해당 dispatch를 자동 재실행하지 않는다. 실행된 결과와 오류를
보존해 중단 사실을 남기는 경로가 필요하다. 프로세스 강제 종료까지 기록을 보장하는 영속화는
첫 단계 범위 밖이며, 이를 exactly-once 실행 보장이라고 부르지 않는다.

### 4.3 loop와 예산

호출 제한은 비용 절약보다 무한 반복과 장시간 정체를 막기 위한 실행 가드레일이다.
기존의 `MAX_LOOPS=7`을 멀티에이전트 전체에 그대로 적용하지 않는다.
F에서는 탐색 호출 상한과 **메인 최종 판단용 예약 호출 2회**를 분리한다.
예약 2회는 초기 설계 기본값으로, 종료 제안 1회와 반려 피드백 반영 1회를 확보한다.
워커와 일반 탐색은 예약분을 소비할 수 없다. 정상적인 조기 finalize는 언제든 가능하다.

탐색 상한 또는 워커 상한에 닿으면 완료된 결과를 먼저 병합한다. 워커 상한만 닿았고 전체
탐색 여유가 있으면 메인이 인계받거나 다른 워커로 이동한다. 전체 탐색 상한에 닿으면
메인에게 §5의 최신 근거를 전달하고 마무리 단계로 전환한다. 이 단계는 finalize만 노출하며
새 조회·워커 호출을 실행하지 않는다. 첫 반려 뒤에는 피드백을 포함해 남은 예약 회차를 쓴다.
무호출·예약 소진이면 기존 게이트리스 판정으로 끝내고, 메인 LLM 실패는 기존 실패 종료로 보낸다.
예약은 정상 반환 가능한 호출 기회를 뜻하며 서비스 장애나 강제 취소에도 실행 성공을 보장하지 않는다.

감사용 `loop`는 메인·워커 분석 호출의 전역 순번이다. 실행기가 증가시키며 `worker_turn`은
워커 내부 순번이다. 별도의 `exploration_calls_used`, `closing_calls_used`와 종료 단계로
예산을 판단한다. **감사 순번이 7에 닿았다는 이유로 게이트 한계 분기를 켜면 안 된다.**
향후 구현에서 `_gate_verdict`, `_drop_unapprovable_pick`, `_gateless_finalize`와 그래프 라우팅의
한계 판단을 명시적 종료 문맥으로 연결한다. 후보 승인·순위·잔차 판정 규칙은 보존한다.
마지막 마무리 회차에는 기존 한계 시 판정 규칙을 적용한다.
종료 문구도 `exploration_limit`, `closing_limit`, `no_tool_response`, `llm_failure` 등 실제
트리거를 받아 만들며, loop 숫자로 “도구 호출 없는 응답”을 추측하는 기존 방식은 확장한다.

구현 plan에서 전체 탐색·워커 턴·도구 호출·시간 상한을 설정값으로 정한다. 운영 수치는
사내에서 조정 가능하게 하며, API 사용량의 엄격한 상한 확인을 로컬 구현 선행조건으로 두지 않는다.
실제 호출·재시도 횟수와 지연은 별도로 관측한다. 리포트 생성은 분석 호출 상한 밖이다.

### 4.4 오류와 커버리지

| 사건 | 기록 및 처리 |
|---|---|
| 복구 가능한 도구 인자 오류 | 기존 `_tool_error_message` 결과 유지. `failed=True`를 붙이지 않음 |
| 복구 불가능한 도구 오류 | 해당 실제 도구 finding에 `failed=True`. 워커 전체 실패와 혼동하지 않음 |
| 그룹 state 누락 | 파이프라인 계약 위반. 빈 그룹/no_data로 변환하지 않음 |
| 워커 LLM 오류 | 워커 식별이 있는 제어 오류 기록. 실행하지 않은 hyp 도구를 failed/ran으로 만들지 않음 |
| 워커 무호출 응답 | 워커 종료. 부모가 계속할지 결정하며 근거 없음 판정으로 번역하지 않음 |
| 탐색 상한 도달 | 결과 병합 후 예약된 메인 마무리 단계. 승인 여부는 기존 게이트가 결정 |
| 마무리까지 소진 | 근거 보존 후 게이트리스 판정. 자동 confirmed 생성 금지 |

워커 LLM 오류 후에는 완료된 기록과 오류를 먼저 반영하고 메인이 이어받는다. 탐색 여유가
없으면 예약 마무리 단계로 이동한다. 같은 실패 워커를 자동 재호출하지 않는다. 이는 현재 메인
LLM 실패 시 전체가 `llm_call_failed`로 종료하는 처리와 다른 **F 정책**이다.
메인도 실패하면 기존 실패 종료를 따르되 수집한 근거는 보존한다.

coverage는 매번 전체 findings와 현재 등록 도구에서 산출한다. 워커 이름은 등록 축이 아니다.
센서 결과는 claim에는 들어가되 등록 가설 축의 ran/statuses/대체 장부에 들어가지 않는 기존
특례를 보존한다. no_data, failed, unrun은 서로 바꾸지 않는다.

## 5. 메시지와 해석 노트

워커 대화는 부모 대화와 분리한다. AI tool call과 대응 ToolMessage는 같은 워커 대화에서
쌍을 이룬다. 부모 대화에 워커의 ToolMessage만 복사해 넣지 않는다.
부모 LLM은 현재 `messages`만 받는다. 따라서 findings 병합만으로 인계가 끝났다고 보지 않는다.
실행기는 병합 완료 후 dispatch 요청에 대응하는 ToolMessage에 아래 **코드 생성 근거 묶음**을
넣는다. 이것이 부모의 다음 분석 입력에 실제 포함되는지 검증한다.

| 필드 | 생성 규칙 |
|---|---|
| `dispatch_id`, `worker_id`, `stop_reason` | 실행기의 실제 제어 상태. 후보 판정 상태와 구분 |
| `audit_revision`, `finding_refs` | 부모가 반영한 최신 기록 버전과 실행 ID. 리스트 위치를 영구 ID로 쓰지 않음 |
| `active_candidates` | 전체 최신 bundle에서 계산한 후보 ID·출처·passes·reject_reason·rank 및 판정 관련 수치. LLM 재작성 금지 |
| `coverage`, `superseded_refs` | 기존 코드가 산출한 전체 커버리지와 대체된 기록 참조 |
| `tool_results` | 해당 dispatch의 실제 도구 결과. 최상위 fdr_table·meta 및 pooling 상세 포함 |

`active_candidates`에는 통과 후보뿐 아니라 약한 후보·표본 미달 후보·센서의 지목 제한도
명시한다. 이는 메인의 선택을 돕는 자료이고, 실제 finalize는 항상 최신 전체 findings로 다시
검증한다. 이전 dispatch 메시지에 남아 있는 후보를 현재 후보로 오인하지 않도록 매 인계와
마무리 호출 직전에 최신 revision의 코드 생성 근거를 전달한다.

첫 단계는 도구가 반환한 원본 결과를 조용히 자르지 않는다. 모델 문맥 한도를 넘으면 실행기가
명시적으로 감지해 축/도구별 페이지와 원본 조회 수단을 제공해야 하며, 총건수·누락 범위·참조를
남긴다. 원본 조회는 이미 실행된 결과의 읽기라 새 통계 계산이나 워커 재실행으로 처리하지 않는다.
마무리 단계 진입 전에 필요한 근거를 준비하고, 원본 조회까지 막는 finalize 전용 단계에서
누락 정보를 복구하도록 요구하지 않는다. 첫 구현에서 페이지 조회를 지원하지 못하면 입력
초과를 명시적 실패로 처리하고, 잘린 입력으로 정상 인계를 가장하지 않는다.

워커의 자유 요약은 이 근거 묶음을 대체하지 않는다.

첫 단계에서는 기존 `thought`/`reason`을 유지하고 별도 자유 해석 노트 채널을 만들지 않는다.
이후 노트를 추가한다면 실행 기록과 구별되는 전용 필드에 출처 call ID를 붙이고, Claim 투영 및
게이트 입력에서는 제외한다. 리포트에서도 측정 사실과 구분해야 한다.
분포 형태 분류 역시 현재 평균·표준편차나 split 값만으로 이름을 붙이지 않는다.

### 5.1 다음 질문으로 이어지는 발전 방향

상세 계약은 [후속 질문·데이터 추천 설계](2026-09-17-후속질문-데이터추천-설계.md)로 구체화했다.
추천기는 F 전체 완성 전에도 리포트 후속 블록으로 구현할 수 있고, 이후 워커 제안을 같은
부모 검증 경로에 연결한다. 현재 단계는 문서 설계이며 자동 실행은 포함하지 않는다.

후속 단계에는 단순 자유 노트 대신 `followup_proposals`를 별도 채널로 둔다.
항목은 `source_refs`, `competing_explanations`, `question`, `required_data`,
`expected_discrimination`과 실행/데이터 상태로 구성한다. 이는 **LLM 제안**이며 Claim이나
passes로 투영하지 않는다. 실행기는 출처가 현재 살아 있는 근거인지, 요청 데이터/도구가
실제로 존재하는지 확인한다. 초기의 단일 `execution_status`는 상세 설계에서
`capability_status`(도구 가능 여부), `data_status`(확보 여부), `blockers`로 분리했다.
도구와 데이터가 동시에 없을 수 있고, 도구 등록이 데이터 보유를 보증하지 않기 때문이다.
효과의 방향은 검증 전 가설로 표시한다.

예: 챔버와 PPID가 같은 wafer 집합을 가리키면 “어느 설명인지 현재 구분 못 한다”를 기록하고,
“챔버는 같고 PPID가 다른 비교군이 있는가”라는 질문과 필요한 데이터를 제안한다.
현재 도구로 못 묻는 조건부 비교는 `needs_new_tool`로 남긴다. LLM이 새 그룹을 만들어 기존
도구에 주입하거나, 같은 도구를 reason만 바꾸어 호출한 뒤 새 검증을 했다고 보고하지 않는다.
새로운 질문의 분모·참조집합·claim 식별자·재실행 대체 단위는 해당 도구 확장 설계에서 정한다.

현재 약한 후보는 `weak_candidate`, 알려진 설명으로 설명되지 않는 이상은
`unexplained_anomaly`라는 문서 용어로 구별한다. 후자는 아직 구현된 판정이 아니며,
`residuals()`를 개명하거나 기존 `weak_signal`의 의미를 바꾸는 작업은 이번 범위에 넣지 않는다.

## 6. 오독 평가 준비

### 비교 조건

멀티에이전트 도입은 확정이다. 아래 비교는 프롬프트와 인계 품질의 개선 자료이며,
단일 에이전트 대비 우위나 API 비용 절감을 증명해야 착수할 수 있다는 조건은 없다.

- A: 현재 통합 프롬프트/도구 설명.
- B: 같은 결과·도구 계약을 받은 축 전용 프롬프트. 숫자나 판정 기준은 바꾸지 않는다.
- pooling 완료 커밋, 설정, 입력 JSON 해시, 모델/서빙 버전, 프롬프트 전문, 원시 응답,
  실행 순서, 반복 번호, 호출 수, 토큰 사용량(제공되는 경우), 지연, 오류를 저장한다.
- 입력 순서를 교차하고 같은 사례를 반복한다. 사례 수와 반복 수는 실행 전에
  고정한다. 작은 파일럿은 오류 유형 발견용이며 개선 효과를 확정하는 자료로 쓰지 않는다.
- 그래프 없이 고정 JSON으로 하는 1차 평가는 **해석 품질만** 측정한다. 후속 도구 선택과
  탐색 깊이, 종단 지연은 별도 실행 평가가 필요하다. mock은 평가 배선 확인에만 사용한다.

### 사례와 채점 기준

| 사례 | 오독으로 세는 응답 |
|---|---|
| 높은 score, `n_reference=0` | 통계적으로 확인됐다고 채택하거나 p=1을 확정적인 무신호로 해석 |
| `target_total != n_target` | 질문별 분모를 전체 그룹 크기로 설명 |
| 구조화 식별자와 구분 문자가 든 key | key 문자열을 자의적으로 분해해 다른 식별자를 만듦 |
| `p_at_floor=true`, 축마다 해상도 다름 | p 숫자만 비교해 우열을 단정 |
| 반올림된 p와 floor가 같지만 `p_at_floor=false` | 숫자 일치만 보고 바닥에 닿았다고 단정 |
| fdr_table와 후보별 p가 함께 있음 | 목록 단위 정보를 후보별 확률로 표현하거나, 목록 신뢰도를 묻는 질문에 관련 정보를 누락 |
| pooled/MH의 부호 또는 임계 구간이 다름 | 합산 카운트로 score를 재계산해 대체하거나 score_pooled로 판정 |
| 센서만 passes=true | 센서 claim을 원인 확정 지목 대상으로 선택 |
| 후보 재실행 대체/부분 커버리지 | 대체된 후보를 현 근거로 인용하거나 안 본 축까지 이상 없음으로 단정 |
| thin_sample/weak_signal/no_data/failed | 표본 미달·약한 분리·비교 불가·실행 실패를 동일한 무신호로 설명 |

각 사례에 질문, 기대 사실, 금지 주장, 해당하는 오류 유형을 함께 저장한다. 요구하지 않은
정보의 단순 생략은 자동 오류로 세지 않는다. 판단 불가 응답은 별도로 세며, 침묵이 많은
모델을 오독률만 낮다는 이유로 개선으로 판정하지 않는다.

수치·식별자는 기계 대조하고, 의미 판단은 A/B 정보를 가린 채 사람이 채점한다. 상충 판단은
근거와 함께 다시 판독한다. 오류 종류별 분모, 사례별 A/B 차이, 필수 사실 응답률을 보고한다.
실패한 LLM 호출도 제외하지 않고 별도 실패율로 보고한다.

**평가의 사용:** 오독 유형별로 프롬프트·근거 묶음·인계 절차를 보완하고 재측정한다.
개선 폭이 작아도 멀티에이전트 목표를 철회하지 않는다. 로컬 구현과 사내 품질 평가는 분리한다.
통합 평가에서는 유효한 후속 질문, 불필요한 동일 조회, 최종 보고서의 근거 누락, 잘못된
확정 주장과 종료 성공을 함께 본다. 호출량·지연은 운영 관측치이고 필요성 심사의 기준이 아니다.
중요한 계약 위반은 구현 수용 기준으로 막고, 해석 오류는 사내 운영 전 수정·재검증한다.

## 7. 구현 시 잠글 수용 기준

아래는 향후 테스트 요구사항이며 이번에 실행한 테스트가 아니다.

| ID | 확인할 계약 |
|---|---|
| F1 | 같은 입력/설정/도구 호출열의 실제 args·result와 bundle 후보·순위·coverage 동일. loop·thought·제어 사건은 비교에서 분리 |
| F1b | 같은 최신 근거·finalize 제출·종료 문맥이면 기존 게이트와 판정 동일. 다른 호출 예산/LLM 선택까지 종단 동일성을 요구하지 않음 |
| F2 | 워커가 준 그룹은 코드 값으로 대체되고 실제 인자가 감사 기록에 남음. 그룹 누락은 명시적 오류 |
| F3 | 정상·복구 가능·복구 불가능 도구 오류 분류가 기존 경로와 동일 |
| F4 | 후보 있음 → 빈 후보 재실행, 동일 후보 재생성, 실패 → 성공의 대체/실패 집계가 기존과 동일 |
| F5 | 워커 중도 실패에도 이전 결과 보존. 필수 ID 검증, 동일 ID/payload 중복 무시, 같은 ID/다른 payload 오류, 실제 재실행 기록 유지 |
| F6 | 노출되지 않은 도구/finalize를 조작해 호출해도 실행되지 않고 coverage를 오염시키지 않음 |
| F7 | 탐색 마지막 회차의 결과도 메인 마무리 입력에 포함. 워커가 예약 2회를 소진하지 못함. 마무리 반려/무호출/LLM 실패/소진별 종료와 근거 보존 검증 |
| F8 | 센서 특례와 SENSOR_MODE=off 보존, 워커 완료를 hyp 실행 완료로 세지 않음 |
| F9 | 원본 result의 pooling 필드 및 기타 추가 필드가 부모/리포트까지 보존 |
| F10 | 부모/워커 메시지의 tool call 응답 대응 완전성, 부모 대화에 고립된 워커 ToolMessage 없음 |
| F11 | 부모 analyze_step의 실제 messages에 최신 revision 근거 묶음이 존재. 대체된 후보 갱신 및 문맥 초과 명시 처리 |
| F12 | 감사 loop가 옛 MAX_LOOPS를 넘어도 탐색 여유가 있으면 강제 종료하지 않음. 실제 종료 트리거와 리포트 문구 일치 |
| F13 | 후속 질문 기능 도입 시 출처 검증·실행 가능 여부 표시, 제안으로 인한 passes/그룹 변경 없음, 동일 wafer 설명 중복으로 강도 가산 없음 |

기존 회귀 기준은 `tests/test_graph_nodes.py`의 그룹 주입·실패·대체·게이트리스 종료 테스트와
`tests/test_evidence.py`, `tests/test_agent_tools.py`다. 구현 시 고정된 기준선에서 먼저 기존
테스트를 확인하고, 첫 단계 F1~F12(추가 F1b 포함) 및 필요한 통합 테스트를 추가한다.
F13은 후속 질문 채널 구현 단계의 요구사항이다.

## 8. 순서와 남은 결정

1. **완료(이번 문서):** 현재 코드 사실 정정, 병합/예산/권한 경계 설계안, 평가 사례와 수용 기준.
2. **pooling 완료 후:** 최종 커밋으로 재대조하고 고정 JSON과 정답 자료를 만든다.
3. **구현 plan:** 공통 실행 경로 → 순차 경로 워커 1개 → 근거 인계·종료 예약·동일 호출열 검증.
   실행 가드레일 기본값, 도구별 소유권과 독립 리뷰 절차를 명시한다. 사내 효과 측정을 기다리지 않는다.
4. **사내 검증:** 평가 모델 연결, Msg-Id/재시도 규약 확인, 사례/반복 수를 고정해 오독·인계·
   후속 선택을 측정하고 개선한다. 동시 요청 한도는 병렬화 전에 확인한다.
5. **확대:** 분포/EDS 워커 연결, 후속 질문 채널. 단계마다 기존 근거·판정 계약을 검증한다.
6. **별도 도구 확장:** 새로운 grain·필터 탐색은 질문과 통계 참조집합,
   재실행 대체 단위를 함께 설계한 별건으로 다룬다.

다음 작업은 pooling 최종 기준선 위에서 구현 plan을 작성하는 것이다. 멀티에이전트의 필요성
검증과 사내 비용 상한 확인은 착수 조건에서 제거했다. API 사용량 여유와 별개로 유한 실행·
실패 인계·정상 종료 계약은 유지한다. 이번 작업은 문서 보완이며 사내 호출이나 제품 코드 수정,
자동 handoff는 수행하지 않았다.
