# 수율 조사 에이전트의 방향과 다음 작업

작성: 2026-09-22. 두 commonality 문서, 현재 코드, 사용자와의 방향 논의를 통합했다.
상태: **합의한 방향과 진행 순서. 구현 완료나 실데이터 검증 결과를 뜻하지 않는다.**
제품 코드 변경은 작업별 `docs/tasks/<task>/plan.md`에서 소유 범위·수용 기준·리뷰를 정한 뒤 진행한다.

## 1. 목표

**공정 이력에서 후보를 찾는 분석기를 기반으로, 무엇을 비교할지와 다음에 무엇을 확인할지를
근거에 연결하는 수율 조사 에이전트로 발전시킨다.**

결과는 다음 다섯 질문에 답해야 한다.

1. 무엇을 설명하는가: 불량 현상·관측 단위·영역·bin·지표·타깃 선정 근거.
2. 무엇과 비교했는가: 대조군 선정 이유·고정 조건·비교 가능 범위.
3. 어떤 후보가 남았는가: 지지 근거·경쟁 설명·표본·결측.
4. 무엇이 설명되지 않는가: 반대 근거·예외 사례·미확인 항목.
5. 다음에 무엇으로 구별하는가: 질문·필요 데이터·비교 조건·도구·실행 가능 여부.

## 2. 현재의 문제와 재사용할 기반

| 문제 | 영향 |
|---|---|
| 원인이 확정된 과거 이슈에서 결과·근거의 타당성 검증이 부족함 | 테스트·더미 결과만으로 현장 원인 탐색 능력을 판단할 수 없음 |
| wafer 집합에 비해 불량 현상과 지표의 정의가 부족함 | 전체 수율과 특정 영역·bin 불량을 구분해 설명하기 어려움 |
| 대조군이 같은 root_lot의 비타깃으로 제한됨 | lot 전체 원인·lot 사이 차이·시간 전후 차이에 한계 |
| 시간·순서·사건 분석 도구가 부족함 | 같은 설비에서도 특정 조건에서만 발생하는 불량을 설명하기 어려움 |
| 후보 탐색 이후의 조사 연결이 부족함 | 교락·약한 신호·비교 불가에서 구체적인 다음 행동으로 이어지기 어려움 |

현재 코드에는 EDS 유사맵, 설비·챔버·PPID·스텝 통과·계측 commonality, 센서 비교,
순열 기반 통계, 설비 commonality의 MH 층화, 후보·교락 관리, 감사 기록과 종료 처리가 있다.
이를 재사용한다. 현재 통계는 주어진 비교와 가정 안의 근거이며 인과성이나 현장 원인 확정을
보증하지 않는다. 계측 commonality의 pooled 분할점 탐색 등 기존 제약도 유지해서 기록한다.

정확히 구분할 것:

- 비타깃은 양호가 확인된 집합이 아니다.
- lot 전체 불량이 반드시 `no_signal`로 끝나지는 않는다. 비교군·결측·실행 경로에 따라 다르다.
- EDS 유사맵 기능과 명시적인 영역·bin별 불량 지표는 서로 다른 기능이다.
- 센서·계측 등 입력값의 차이와, 설명할 결과인 불량 정도의 연속값 분석은 다른 질문이다.
- 과거 사내 적재·연동 기록의 존재와, 원인 확정 사례를 이용한 조사 효용 검증은 구분한다.

## 4. 설계 원칙

1. 기존 그래프와 근거 관리 구조를 유지한다. 판정 의미론의 추가 정교화는 실제 사례가
   요구할 때 검토한다. 확인된 결함의 수정이나 새 질문에 필요한 통계 설계까지 금지하지 않는다.
2. 코드가 계산·식별자·출처·실행 상태를 관리하고, LLM은 해석과 질문·분석 방향을 제안한다.
3. Hint는 관측 단위·데이터 범위·출처를 갖는다. 계산 결과, 사람의 제보, LLM 추정을 구분하고
   미확인과 미검출을 분리한다. Test·Map 미확인만으로 가능한 모든 분석을 막지 않는다.
4. 라우팅 규칙은 조사 우선순위를 안내한다. 데이터·도구 가용성, 기수행 결과, 경쟁 설명을
   구별하는 데 도움이 되는지를 함께 보며, 단서를 원인으로 단정하지 않는다.
5. 비교 조건을 바꾼 후속 분석은 명시적인 별도 실행으로 남긴다. 그룹·선정 이유·조건·원천 범위·
   실행 결과를 이전 질문과 연결한다. 기존 실행의 그룹을 조용히 덮어쓰지 않는다.
6. lot 간 비교는 비교 가능한 제품·route·시기와 분석·순열 단위를 별도 설계한다.
   lot 내부 MH·순열 방식을 그대로 확대하거나 wafer 수를 독립 lot 수처럼 세지 않는다.
   반복적인 조건 탐색의 통계적 해석과 독립적인 재확인도 구분한다.
7. timestamp 차이를 바로 정체시간으로, wafer 번호를 실제 처리 순서로 간주하지 않는다.
   빈도 분석은 처리 스텝 수·재작업에 따른 노출 증가도 검토한다.
8. 양호 사례 존재만으로 후보를 제거하지 않는다. 어느 가설의 반례이며 어떤 조건부 설명이
   남는지 기록한다. 차이 미검출을 이상 없음으로 바꾸지 않는다.
9. 데이터 부족·도구 실패·새 분석 없음·예산 소진에도 보고한다. 근거가 충분해질 때까지
   무한히 반복하지 않으며, 필요한 데이터와 미확인 이유를 남긴다.

## 5. 진행 순서

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1. P1-3 사례 확보 | 보완한 요청서로 3~5건 확보. 기능 검증 사례와 lot 전체 영향 등 한계 확인 사례 포함 | 원천 의미·범위 확인, 별도 적재 및 검증, 초기 현상·최종 원인·확정 근거·정보 시점 확보 |
| 2. P1-4 실측 | LLM 없이 기존 commonality를 실행하고 최종 원인·확정 근거와 대조 | 후보 적중·경쟁 설명 구별·근거 부족에 대한 처리와 필요 데이터 정리 |
| 3. P2-5/6 조사 결과·추천 | 교락 설명과 근거에 연결된 후속 질문·필요 데이터 출력 | 추천별 출처·조건·데이터·실행 상태 보존, 기존 판정 불변 |
| 4. 필요한 분석 확장 | 사례에 따라 조건부 비교, lot 간 비교, 시간·순서·빈도·불량 정도 분석 선택 | 질문에 맞는 데이터·통계 계약과 의미 있는 검증 확보 |
| 5. P3-9 실행 연결 | 후속 비교를 별도 실행하고 이전 조사와 연결 | 제안 → 데이터 확인 → 실행 → 판단 갱신 추적 |
| 6. P4-10 F 통합 | 가용 분석 기능을 단서 기반 선택과 워커 분담에 연결 | 워커들이 실제로 서로 다른 질문을 조사하고 근거를 일관되게 통합 |

P3-7(`where`)·P3-8(group 계약)은 4단계에서 필요한 비교에 맞춰 결정한다. 새로 적재된
다른 lot이 있다고 현재 계약에서 자동 비교되는 것은 아니다. 별도 후속 실행과 실행 중
그룹 변경은 다른 선택이며, 자유로운 그룹 변경을 필수 목표로 두지 않는다.

‘비용이 싼 분기’를 고정된 선행 단계로 추가하지 않는다. 컬럼 존재만으로 구현 비용이나
통계적 타당성을 판단할 수 없으며, 실제 사례가 lot 사이 비교를 요구하면 그것을 먼저 설계한다.
F는 합의된 목표로 유지하고 라우터를 별도 경쟁 설계로 만들지 않는다.

## 6. 지금과 P1-3 답변 이후의 구체 작업

### 지금 받을 것

[P1-3 요청서](P1-3-원천추출-요청서.md)는 보완 완료됐다. 답변은 아래 세 묶음이다.

- 사례별 수율·전체 공정 이력 파일과 컬럼 대응·단위 설명. 사용자가 직접 추출한다.
- 엔지니어에게 필수로 받을 것: 초기 현상·타깃·불량 기준, 최종 원인과 확정 근거,
  당시 이용 가능했던 정보와 나중에 알게 된 정보의 구분. 최종 원인·확정 근거는 평가 자료로 분리한다.
- timestamp·슬롯·실제 순서·추가 비교 lot 자료 등의 의미와 제공 가능 여부. 불가·미확인도 답변이다.

상세 조사 순서·배제 후보·헷갈린 설명·조사 기간은 선택 자료다. 없더라도 사례 검증이나
후속 질문 범위 결정을 막지 않는다. 확정 근거는 비교·재현·조치 후 결과 등으로 받는다.

추가 자료 확보 때문에 기본 자료 전달을 늦추지 않는다. PM·자재·처리 시각 등 원천 확보
가능성은 병행 확인한다. 제공 불가 항목은 기능 범위와 후속 조사 제약을 정하는 입력이다.

### 답변을 받으면

1. **자료 검수:** 키·수율 단위·PPID 관측 단위·전체 wafer/스텝·재작업·결측·시각 의미 확인.
   초기 입력과 정답·추가 조사 자료를 분리하고 모호한 항목만 구체적으로 재확인한다.
2. **적재 준비 및 검증:** 실제 파일 형식에 맞춰 CSV/parquet 입력 어댑터와 사례 DB 경로를
   정한다. 현재 `_extract()`는 미구현이므로 필요 구현은 별도 plan으로 진행한다.
   더미 DB를 보존하고 `load()`·`validate()`의 fatal 0건과 경고·조인·단위를 확인한다.
3. **최초 실행 고정:** 타깃·대조군·root_lot별 표본·설정·입력 범위를 결과를 보기 전에 기록한다.
4. **P1-4 실행:** 사내 LLM·EDS·센서 연결 없이 기존 도구를 직접 실행한다. 후보·순위·분모·
   제외 이유·비교 불가·실패를 남긴다. 실제 사례 분석과 새 기능 구현은 섞지 않는다.
5. **결과·근거 대조:** 최초 결과를 기록한 뒤 최종 원인·확정 근거를 열어, 아래 표로 기능 공백을
   정리한다. 상세 조사 경로가 있으면 실패 원인 진단·효율 비교의 보조 자료로만 사용한다.
6. **다음 구현 plan 확정:** P2-5/6 범위와 그 이후 필요한 도구·비교 계약의 순서를 결정한다.
   정답을 보고 조건·설정을 바꾼 실험은 최초 평가와 구분한다.

### 자료 대기 중 가능한 일

기존 순서상 P2-5 교락 설명 보완은 독립 착수 가능하다. 필요하면 별도 plan으로 진행하되,
이번 문서 저장이 제품 코드 변경 착수를 뜻하지는 않는다. P2-6은 실제 사례로 우선 범위를 정한다.
데이터 회신만으로 P1-3 완료를 선언하지 않으며, 적재 검증까지 확인한다.

## 7. 평가 기준과 한계

원인 후보 적중뿐 아니라 비교의 타당성, 한계 보고의 정확성, 다음 질문의 구체성,
실행 가능 상태의 정직성, 원본 근거까지의 추적 가능성을 평가한다.
한계 확인 사례에서는 현재 도구의 원인 적중을 필수로 요구하지 않는다.
핵심 평가는 (1) 알려진 원인 후보 탐색, (2) 경쟁 설명을 구별할 근거,
(3) 데이터 부족 시 확정 보류와 필요한 확인의 식별이다. 조사 순서 일치는 성공 조건이 아니다.

선별한 3~5건은 기능 공백을 찾는 출발점이며 사내 원인 발생 비율의 추정 표본이 아니다.
사례 한 건에서 유용했다고 일반적인 효과까지 검증된 것으로 보지 않는다.
이번 작업은 방향 문서 저장이며, 새 실데이터 평가나 제품 테스트를 실행한 결과가 아니다.
