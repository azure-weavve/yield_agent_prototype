# 사내 투입 점검표 — 무엇을 확인하고, 어떻게 확인하는가

사내망에서 프로토타입을 처음 돌릴 때 **손에 들고 순서대로 확인하는** 문서다.
2026-08-02 기준 코드 직접 검증 결과이며, 명령과 파일 경로는 실제로 존재하는 것만 적었다.

**이 문서가 아닌 것**

- 무엇을 바꿔야 하는지의 체크리스트는 [`사내-데이터-변환시-할일.md`](사내-데이터-변환시-할일.md)
- ID 체계·ETL 조인 규칙 상세는 [`internal-data-integration.md`](internal-data-integration.md)
- 사내 연동 전에 미뤄 둔 항목은 [`deferred-internal-integration.md`](deferred-internal-integration.md)

이 문서는 **"확인 절차와 판독법"** 만 다룬다. 특히 4장(조용히 틀리는 것들)이 핵심이다 —
에러 없이 틀린 답을 내는 상태들이라, 절차를 모르면 그냥 지나간다.

## 2. `_extract()` 입력 계약

`data/load_internal.py:455` 의 `_extract()` 가 아래 형태로 반환하면 나머지는 스크립트가 한다.
**원천 컬럼명을 그대로 통과시켜도 된다.**

```python
yield_records : [{root_lot_id, wafer_id, lot_id, lot_type, yield, date,
                  defect_type(optional)}, ...]          # wafer 1장당 1행
step_records  : [{root_lot_id, wafer_id, step_seq, eqp_id,
                  area(optional), ch_id(optional), ppid(optional),
                  timestamp}, ...]                      # wafer×스텝당 1행
```

`step_records` 는 커도 되므로 리스트 대신 제너레이터를 반환해도 된다.

### 이름이 겹쳐서 가장 헷갈리는 지점 셋

| 필드 | 원천 | 이 프로토타입 | 변환 주체 |
|---|---|---|---|
| `wafer_id` | 두 자리 **순번** (`"01"`, `"13"`) | **합성 조인 키** (`"A45Z5_01"`) | 스크립트가 `root_lot_id + "_" + zero-pad(순번,2)` 로 합성 |
| `lot_type` | 사내 **두 자리 코드** (`"PP"` 양산 · `"ES"` 평가) | `"prod"` / `"eval"` | `classify_lot_type()` (첫 글자 `P` = 양산) |
| `step_seq` | 순번 코드 (문자2 + 숫자6) | 그대로 | 없음. **공정명(`area`)과 뒤바뀌지 않게 주의** |

순번 키는 `wafer_no` 로 넘겨도 받는다(`_wafer_no()`).

> **조인은 바이트 단위 일치를 요구한다.** `yield` · `step_history` · **EDS 응답** 세 곳의
> wafer 식별자가 모두 같은 형태여야 한다. EDS 가 다른 체계를 쓰면 `HttpEDSSearcher` 에서
> 조립해야 한다 (5-2 참조).

## 3. 적재와 검증

### 3-1. 적재 실행

```bash
python -X utf8 -m data.load_internal
# 스크립트 경로(`python -X utf8 data/load_internal.py`)로도 돌아가지만, `-m` 이
# 회귀 테스트가 검증하는 경로다. 둘 다 저장소 루트에서 실행한다.
# 종료코드 0 = DB 교체됨 / 1 = fatal 있어 교체 중단
# 치명적 오류를 무시하고 교체하려면 --force
# 다른 경로로 적재하려면 --db 경로
```

### 3-2. 출력 판독

스크립트가 이런 형태로 찍는다.

```
[적재] yield 812행 / step_history 794,336행
[구성] root_lot 34개 · 이력 보유 wafer 812장 · lot_type {'prod': 780, 'eval': 32}
[이력] wafer 당 스텝 {'min': 940, 'max': 1010, 'avg': 978.3} · ch_id 결측률 0.02 · ppid 결측률 0.0 · area 결측률 0.0
[라벨] defect_type 보유 0건 (없으면 EDS 로 그룹을 만든다)
[정합성] 이상 없음
[교체] .../data/yield.db 갱신 완료
```

**`[라벨] defect_type 보유 0건` 은 정상이다.** 사내 라벨은 대부분 NULL 이고, 그룹은 EDS 가 만든다.

### 3-3. 치명적 오류 (교체 차단)

이게 뜨면 DB 가 안 바뀐다. 원천이나 매핑을 고쳐야 한다.

| 메시지 | 뜻 | 확인할 것 |
|---|---|---|
| `yield 0행: 추출 결과가 비었다` | `_extract()` 가 빈 결과를 냈다 | 추출 쿼리·필터 |
| `wafer_id 형식 위반 N건` | 합성 키가 `..._숫자2자리` 형태가 아니다 | 순번이 3자리 이상이거나 문자가 섞였는지 |
| `root_lot_id 불일치 N건` | `wafer_id` 접두와 `root_lot_id` 가 다르다 | 두 컬럼이 다른 원천에서 왔는지 |
| `step_history 고아 wafer N/M건` | 이력엔 있는데 yield 에 없는 wafer. **50% 초과 시 fatal** | **조인 키 불일치의 주 증상.** yield 쪽 추출 범위가 좁은지 |
| `step_history 없는 wafer N/M건` | yield 엔 있는데 이력이 없다. **50% 초과 시 fatal** | commonality 분모에서 빠진다. 이력 추출 범위 |

### 3-4. 경고 (교체는 되지만 봐야 함)

| 메시지 | 뜻 | 확인할 것 |
|---|---|---|
| `step_seq 형식 위반 N종` | 문자2+숫자6 이 아니다 | **`step_seq` 와 `area` 가 뒤바뀌어 실렸을 가능성.** 이러면 공정명(`"Etch"`)으로 묶인 후보가 그럴듯하게 나와서 더 위험하다 |
| `wafer×스텝 중복 이력 N건` | 같은 wafer 가 같은 스텝을 여러 번 | 재작업(rework)이면 정상. 아니면 조인 중복 |
| `yield 범위(0~100) 이탈 N건` | 단위가 다르거나(0~1) 결측 표현이 섞임 | 원천 단위 |
| `양산(prod) lot 0건` | `classify_lot_type()` 이 전부 eval 로 판정 | 원천 `lot_type` 코드 첫 글자가 `P` 인지 |

## 4. 조용히 틀리는 것들 (이 문서의 핵심)

**에러도 경고도 안 뜨는데 답이 틀리는 상태들이다.** `[이력]` 줄의 결측률 숫자를
직접 눈으로 봐야 하고, 4-2 는 **적재 리포트로는 아예 안 보인다.**

### 4-1. `ppid 결측률 1.0`

`hyp_ppid_commonality`(2차 가설)가 **에러 없이 후보 0** 으로 끝난다. 게이트는 이걸
"PPID 로는 안 갈린다" 로 읽는데, 실제로는 **PPID 가 안 실린 것**이다. 두 상태를 구분할
수 없게 된다.

→ 원천에 ppid 가 있는데 안 실렸는지, 아니면 그 스텝들에 PPID 개념이 없는지 확인.

### 4-2. `ppid` 조인 단위 — **자동 검사 없음. 원천 쿼리를 사람이 볼 것**

ppid 가 wafer×스텝 이력이 아니라 **lot·레시피 마스터에서 조인**돼 오면, 결측률은
`0.0`(초록)인데 `hyp_ppid_commonality` 가 에러 없이 **틀린 집계**를 낸다. 타깃군이 한 lot
에 몰려 있으면 "PPID_X: 타깃 전원 통과 / 대조군 0" 이라는 분리 점수 1.0 후보가 만들어지고
게이트가 정상 승인한다. 실제로 말한 내용은 **"그 wafer 들이 같은 lot 이다"** 뿐이다.

**적재 리포트로는 이걸 구분할 수 없다.** 세 상태가 테이블 안에서 같은 모양이기 때문이다.

| 상태 | lot×스텝 안 wafer 간 ppid | wafer 의 스텝 간 ppid |
|---|---|---|
| lot 마스터 조인 (lot 하나에 ppid 하나) | 동일 | **동일** — 물리적으로 불가능한 모양 |
| lot×스텝 마스터 조인 (레시피 마스터) | 동일 | 갈림 |
| 정상 (wafer×스텝 단위) | **대개 동일** (도메인상 정상) | 갈림 |

아래 두 줄이 lot 마스터 조인만은 걸러낸다. 나머지 둘은 구분 불가다.

```sql
-- wafer 의 스텝 간 ppid 가 1종뿐이면 lot 마스터 조인 (정상 데이터에서는 나올 수 없다)
SELECT COUNT(*) FROM (SELECT wafer_id FROM step_history WHERE ppid IS NOT NULL
                      GROUP BY wafer_id HAVING COUNT(DISTINCT ppid) = 1);
```

> **여기 있던 `[grain]` 자동 진단은 2026-08-03 에 삭제했다.** lot 안에서 ppid 가 안 갈리는
> 것을 의심 신호로 읽었는데 그게 도메인상 **정상**이라(같은 root_lot 을 PPID 시험용으로
> 나눌 때만 갈린다) 세 상태를 구분하지 못했다. 실제로 `6,000/1,300,000` 이라는 비율을
> 보고 사람이 "99.5%가 그러면 조인 문제" 라는 틀린 판단을 했다. 없는 지표가 틀린
> 지표보다 낫다고 보고 지웠다.

→ **할 일: 원천 추출 쿼리에서 ppid 조인 키를 확인한다** (1장 4번). 조인 키가 `lot_id` 나
레시피 마스터면 그 컬럼은 쓸 수 없고, `hyp_ppid_commonality` 결과를 믿지 않는다.

### 4-3. `area 결측률 1.0`

분석은 멀쩡히 돈다. 다만 리포트의 스텝이 `CC002000` 뿐이라 **사람이 무슨 공정인지 못 읽는다.**
증상이 없어서 놓치기 쉽다.

### 4-4. `ch_id 결측률` 이 높음

commonality 가 **챔버 레벨을 거의 못 쓴다.** 설비 레벨만 남으므로 원인 지목이 거칠어진다.
에러는 안 난다.

## 5. LLM 없이 tool 단위 검증

LLM 변수를 빼고 **어디서 깨지는지**를 먼저 가른다. 파이프라인 순서대로 직접 호출한다.

```bash
python -X utf8 -c "
from tools import yield_tools as yt, target_selection, grouping
from domain import registry, engine

# (1) 이상 lot
lots = yt.find_low_yield_lots()
print('이상 lot', len(lots), lots[:5])

# (2) 대상 선정
targets = target_selection.auto_select_targets()
print('타깃', targets)

# (3) EDS 형제 묶기
norm = grouping.normalize_target(targets[:1])
print('normalize', norm)

# (4) 대조군
group = norm.get('target_group') or targets
ctrl = grouping.select_control(group)
print('대조군', ctrl)

# (5) 1단 commonality
spec = next(s for s in registry.load_hypotheses() if s['id']=='eqp_ch_commonality')
res = engine.evaluate(spec, group, ctrl['control_group'])
print('status', res['status'])
for c in res['candidates'][:5]:
    print(' ', c['claim_id'], 'score', c['score'], 'passes', c['passes'], c.get('reject_reason'))
"
```

### 5-1. `find_low_yield_lots` — 이상 lot 이 상식적인가

| 결과 | 의심 | 대응 |
|---|---|---|
| 0건 | `YIELD_THRESHOLD=90` 이 사내 분포와 안 맞는다 | **여기서 멈춘다.** 임계값 조정 필요 (8장 참조) |
| 거의 전부 | 평가랏이 섞였다 | 7장 b번(`lot_type` 필터)의 근거가 된다 |

### 5-2. `normalize_target` — EDS 첫 시험대

**사내 EDS 가 여기서 처음 불린다.** 응답 필드명이 추정값이라 틀어질 확률이 높다.

현재 `HttpEDSSearcher`(`tools/eds_search.py:66`)가 가정하는 것:

```python
# 요청
{"line_id": "S3", "product": "All Products", "wafer_id": ..., "n_results": k}
# 응답
{"query_wafer": {...}, "similar_wafers": [{"rank":…, "wafer_id":…, "similarity":…}, …]}
```

확인할 것:

- [ ] 요청 파라미터명·고정값(`line_id="S3"`, `product="All Products"`)이 맞는가
- [ ] 응답의 유사 wafer 배열 키가 `similar_wafers` 인가
- [ ] 각 항목의 식별자 키가 `wafer_id` 이고, **값이 `{root_lot}_{순번}` 체계인가** (다르면 조립 필요)
- [ ] 유사도 키가 `similarity` 인가, 스케일은 무엇인가

> ⚠️ **`EDS_MIN_SIMILARITY=0.5` 절대 임계는 지금 적용 보류 상태다.** 사내 similarity 가
> 음수 스케일(예 -0.18 ~ -0.23)이라 걸면 전량 제외된다. 서버 rank 순 + top-k 로만 컷하고
> 있다. 실제 분포를 확인한 뒤 임계를 정한다.

실패해도 크래시하지 않고 `eds_lookup_failed` 조기 출구로 나온다.

### 5-3. `select_control` — 대조군이 잡히는가

`CONTROL_MIN_SIZE=3` 미만이면 확장하지 않고 정직하게 보고한다. 여기서 막히면 대조군
정의(같은 root_lot 비타깃 전원)부터 다시 봐야 한다.

### 5-4. `engine.evaluate` — 1단 commonality

볼 것 셋:

- [ ] 후보마다 `claim_id` 가 붙는가 (형식: `eqp_ch_commonality:chamber:CC002000:ETCH9_B`)
- [ ] `status` 가 `ok` 인가 `no_signal` 인가
- [ ] **`passes` 가 전부 `False` 는 아닌가**

`passes` 가 전부 False 면 `COMMONALITY_PASS_MIN_SCORE=0.5` / `COMMONALITY_PASS_MIN_TARGET=2`
가 사내 분포에 안 맞는 것이고, 그러면 **E2E 가 항상 반려로 끝난다.** `reject_reason` 에
어느 조건에 걸렸는지 나온다.

```bash
"
```

- [ ] `HttpSensorStore.fetch(step_seq, wafer_ids)` 요청/응답 스키마가 맞는가
- [ ] `SENSOR_MIN_SAMPLE=3` 미만이면 비교하지 않고 그 사실을 보고한다 (정상 동작)

### 실제 LLM 에서만 드러나는 실패

mock 은 각본이라 절대 안 내는 것들이다.

| 증상 | 원인 | 대응 |
|---|---|---|
| **`반려: claim_id '...' 는 도구 결과에 없다`** 가 반복 | LLM 이 claim_id 를 줄이거나 지어냈다 | **이번 게이트 작업이 만든 새 요구다. 실전 첫 시험대가 여기일 가능성이 높다.** 반복되면 `graph/nodes.py:44` 의 `ANALYZE_SYSTEM_PROMPT` 를 조인다 |
| `반려: claim_id 를 제출하지 않았다` | LLM 이 문장으로만 결론을 냄 | 위와 같음 |
| 엉뚱한 tool 이름 | LLM 환각 | **이미 방어됨** — ToolMessage 로 복구된다 |
| 비숫자 confidence | LLM 이 `"high"` 등을 냄 | **이미 방어됨** — 게이트가 형식 오류를 안내한다 |
| 한 메시지에 tool_call 여러 개 | 실제 LLM 에서만 발생 | **이미 방어됨** |

## 8. 임계값 — "튜닝" 과 "막힘" 을 구분할 것

정합성 맞추기(튜닝)는 나중으로 미뤄도 된다. 다만 **아래 둘은 "안 돌아감" 으로 나타나므로**
튜닝이 아니라 막힘 해소로 다뤄야 한다.

| 값 | 기본 | 안 맞으면 |
|---|---|---|
| `YIELD_THRESHOLD` | 90.0 | 5-1 에서 이상 lot 0건. **거기서 멈춘다** |
| `COMMONALITY_PASS_MIN_SCORE` / `_MIN_TARGET` | 0.5 / 2 | 후보가 전부 `passes=False`. **E2E 가 항상 반려**로 끝난다 |

나중에 볼 것: `EDS_MIN_SIMILARITY`, `SIBLING_MIN_SIMILARITY`, `MAX_LOOPS`,
`CONFIDENCE_THRESHOLD`, `SENSOR_TOP_K`, `SENSOR_MIN_SAMPLE`, `CONTROL_MIN_SIZE`.
